# anyOS Subsystem Audit — Detailed Findings

_Per-subsystem output from the 12 audit agents. 151 problems found (9 critical, 54 high, 56 medium, 32 low). See [ROADMAP.md](ROADMAP.md) for the synthesized plan._

---

## MEMORY — kernel memory (physical/buddy/heap/virtual_mem/vma/physmap/slab/swap/user_vmap + page-fault & demand-paging)

**Architecture:** The memory subsystem is layered and mostly well-factored. Physical allocation is a two-stage design (physical.rs): a stage-1 bootmem bitmap that comes up at entry, then a migration to a buddy allocator (buddy.rs) with two zones — ZONE_DMA (<64 MiB, the universal identity window) and ZONE_NORMAL (the rest). The buddy uses intrusive free lists stored in the freed pages themselves, reached via physmap (physmap.rs), a 2 MiB-huge-page direct map at PML4[384] (0xFFFF_C000_0000_0000) mirroring Linux's __va. A FrameAllocPolicy {LowIdentity, Any} enum routes legacy "phys as *mut" callers to ZONE_DMA. State lives in module-level Spinlock<BuddyZone> statics (BSS arrays sized for a hard 16 GiB cap).

Virtual memory (virtual_mem.rs, 1996 lines, x86_64) uses 4-level paging with PML4[510] recursive self-map. It owns map_page/unmap_page, the *_in_pd CR3-switching foreign-PD helpers, create/clone/destroy_user_page_directory (fork is EAGER full-copy, no CoW), PCID support, guard pages (PTE_GUARD bit 10), and the heap+mmap demand-paging fault handlers. aarch64 swaps in virtual_mem_stub.rs via cfg in mod.rs. The kernel heap (heap.rs, 1075 lines) is a sorted address-ordered linked-list free-list with demand-paged growth, fronted by per-CPU size-class buckets (32 B..128 KiB, 13 classes) and per-CPU overflow free-list caches, all lock-free with IF=0; the slow path takes one global IRQ-safe atomic spinlock. A SLUB-style object cache (slab.rs) sits above the buddy for fixed-size objects (KBox/KmemCache), used by vma.rs. Per-process mmap regions are tracked in vma.rs as a slab-backed sorted singly-linked list per page-directory, in a global Spinlock<Vec<ProcessVmas>> scanned linearly.

Swap (swap.rs, 290 lines) is the critical gap: it is a backing-store-and-slot-registry STUB ONLY. swapon/swapoff register a file, a bitmap allocates/frees slots, and write_page/read_page do the file I/O — but write_page/read_page/allocate_slot/free_slot have ZERO callers anywhere in the tree (confirmed by grep). There is no page-out/eviction path, no victim selection (no clock/LRU/second-chance), no kswapd-equivalent reclaim daemon, no swap-in on page fault, and no PTE swap-entry encoding. The module's own doc admits "policy bits... out of the first slice". OOM therefore returns None up the stack rather than reclaiming.

### Problems
- **[HIGH/swap/effort:xl]** Swap is a non-functional stub: no eviction, no swap-in, no reclaim — swapon succeeds but never frees a single page
    - evidence: kernel/src/memory/swap.rs:1-290 implements only a slot registry. write_page (202), read_page (217), allocate_slot (167), free_slot (187) have ZERO callers anywhere (grep across kernel/src confirms only swap.rs references them). There is no page-out path, no victim selection (no clock/second-chance/LRU), no swap-entry PTE encoding, no swap-in on fault: the #PF handler (kernel/src/arch/x86/idt.rs:1837-1861) only handles not-present demand paging for heap/mmap/DLL and never consults swap. OOM paths (heap.rs:732 grow_heap returns false; virtual_mem.rs:1848/1911 alloc_frame returns None) simply fail allocation. docs/syscalls.md:252-258 documents swapon/swapoff as 'mechanism-only'. So the whole feature is inert: enabling swap cannot relieve memory pressure.
    - impact: Problem #6 directly: there is effectively no swap. Under memory pressure the kernel cannot page out; large workloads (apt/LXE, Surf, browsers) hit hard OOM and allocation-failure cascades instead of degrading gracefully.
    - fix: Build the policy half: (1) add a swap-entry PTE encoding (use a non-present PTE with a software bit + SwapSlot packed in bits 12-62, distinct from PTE_GUARD bit 10 / PTE_VRAM bit 9). (2) Add a reclaim entry point reclaim_pages(n) that walks reverse-mapping or per-process VMAs, selects victims via an accessed-bit (PTE bit 5) clock sweep, calls swap::allocate_slot()+write_page(), then rewrites the PTE to the swap entry and frees the frame. (3) In the #PF not-present handler, detect a swap-entry PTE, allocate_slot's reverse → read_page() into a fresh frame, restore the PTE. (4) Trigger reclaim from grow_heap and alloc_frame_with OOM, and optionally a low-watermark kthread. Without these, swap.rs should be marked experimental in docs and the syscalls return ENOSYS to avoid implying functionality.
- **[HIGH/performance/effort:xl]** No copy-on-write for fork: every fork eagerly copies the entire address space
    - evidence: kernel/src/memory/virtual_mem.rs:1207-1466 clone_user_page_directory_inner walks every user PTE and, for every non-shared page, does physical::alloc_frame_with + map two temp pages + copy_nonoverlapping(4096) + map_page_in_pd (lines 1395-1460). DLL RO pages are shared (1336) but all writable/anonymous/stack/heap pages are physically duplicated immediately. There is no CoW marking anywhere (grep for cow/copy-on-write finds only filesystem overlayfs, not VM). A fork of a process with a 200 MiB heap copies 200 MiB synchronously with IF toggling per page.
    - impact: Problem #9 (perf) and #4 (LXE): fork()+exec() is the hot path for every shell command and every Linux process spawn. Eager copy makes fork O(resident size) and multiplies peak memory, worsening the OOM problem from the swap gap.
    - fix: Implement CoW: in clone, map both parent and child PTEs read-only with a software COW bit and bump a per-frame refcount (a refcount array parallel to buddy's order_of_alloc, or a small hash). On write #PF (err_code bit1=1) to a COW page, allocate a fresh frame, copy once, drop the parent refcount, and restore writability. This also fixes the elaborate 'quarantine live parent frames' hack (1394-1428) which exists only because eager copy races the allocator.
- **[MEDIUM/file-length/effort:large]** virtual_mem.rs (1996 lines) duplicates the 4-level page-table walk in clone and destroy with hand-inlined recursive-address arithmetic
    - evidence: kernel/src/memory/virtual_mem.rs:1262-1342 (clone walker) and 1695-1786 (destroy walker) are near-identical 4-deep nested loops recomputing sign_extend(RECURSIVE_INDEX<<39|...) by hand at each level, with subtly different skip rules (is_identity_map vs is_kernel_low_identity_pde, is_dll). The recursive-address math is also separately duplicated in is_mapped_in_pd (1587-1597), set_page_flags_in_pd (1627-1638), and the debug_recursive_* helpers (232-257).
    - impact: Problem #1 and #2: this is the single largest, most-duplicated kernel file and the divergence between the clone and destroy skip-logic is a real correctness hazard (a page treated as private by destroy but shared by clone, or vice-versa, double-frees or leaks).
    - fix: Extract a single `unsafe fn for_each_user_pte(pml4_range, |vaddr, pte_ptr, level_info|)` iterator over the recursive map and drive clone/destroy/flag-update through it. Move the recursive-base computation into one PageWalk type. Then split the file per the key_files suggestion. This removes ~600 duplicated lines and the risk that clone and destroy disagree about which PTEs are 'identity/DLL/shared'.
- **[HIGH/stability/effort:medium]** heap.rs grow_heap_exact advances the committed watermark BEFORE mapping the backing pages and can leave a partially-mapped, already-committed window on OOM
    - evidence: kernel/src/memory/heap.rs:751-789: grow_heap_exact stores the new HEAP_COMMITTED watermark (755, Release) first, then loops mapping frames (776-788). If physical::alloc_frame_with returns None mid-loop it `return false` (782) but the watermark has already advanced — HEAP_COMMITTED now claims pages [old, new) are valid heap, yet some are unmapped with no PTE. is_in_heap() (641) then reports those addresses as in-heap, and the new FreeBlock at `base` (792) is written into the (still-mapped) first page, but the demand-paging handler handle_heap_demand_page (virtual_mem.rs:1806) will try to back the unmapped tail later — which is fine only if frames are available. Worse, the free block size is set to the full `growth` (793) regardless of how many pages actually mapped, so alloc_inner can hand out a block spanning unmapped pages → write fault on a committed address with the allocator believing it is backed.
    - impact: Problem #3: under true OOM during heap growth this produces an inconsistency between HEAP_COMMITTED and the page tables, turning a recoverable allocation failure into a later #PF on a 'valid' heap address (potential triple fault since the handler also can't get a frame).
    - fix: Map all frames first into a scratch list; only on full success advance HEAP_COMMITTED and publish the FreeBlock. On partial failure, free the frames already allocated and return false with the watermark unchanged. Alternatively, size the published FreeBlock to the number of pages actually mapped and roll the watermark back to old+mapped_bytes.
- **[MEDIUM/stability/effort:small]** OOM during virtual_mem::init / heap::init panics the kernel via .expect() instead of failing gracefully
    - evidence: kernel/src/memory/virtual_mem.rs:285,306,312,317,338,343,358,406,409,412 all use .expect("OOM ...") on physical::alloc_frame during paging setup; heap.rs:1038 .expect("Failed to allocate heap frame"). These are boot-time and arguably acceptable, but vma.rs:315 `cursor = &mut cursor.as_mut().expect("cursor vanished").next` runs on the live sys_mmap path: if the list shape is ever inconsistent (e.g. after a slab-cache corruption), a user mmap call panics the whole kernel rather than failing the syscall.
    - impact: Problem #3: a single corrupted VMA node turns a per-process fault into a system-wide halt.
    - fix: Boot-path expects are tolerable but should at least call a structured panic that renders the RSOD. The vma.rs:315 expect on the live mmap path must be replaced with a graceful break/return false so a corrupt VMA list fails the mmap with ENOMEM instead of taking down the kernel.
- **[MEDIUM/performance/effort:medium]** Heap per-CPU caches/buckets are not drained on CPU offline and an allocation can migrate cores between the bucket-empty check and the slow path
    - evidence: heap.rs:528-562: alloc disables interrupts, reads cpu_id (530), tries bucket_alloc/percpu_alloc, then on miss RE-ENABLES interrupts (restore_interrupt_state at 548) before taking the global lock (555). A timer preemption + migration between 548 and 555 is possible; the slow path then allocates a class-sized block but on dealloc a DIFFERENT cpu_id may be observed, routing the freed block to another CPU's bucket. This is memory-safe (counters are per-CPU atomics and IF=0 guards each section) but causes unbounded bucket residency skew: per CLAUDE.md the design assumes ~2 MiB/CPU; a migrating workload can pin freed blocks on idle CPUs while a busy CPU keeps hitting the global lock. There is also no path to flush a CPU's PERCPU_BUCKETS/PERCPU_CACHES when a core is parked, so on a 16-CPU cap (PERCPU_MAX_CPUS) those bytes are stranded (counted as 'cached free' in heap_stats:941 but never returned to the global list except via the 256 KiB overflow flush).
    - impact: Problem #9 (alloc perf) and #3: explains the historical '73 KiB alloc panicked after 10h uptime' note (heap.rs:96) — fragmentation/stranding under long uptime. Stranded per-CPU cache can make grow_heap fail (and thus OOM) while tens of MiB sit idle in other CPUs' buckets.
    - fix: Add a periodic/explicit drain_percpu_caches(cpu) called on CPU park and from a low-memory hook that flushes both buckets and the overflow cache back to the global list under the heap lock. Consider capping total cached bytes globally (not just per-class) and flushing the largest classes first when global free drops below grow threshold, so cached-but-stranded memory can satisfy a large request before grow_heap fails.
- **[MEDIUM/architecture/effort:large]** Buddy/bootmem hard-cap physical memory at 16 GiB in static BSS; >16 GiB RAM is silently dropped
    - evidence: buddy.rs:84-86 MAX_MEMORY=16 GiB, MAX_FRAMES, BITMAP_BYTES are const; the zone carries [u8;MAX_FRAMES] order_of_alloc + two [u8;MAX_FRAMES/8] bitmaps = ~20 MiB BSS PER ZONE, ~40 MiB for two zones (acknowledged buddy.rs:74-83 and virtual_mem.rs:346-356). physical.rs:114-116 STAGE1 also caps at 16 GiB and init() truncates max_usable_addr to STAGE1_MAX_MEMORY (197-199). physmap caps at 64 GiB (physmap.rs:80) — inconsistent with the 16 GiB frame cap. RAM above 16 GiB is never registered as free.
    - impact: Problem #2/#9: 40 MiB of always-resident BSS for the order/bitmap arrays even on a 512 MiB VM, and a silent ceiling that makes the OS unusable on >16 GiB hosts.
    - fix: Per the referenced todos/buddy-no-cap.md plan, move order_of_alloc and the bitmaps off static BSS into bootmem-allocated arrays sized from the actual E820/DTB extents at late_init. At minimum, unify the caps (buddy MAX_MEMORY, STAGE1_MAX_MEMORY, MAX_PHYSMAP_BYTES) to one constant and log a warning when RAM is truncated so the drop is visible instead of silent.
- **[LOW/performance/effort:medium]** VMA registry is a global Spinlock<Vec> scanned linearly by PD on every mmap/munmap/fault, and leaks entries if init_process is not matched by destroy_process
    - evidence: vma.rs:60 VMA_REGISTRY is one global Spinlock<Vec<ProcessVmas>>; every alloc_region/free_region/contains_addr does reg.iter().find(|p| p.pd==pd) (e.g. 140, 204, 295) — O(processes) under a single global lock, and contains_addr is called from the page-fault demand path (virtual_mem.rs:1890) so a fault in any process serializes on the same lock as every mmap. The comment (57-59) assumes '<20 processes'. destroy_process (271) is the only cleanup; it is called from many loader/fork error paths (confirmed) but a code path that init_process()es a PD and then fails before registering destroy leaks a ProcessVmas (and its slab-backed node chain) forever, since nothing reconciles the registry against live PDs.
    - impact: Problem #9: under many processes, every page fault and mmap contends one global lock and scans a Vec. Low severity today only because process counts are small.
    - fix: For scale, switch to a per-process pointer (store the VMA list head in the thread/process struct keyed by PD) so lookups are O(1) and the lock is per-process, not global — this also removes the demand-fault contention. Add a debug assertion/audit that every registry PD corresponds to a live page directory, and ensure destroy_process is unconditionally called from the deferred PD-destroy drain (it is wired at scheduler/mod.rs:1985 and deferred.rs:55, but the early loader error paths should be re-audited).
- **[LOW/performance/effort:medium]** create_user_page_directory uses fixed kernel temp VAs (0xBFF0_0000..) serialized by a single global lock — fork/exec storms serialize address-space creation
    - evidence: virtual_mem.rs:1090-1108 temp_pml4/pdpt/pd are fixed VAs guarded by one global CREATE_USER_PD_LOCK; clone uses per-CPU temp VAs (1191-1241, MAX_CLONE_CPUS=8) but the PD *creation* still funnels through the single CREATE_USER_PD_LOCK because clone calls create_user_page_directory_inner first (1227). zero_frame (612) similarly serializes all frame-zeroing on one ZERO_FRAME_LOCK + one fixed temp VA (0xBFF1_0000).
    - impact: Problem #9 and #4: every process spawn / Linux exec creates a PD under one global lock plus per-frame zeroing under another; on SMP this is a measurable spawn-latency bottleneck and a deadlock-surface (the locks nest with PAGE_TABLE_LOCK).
    - fix: Give create_user_page_directory and zero_frame per-CPU temp VAs like clone already does, removing the global serialization. Better: use physmap to write into the freshly allocated PT pages directly (phys_to_virt) instead of mapping/unmapping fixed temp VAs at all — physmap already covers all RAM, so the temp-VA dance and its locks become unnecessary for kernel-side writes.
- **[LOW/stability/effort:small]** physmap omits NX on the direct map (kernel-writable + executable RAM alias)
    - evidence: physmap.rs:99-108 explicitly omits PAGE_NX because EFER.NXE is not yet set at physmap::init time, mapping all RAM at PML4[384] as present+writable+global with NO no-execute. The comment notes the fix requires a two-pass init after NXE goes live. Every RAM page therefore has a W+X kernel alias for the life of the system.
    - impact: Problem #3 (hardening): a kernel write primitive plus this W+X alias is directly exploitable; also any stray jump into physmap executes attacker-controlled data.
    - fix: Split physmap init: install PD entries in init_memory, then after syscall_msr sets EFER.NXE do a second pass ORing PAGE_NX into every physmap PDE (and CR3 reload). This makes the direct map W^X and removes a writable+executable alias of all of physical RAM — a meaningful kernel-hardening / exploit-mitigation gap.
- **[LOW/stability/effort:medium]** handle_user_mmap_demand_page maps any fault inside a registered VMA as a writable+user zero page regardless of the VMA's recorded flags
    - evidence: virtual_mem.rs:1884-1934: on a not-present user fault inside a VMA, it always maps with PAGE_WRITABLE|PAGE_USER (1925) and ignores Vma.flags (vma.rs:28 stores the intended flags, set to 0x02|0x04 = WRITABLE|USER for all regions at alloc_region_in:152). So a read-only or PROT_NONE mmap region, if it ever reaches this repair path, becomes writable. Combined with vma.rs always storing flags=WRITABLE|USER (it never records actual mmap prot), mprotect semantics are not enforced by the demand-paging repair.
    - impact: Problem #3/#4: weakens mmap protection guarantees; a PROT_READ mapping can silently become writable via the repair path, and Linux programs relying on mprotect/PROT_NONE guard pages get wrong behavior.
    - fix: Store the real prot/flags in the Vma (thread mmap prot through alloc_region) and have handle_user_mmap_demand_page map with exactly those flags (translating PROT_NONE to a refusal). At minimum, only repair regions whose recorded flags permit the faulting access type (err_code bit1 = write).
- **[LOW/stability/effort:medium]** Double-free guard in dealloc_inner only checks the head-side scan, not the coalesced neighbor, and bucket_dealloc has no double-free detection at all
    - evidence: heap.rs:885-888 dealloc_inner skips the free 'if current==block' but only while walking until current>=block — a block already coalesced into a PRECEDING free block (so it is no longer its own list node) is not detected and gets re-inserted, splitting a coalesced region. The fast bucket path bucket_dealloc (224-238) does ZERO validation: a double-free of a bucket-sized object pushes the same address onto the bucket twice → the next two bucket_allocs hand out the same pointer (use-after-free). The bucket_alloc corruption checks (188-220) only validate that links point inside the heap, not that an address appears once.
    - impact: Problem #3: a double-free of any <=128 KiB allocation (the common case) is silently turned into aliasing rather than caught — exactly the class of bug that produces the intermittent 'RIP inside LockedHeap::alloc, CR2=0xFFFFFFFF' crash the code comments already reference (heap.rs:184-187).
    - fix: Add a cheap double-free guard to the bucket path: before pushing, optionally poison freed blocks (write a magic + scan a few) or maintain a small per-bucket recently-freed ring to catch immediate double-frees. Document that the bucket path trades safety for speed and ensure callers can't double-free (the current 'is_in_heap then leak' guard at dealloc:579 does not catch in-range double-frees).

### Refactor opportunities
- Extract a single for_each_user_pte() recursive-map iterator and route clone/destroy/flag-update/is_mapped through it (removes ~600 duplicated lines in virtual_mem.rs and the clone/destroy skip-logic divergence).
- Extract one coalesce_into_sorted_list() helper; it is copy-pasted in heap.rs percpu_flush_half, grow_heap_exact, and dealloc_inner with subtly different cycle guards.
- Replace fixed kernel temp-VA + global-lock page-table writes (create_user_page_directory, zero_frame, map_page_in_pd) with direct physmap writes, eliminating CREATE_USER_PD_LOCK / ZERO_FRAME_LOCK serialization.
- Move VMA list head into the per-process structure (O(1), per-process lock) instead of one global Spinlock<Vec> scanned linearly on every mmap and page fault.
- Unify the 16 GiB/64 GiB physical-memory caps (buddy MAX_MEMORY, STAGE1_MAX_MEMORY, physmap MAX_PHYSMAP_BYTES) into one constant and move buddy's order/bitmap arrays off static BSS to runtime-sized allocations (todos/buddy-no-cap.md).
- Split virtual_mem.rs (1996) and heap.rs (1075) per the key_files split suggestions to satisfy problem #1.

### Test gaps
A kunit harness exists (kernel/src/kunit/) with real coverage: memory_tests.rs (heap stats/validate, physical alloc/free roundtrip, slab reuse), buddy_tests.rs (order_for, split/merge chains, alloc_contiguous, alloc-until-OOM with audit() after each op), vma_tests.rs (init/alloc/free/clone/destroy, gap-find), and physmap_tests.rs. These run headless in the live kernel and report over serial — the right pattern.

Gaps, each coverable headlessly: (1) SWAP has NO tests at all — add swap_tests.rs that creates a small ramfs swap file, swapon, allocate_slot/write_page/read_page round-trip (verify bytes survive), free_slot, swapoff-busy rejection, double-swapon rejection, NoSpace exhaustion. This would have immediately flagged that the I/O functions are never exercised. (2) No eviction/swap-in test because no eviction exists — once implemented, a test should mmap+touch enough anonymous pages to force reclaim, then re-read and assert contents (proves page-out+page-in round-trips through swap). (3) heap grow_heap OOM-rollback: a test that drives the buddy near-empty (alloc_until_oom already does this for buddy; add a heap-growth-under-low-frames test) and asserts HEAP_COMMITTED stays consistent with mappings and that a subsequent in-range access does not fault. (4) Double-free detection: a test that frees a bucket-sized allocation, frees it again, then allocs twice and asserts the two pointers differ (currently would FAIL, documenting the bug). (5) CoW: once implemented, a fork test asserting parent and child share frames until write, then diverge — testable via map_page_in_pd/virt_to_phys in a synthetic two-PD scenario without spawning userspace. (6) reclaim_empty_user_tables: a mmap/munmap cycle test asserting page-table frame count returns to baseline (the '96 leaked pages after 192 MiB' regression referenced in virtual_mem.rs:692 has no automated guard). (7) handle_user_mmap_demand_page flag enforcement: a test mapping a read-only VMA and asserting the repair path does not grant write — currently would FAIL.

### Open questions
Is there any consumer expected to call swap::write_page/read_page that simply was never wired (e.g. a planned kswapd kthread), or was the policy half intentionally deferred indefinitely? The module doc says 'first slice' implying staged work. Second: does the project intend CoW fork at all, or is eager-copy a deliberate simplicity choice given the no-swap design? The 'quarantine live parent frames' hack suggests recurring fork-aliasing pain that CoW would eliminate. Third: confirm whether handle_user_mmap_demand_page is reachable in normal operation (it is described as a 'conservative repair' for cross-CPU races) — if it fires routinely, its flag-ignoring behavior is a live correctness bug; if it is truly rare, severity stays low.

## SCHEDULER — Scheduler &amp; Task subsystem (kernel/src/task/, kernel/src/task/scheduler/)

**Architecture:** anyOS uses a Mach-style preemptive scheduler with 128 priority levels. The run queue (kernel/src/task/scheduler/run_queue.rs) is a genuinely O(1) bitmap-indexed multi-level FIFO: a 2×u64 bitmap tracks non-empty priority levels and `leading_zeros` finds the highest. Each CPU has its own RunQueue inside `PerCpuState`, and idle CPUs steal work from the busiest peer in `pick_next` (mod.rs:1314). This data-structure layer is well-designed and the per-priority selection is not a bottleneck.

The fatal architectural flaw is that ALL per-CPU run queues, the entire thread list (`Vec<ThreadBox>`), and every per-thread field live behind ONE global `SCHEDULER: Spinlock<Option<Scheduler>>` (mod.rs:132). The "per-CPU run queues" are only logically per-CPU; physically every enqueue/dequeue/wake/accessor serializes through this single lock. The lock is IRQ-disabling and non-recursive (sync/spinlock.rs). Lock-free per-CPU atomic mirrors (PER_CPU_CURRENT_TID/IS_USER/THREAD_NAME/ABI/LINUX_ROOTFS) exist to keep the very hottest reads off the lock, but the two most important ones — `current_thread_abi` and `current_thread_linux_rootfs` — were reverted to lock-based because the cache could go stale (thread_config.rs:80-98, 125-142). The result: every x86_64 syscall and every Linux path syscall takes the global lock.

Thread lifecycle is spread across lifecycle.rs (exit/kill/fault recovery + cascade-kill), wait.rs (waitpid/sleep — using polling loops, not pure wakeups), signals.rs, spawn.rs, fork.rs, and deferred.rs (deferred PD-destroy and fault-cleanup queues to keep heavy teardown out of the lock). Context switch is hand-written asm (asm/x86/context_switch.asm) with a canary + XOR checksum + RSP/RIP range validation on every switch — defensive but adds ~40 memory ops per switch. There is heavy reliance on `save_complete` flags, "pinned kernel continuation" heuristics, and three separate fault-recovery entry points (try_exit_current, bad_rsp_recovery, fault_kill_tid_and_idle) that each duplicate ~80 lines of teardown — strong evidence of accreted stability patches rather than a clean design.

mod.rs is a 2786-line god-module mixing: global statics, per-CPU caches, the Scheduler core, schedule_inner (600+ lines), two architecture variants of the timer entry, FPU lazy-switch, reaper, maintenance, AND 7 inline kunit tests.

### Key files

### Problems
- **[CRITICAL/performance/effort:medium]** Every x86_64 syscall takes the global SCHEDULER lock just to read the ABI personality
    - evidence: syscall/mod.rs:701 `let abi = crate::task::scheduler::current_thread_abi();` runs on EVERY x86_64 syscall, and its comment (line 697) falsely claims it is a 'lock-free per-CPU read'. The actual impl in scheduler/thread_config.rs:89-98 does `let guard = SCHEDULER.lock();`. The lock-free PER_CPU_CURRENT_ABI cache exists (mod.rs:205, load_per_cpu_abi at mod.rs:523) but was deliberately reverted (thread_config.rs:80-88) because it goes stale on the idle-on-exit transition that skips update_per_cpu_name.
    - impact: Serializes the entire syscall path of every process through one IRQ-disabling spinlock. Under multi-core load or syscall-heavy workloads (LXE ld.so, compositor, network servers) this is the dominant scheduler/IO performance ceiling and a freeze amplifier (problems #9, #3, #4). On contention the spinlock can stall 100-400ms (sync/spinlock.rs:18 SPIN_TIMEOUT).
    - fix: Make the lock-free cache trustworthy by validating it against PER_CPU_CURRENT_TID: store (tid, abi) atomically (pack into one AtomicU64) and have load_per_cpu_abi compare the cached TID against PER_CPU_CURRENT_TID before trusting it; fall back to the lock only on mismatch. Ensure EVERY thread-on-CPU transition (including the idle-on-exit path in lifecycle.rs prepare_idle_recovery_context / enter_idle_recovery) updates the cache. Add a kunit test asserting the cache matches the locked read after each switch/exit path.
- **[HIGH/performance/effort:medium]** Per-IO global lock acquisitions: IO accounting and rootfs lookup serialize read/write/path syscalls
    - evidence: scheduler/diagnostics.rs:190-228 record_io_read/io_write/net_tx/net_rx each do `SCHEDULER.lock()`, called from syscall/handlers/io.rs:53,179,291,338 and net/socket handlers on every successful read/write/send/recv. Separately, scheduler/thread_config.rs:129 current_thread_linux_rootfs takes the lock and is called by syscall/linux/path.rs:367 on every Linux open/stat/access/readlink. So a single Linux read() = lock for ABI + lock for accounting; a Linux open() = lock for ABI + lock for rootfs.
    - impact: 2-3 global IRQ-disabling lock acquisitions per IO/path syscall. Throttles file IO, network throughput, and LXE program startup (ld.so probes ~10 paths/lib). Directly hits problems #9 and #4.
    - fix: Accumulate IO counters in lock-free per-CPU atomics (already the pattern for PER_CPU_*), flush into the Thread struct lazily in schedule_inner or the reaper. Serve the Linux rootfs from the validated lock-free PER_CPU_LINUX_ROOTFS cache (already populated at mod.rs:541) using the same TID-validation fix as the ABI cache.
- **[HIGH/stability/effort:medium]** deferred_wake circular-overwrite can drop a wakeup and corrupts DEFERRED_WAKE_PENDING count
    - evidence: scheduler/mod.rs:352-370. When all 256 slots are occupied, the fallback (lines 368-369) does `DEFERRED_WAKE_TIDS[idx].store(tid)` WITHOUT incrementing DEFERRED_WAKE_PENDING, but the drain loop (mod.rs:2196-2202, 1793-1799) unconditionally `fetch_sub(1)` for every non-zero slot it swaps. This (a) clobbers a previously-stored pending TID that may never have been drained → a genuinely lost wakeup under IRQ storm (the exact failure the 256 slots were sized to prevent), and (b) desyncs DEFERRED_WAKE_PENDING (can underflow via Relaxed fetch_sub), defeating the fast-path skip and potentially wasting a 256-slot scan every tick forever.
    - impact: A thread blocked in tcp::recv / pipe / event wait can be permanently stuck if its wake lands in the overwrite path (manifests as a hung shell/app — problem #3). Counter underflow degrades the tick fast-path.
    - fix: In the full-slots fallback, only overwrite a slot whose current value the drain will still account for, and keep PENDING consistent (e.g. when overwriting a non-zero slot, do not change PENDING; when overwriting a zero slot, increment). Better: replace the linear-probe array with a proper MPSC ring buffer (head/tail indices) so a full ring blocks the producer or grows, never silently drops. Add a kunit no-lost-wakeup test that floods deferred_wake past capacity and asserts every TID is eventually drained.
- **[MEDIUM/performance/effort:medium]** waitpid / waitpid_any use polling loops with halt() instead of pure event wakeups
    - evidence: scheduler/wait.rs:206-226 (waitpid) and 287-315 (waitpid_any): after blocking and scheduling, the thread loops { lock SCHEDULER; check child terminated; enable_interrupts; halt() }. It re-wakes on ANY interrupt and re-takes the global lock to re-check, rather than staying blocked until exit_current explicitly wakes the exit_waiter_tid (which it does set, at lifecycle.rs:547).
    - impact: A parent in waitpid wakes on every timer tick (1000 Hz) and every device IRQ, each time grabbing the global SCHEDULER lock to re-scan, adding lock traffic proportional to interrupt rate × number of waiting parents (problem #9). The explicit wakeup path already exists, making the poll redundant defensive code.
    - fix: Trust the exit_waiter_tid wakeup: block, schedule, and on resume check the condition exactly once; if not satisfied (spurious wake) re-block rather than spin-halt. Keep a single defensive re-arm but not a per-interrupt poll. Validate with a kunit/headless test counting SCHEDULER lock acquisitions while N parents wait on long-running children.
- **[HIGH/architecture/effort:large]** No priority inheritance / donation — unbounded priority inversion on the global lock and on user mutexes
    - evidence: priority.rs has set_thread_priority but no inheritance mechanism; the scheduler picks strictly by static priority (run_queue.rs highest_priority). A low-priority thread holding SCHEDULER (or any contended kernel lock / futex) can be preempted, while a high-priority thread spins in spinlock.rs:161 burning a core. The spinlock even re-enables interrupts mid-spin (spinlock.rs:217) specifically to let the (possibly lower-priority) holder run — an ad-hoc workaround for the missing inheritance.
    - impact: On a busy system a critical thread (compositor, marked `critical`) can be starved behind a background thread that holds the global lock, producing the compositor freezes/jank described in problems #3 and #7. Worst case is unbounded with many low-priority CPU hogs.
    - fix: Short term: shrink the global lock's hold time (the two fixes above) so inversion windows are tiny. Medium term: add priority-inheritance to the kernel lock used for futexes and to SCHEDULER (boost the owner_cpu's current thread to the waiter's priority while contended). Add a fairness invariant test: a priority-127 ready thread must be picked within one tick even when a priority-1 thread holds the lock.
- **[MEDIUM/performance/effort:medium]** O(n) linear scans of the thread Vec on common operations instead of the find_idx hash cache
    - evidence: Dozens of hot functions use `sched.threads.iter().find(|t| t.tid == tid)` / `.position(...)` instead of the cached find_idx (mod.rs:754): signals.rs:14,101,277,289,315,358; spawn.rs:55,165,315; priority.rs:85,118,188,216,266,273; fork.rs:87,99,111,123; thread_config.rs:54,108; accessors.rs:240 thread_has_cap. collect_and_terminate_children (lifecycle.rs:186-201) is O(children × threads) BFS, and terminate_same_pd_threads_for_fault / has_live_siblings scan all threads. find_idx itself falls back to O(n) and the whole TID cache is wiped (invalidate_tid_cache, mod.rs:794) on every reap swap_remove.
    - impact: With many threads (LXE multi-threaded apps, fork storms) these scans run under the global lock, lengthening hold time and feeding the inversion/contention problems above. The full TID-cache invalidation on every reap makes find_idx O(n) right after each reap.
    - fix: Route all by-TID lookups through find_idx. Replace full-cache invalidation on swap_remove with a targeted fixup (only the moved entry's slot changes — its index is known). Consider a real HashMap<u32,usize> keyed by TID maintained incrementally. Cap cascade-kill BFS cost by indexing children by parent_tid.
- **[MEDIUM/architecture/effort:medium]** Three duplicated fault-recovery paths with ~80 lines of copy-pasted teardown each
    - evidence: lifecycle.rs: try_exit_current (604-729), bad_rsp_recovery (738-828), and fault_kill_tid_and_idle (839-922) each repeat: find thread, terminate_same_pd_threads_for_fault, has_live_siblings check, mark Terminated + clear page_directory/exit_waiter/parent, switch to kernel_cr3, defer_fault_exit_cleanup, defer_fault_pd_destroy, enter_idle_recovery. exit_current and kill_thread duplicate yet another variant. Subtle divergence between copies is exactly how stability regressions (problem #3) creep in.
    - impact: High maintenance risk: a fix applied to one recovery path silently misses the others. The paths already differ (e.g. critical-thread sparing only in bad_rsp_recovery) in ways that are hard to audit.
    - fix: Factor a single `fn terminate_thread_and_address_space(sched, idx, code, tick) -> (cleanup_tids, pd_to_destroy)` used by all five callers, and a single `fn finish_fault_recovery(cpu, tid, code, abi, cleanup, pd)`. The recovery entry points then only differ in how they acquire the lock and which thread they target.
- **[MEDIUM/stability/effort:small]** ensure_idle_thread can allocate a 2 MiB stack while holding SCHEDULER, violating the documented lock rule
    - evidence: schedule_inner calls sched.ensure_idle_thread(cpu_id) under the lock (mod.rs:2211, and again in schedule_tick_from_user_irq:1807). On the recovery branch (mod.rs:885) ensure_idle_thread calls Thread::new → PageAlignedStack::alloc → alloc_zeroed(2 MiB+4K) which acquires HEAP_ALLOCATOR — directly contradicting the module header rule 'NEVER allocate while holding SCHEDULER ... the spin can take 100+ ms' (mod.rs:21-22).
    - impact: Rare (only when an idle thread is found missing/corrupt) but when hit during contention it can stall the scheduler hot path 100+ms or deadlock if HEAP_ALLOCATOR is held by a thread waiting on SCHEDULER. Because it is in the recovery path it triggers precisely when the system is already unstable.
    - fix: Pre-allocate all per-CPU idle thread stacks once at boot/AP-bring-up (register_ap_idle already exists) and make the schedule_inner path assert-and-park rather than allocate. If lazy creation must stay, allocate the ThreadBox outside the lock (as spawn() does) and only insert under the lock.
- **[MEDIUM/performance/effort:large]** Per-thread 2 MiB kernel stacks from the kernel heap — heavy memory pressure with many threads
    - evidence: thread.rs:277 KERNEL_STACK_SIZE = 2 MiB per thread, allocated via alloc_zeroed from the kernel heap (thread.rs:44-64, over-allocates +4K for page alignment). Thread also embeds name[32]+args[256]+cwd[512]+linux_rootfs[512]+fpu_state[832]+fd_table+signals inline, so the slab object itself is multi-KB. Reaper holds zombies up to 1000-5000 ms (mod.rs:1233-1248) keeping those 2 MiB stacks live long after exit.
    - impact: 100 threads = ~200 MiB of kernel stacks alone, plus long zombie retention. LXE multi-threaded apps and fork storms can exhaust the kernel heap, and zeroing 2 MiB per spawn is a measurable spawn-latency cost (problem #9, and contributes to LXE instability #4).
    - fix: Reduce default kernel stack (most threads never approach 2 MiB; size by role, e.g. 64-256 KiB with a guard page, reserve 2 MiB only for the compositor/VFS-deep threads), or demand-map stack pages so only touched pages consume RAM. Shorten zombie retention for detached/orphan threads (already partially done) and reclaim the stack immediately on reap rather than after the grace delay where safe.
- **[LOW/stability/effort:large]** Timer-path try_lock failure silently skips deferred-wake and sleeper-deadline draining for that tick
    - evidence: schedule_inner timer path (mod.rs:2130-2143) and schedule_tick_from_user_irq (mod.rs:1761-1772) use SCHEDULER.try_lock() and return immediately on contention, counting the tick as contended-busy but NOT draining DEFERRED_WAKE_TIDS or calling wake_expired_sleepers. Draining only happens once the lock is finally acquired by some path.
    - impact: Under sustained cross-CPU lock contention, timed sleepers and deferred wakeups experience latency spikes (delayed by however long the lock stays contended). Combined with the deferred_wake count bug above, this can extend a missed-wake window. Bounded in practice because the voluntary path also drains, but it adds jitter to timers/sleeps (problem #3 freezes-feel, #9 latency).
    - fix: This is inherent to one global lock; the real fix is reducing lock hold time (problems above). As a stopgap, let the IRQ path drain the lock-free DEFERRED_WAKE ring into per-CPU local queues without the global lock, and process sleeper deadlines via a lock-free min-heap of next-deadlines so timer wakeups don't depend on winning the global lock.
- **[LOW/stability/effort:small]** DEFERRED_WAKE_PENDING uses Relaxed ordering with no overflow/underflow guard
    - evidence: mod.rs:333 DEFERRED_WAKE_PENDING; increment at 359 (Relaxed fetch_add), decrement at 2199/1796 (Relaxed fetch_sub). No saturation. Combined with the overwrite path not incrementing (problem above), the counter can drift; a Relaxed fetch_sub past zero wraps to ~u32::MAX, making the `> 0` fast-path check always true.
    - impact: Defeats the intended optimization (skip 256-slot scan when empty), so every tick scans all 256 slots under the lock — small but constant added hold time. Low severity because it only wastes cycles, never corrupts thread state.
    - fix: Make the count saturating and only adjust it in lockstep with actual slot 0→tid and tid→0 transitions inside the drain (count = number of slots actually swapped this drain), or derive 'pending' purely by OR-reducing the slots once with SIMD-free word scan. Add a debug assert that PENDING never exceeds DEFERRED_WAKE_SLOTS.
- **[LOW/performance/effort:medium]** least_loaded_cpu and rebalance use O(MAX_CPUS) + O(n threads) scans under the lock; work-stealing scans all CPUs every pick
    - evidence: add_thread → least_loaded_cpu (mod.rs:1100-1121) scans all CPUs on every spawn; rebalance_affinity_once (mod.rs:990-1058) does two full O(n) thread-list passes; pick_next work-stealing (mod.rs:1325-1336) scans all CPUs' total_count on every miss. All under the global lock.
    - impact: Minor on small core counts but compounds the global-lock hold time on busy systems and during fork storms. Not the primary bottleneck (the per-syscall ABI/IO locks are), but it lengthens the same critical section.
    - fix: Cache per-CPU run-queue lengths in atomics so least_loaded_cpu and work-stealing victim selection are lock-free reads. Make rebalance incremental rather than full-scan. Lower priority than the per-syscall lock fixes.

- Introduce a typed PerCpuCache abstraction that packs (tid, value) atomically and validates against PER_CPU_CURRENT_TID, then build current_thread_abi/linux_rootfs/uid/gid/capabilities on it — this is the keystone refactor that removes the global lock from the syscall hot path and unblocks problems #9 and #4.
- Replace the 64×ForkPendingSlot::empty() hand-expanded array (loader.rs:432-497) and similar with const-fn array initializers.

### Test gaps
Only 7 kunit functions exist (mod.rs:1471-1636), covering pinned-continuation pinning, run-queue dedup invariants, save_complete gating, and reaper stack-reference safety — good but narrow. UNTESTED and headless/kunit-testable invariants: (1) No-lost-wakeup: flood deferred_wake() past 256 slots and assert every distinct TID is eventually moved Blocked→Ready (would have caught the overwrite/PENDING bug). (2) DEFERRED_WAKE_PENDING never underflows and equals the true non-zero slot count after each drain. (3) Scheduler fairness: with a priority-127 Ready thread enqueued, pick_next must return it before any lower-priority thread, even across work-stealing. (4) ABI/rootfs cache coherence: after every thread-on-CPU transition path (normal switch, idle-on-exit in lifecycle.rs, try_exit_current, bad_rsp_recovery) the lock-free PER_CPU_CURRENT_ABI/LINUX_ROOTFS must equal the locked read for the current TID — this is the exact staleness that forced the lock-based revert and is the highest-value test to add before re-enabling the lock-free fast path. (5) Cascade-kill correctness: build a 3-level parent→child→grandchild tree and assert exit_current/kill_thread mark every descendant Terminated exactly once and free the shared PD only when the last live thread dies. (6) waitpid wakeup-not-poll: count SCHEDULER lock acquisitions while a parent waits on a long sleeper child and assert it does not scale with timer-tick count. (7) Round-trip context_switch save/restore preserves RSP (the asm saves RSP+8; a kunit could save into a CpuContext, validate canary/checksum, and confirm the documented offsets match context.rs). Most of these are pure data-structure tests runnable under the existing `kunit` feature without real CPUs; (4) and (6) are best exercised via the headless serial harness since they involve real context switches.

### Open questions
1) The lock-free ABI/rootfs cache was reverted specifically because the idle-on-exit transition in lifecycle.rs does not call update_per_cpu_name — is there any other transition (AP bring-up, fork_return_to_user, signal trampoline return) that also bypasses the cache update? A full audit of every site that sets PER_CPU_CURRENT_TID vs. every site that calls update_per_cpu_name is needed before re-enabling the fast path. 2) Does any caller of record_io_*/adjust_current_user_pages ever hold VFS or ALLOCATOR when calling (which would invert the documented lock hierarchy)? io.rs calls them after the VFS call returns, but net/socket paths were not fully traced. 3) Is the SCHEDULER spinlock's mid-spin STI window (spinlock.rs:217) ever entered while the caller is on an interrupt stack that the scheduler could migrate — i.e., can re-enabling interrupts during a contended SCHEDULER.lock() spin in a non-IRQ but non-preemptible context cause the same stack-sharing corruption the schedule_inner comment (mod.rs:2104-2113) warns about? 4) What is the measured worst-case SCHEDULER lock hold time today (the maintenance audit scans the whole thread list under the lock at mod.rs:2022) — is the 100-400ms SPIN TIMEOUT ever actually hit in normal multi-core operation?

## SYSCALL — Native syscall layer + Windows (WXE) execution environment

**Architecture:** The syscall layer has two entry asm stubs under kernel/asm/x86/: syscall_fast.asm (SYSCALL/SYSRET → IRETQ) is the only live user entry; the legacy INT 0x80 path was removed (the CLAUDE.md-referenced kernel/asm/x86/syscall_entry.asm does NOT exist). Both syscall_fast.asm and the IRQ/ISR epilogues in interrupts.asm correctly restore DS/ES=0x23 and swapgs before IRETQ when returning to ring 3, and correctly skip the fixup on kernel-to-kernel returns (CS.RPL check). The DS/ES restoration rule from CLAUDE.md is observed in the asm; syscall_fast.asm also has substantial defensive recovery (PERCPU repair via LAPIC_TO_PERCPU, bad-kernel-RSP fallback returning -EAGAIN). This part is solid.

Dispatch lives in kernel/src/syscall/mod.rs::syscall_dispatch_64 (entry) → dispatch_inner (giant ~470-line match over ~180 native syscall numbers). There are THREE parallel ABIs sharing the one SYSCALL entry: native (dispatch_inner), Linux (linux::dispatch, ~lines 317+, its own giant match), and Windows (windows::dispatch). The ABI is selected per-thread via current_thread_abi(). Handlers are split into kernel/src/syscall/handlers/{io,process,system,net,display,disk,...}.rs by category, which is a reasonable decomposition, but display.rs (2156) is far too long and each arch gets a fully duplicated #[cfg] copy of nearly every handler. User-pointer validation is the central architectural weakness: helpers.rs provides a TOCTOU-safe is_user_range_accessible (validates every crossed page mapping) plus copy_user_bytes/copy_to_user_bytes, but only 3 of 15 handler files use it. Most handlers use only is_valid_user_ptr (a pure range check that does NOT confirm pages are mapped) or no check at all, then deref raw *mut/*const pointers (79 from_raw_parts, 98 raw *mut casts across handlers).

WXE (Windows) is implemented as a PE loader (task/loader/windows.rs, 1485 lines) plus an NT/CRT service dispatcher (syscall/windows/mod.rs 1277 + crt.rs 719). WXE state is a single global Spinlock<Vec<WxeProcessState>> keyed by page-directory phys addr. The PE loader is carefully bounds-checked (checked_add everywhere, rva_to_file_offset validation, image-range validation), and the WXE service layer correctly uses copy_user_bytes / is_user_range_accessible for most reads/writes — it is actually MORE disciplined about user pointers than the native handlers. WXE GS-base (TEB) is plumbed through set_thread_windows_gs_base and restored into KERNEL_GS_BASE on every context switch (scheduler/mod.rs:2651) and on ring-3 entry (loader.rs:1619).

### Problems
- **[CRITICAL/stability/effort:small]** sys_time / sys_set_time deref user pointer with only a NULL check — arbitrary kernel read/write
    - evidence: kernel/src/syscall/handlers/system.rs:20-32 (sys_time) writes 8 bytes via `let buf = buf_ptr as *mut u8; *buf = ...; *buf.add(7)=0;` guarded only by `if buf_ptr != 0`. system.rs:40-53 (sys_set_time) reads via `buf_ptr as *const u8` after only `if buf_ptr == 0 { return MAX }`. Neither calls is_valid_user_ptr nor is_user_range_accessible. There is NO upper-bound/kernel-half check. A user process passing buf_ptr=0xFFFFFFFF80000000 makes the kernel WRITE 8 attacker-influenced bytes into kernel memory (sys_time) or treat kernel memory as date input (sys_set_time). Both run on CPL0 with kernel CR3-equivalent access to the higher half.
    - impact: Local privilege escalation / kernel memory corruption from any unprivileged process; also a trivial kernel #PF→panic DoS by passing an unmapped in-range address.
    - fix: Gate every dereference with copy_to_user_bytes/copy_user_bytes (which call is_user_range_accessible). For sys_time write the 8-byte buffer via copy_to_user_bytes(buf_ptr,&out,8); for sys_set_time read via copy_user_bytes(buf_ptr,8,8). Audit ALL handlers that only check `ptr != 0`.
- **[CRITICAL/stability/effort:medium]** sys_net_config (and many handlers) use raw copy_nonoverlapping through user pointers with no range/mapping validation
    - evidence: kernel/src/syscall/handlers/net.rs:30-39 cmd=0 does `core::ptr::copy_nonoverlapping(cfg.ip.0.as_ptr(), buf, 4)` etc into `buf_ptr as *mut u8` after only `if buf_ptr == 0`. cmd=1 (net.rs:46-61) reads 16 bytes from `buf_ptr as *const u8` with only a NULL check. cmd=7 (net.rs:107) builds a 8*128-byte mutable slice from buf_ptr unchecked; cmd=8 (net.rs:116) reads `*(buf_ptr as *const u32)` unchecked. None validate the pointer is in user space or mapped.
    - impact: Same class as sys_time: kernel-mode arbitrary read/write or #PF panic from unprivileged callers. SYS_NET_CONFIG only requires CAP_NETWORK, which most networked apps hold.
    - fix: Replace all raw copy_nonoverlapping/slice derefs in net.rs with copy_user_bytes/copy_to_user_bytes. Add a project lint or grep gate in CI that flags `as *mut`/`from_raw_parts` in handlers/ not preceded by is_user_range_accessible.
- **[HIGH/stability/effort:large]** is_valid_user_ptr is used pervasively but does NOT verify pages are mapped → kernel #PF (TOCTOU) on unmapped in-range user addresses
    - evidence: helpers.rs:53-63 is_valid_user_ptr only checks ptr!=0 and ptr+len <= 0x0000_8000_0000_0000 (range only). The mapping-aware check is is_user_range_accessible (helpers.rs:84-101). Grep shows is_valid_user_ptr is referenced in all 15 handler files, but is_user_range_accessible only in helpers.rs, signal.rs, process.rs. Examples relying on range-only check then raw-deref: display.rs:536 (sys_gpu_command from_raw_parts after is_valid_user_ptr), display.rs:785 (sys_input_poll mut slice), display.rs:1517/1607/1644 (3D submit/dma), system.rs:257/338/374/492/528/548. If userspace passes a valid-range but unmapped address (or unmaps it on another thread between check and use — TOCTOU), the kernel dereferences it and faults in CPL0.
    - impact: Kernel page fault (panic / thread-kill-in-kernel-context) triggerable by any process; on SMP a concurrent munmap makes even is_user_range_accessible racy unless the address space is pinned for the syscall.
    - fix: Standardize on copy_user_bytes/copy_to_user_bytes for all user transfers; for in-place slice access (compositor hot paths) keep is_user_range_accessible but document that SMP munmap races remain. Longer term, add a proper copy-fault handler (exception-table style) so a faulting user access returns -EFAULT instead of panicking.
- **[HIGH/stability/effort:small]** sys_fstat / sys_pipe2 write through user pointer with only a NULL or range check, not mapping-validated
    - evidence: io.rs:553-578 sys_fstat: after `if buf_ptr == 0` it writes `*(buf_ptr as *mut u32)` ... `*buf.add(3)` for the pipe/tty branch AND the file branch (io.rs:607-617) — no is_valid_user_ptr at all. io.rs:719-723 sys_pipe2 writes `*(pipefd_ptr as *mut u32); *ptr.add(1)` guarded only by is_valid_user_ptr(…,8) (range, not mapping). A NULL-check-only fstat with a kernel pointer writes 16 bytes into the kernel half.
    - impact: Kernel write primitive / #PF panic via the very common fstat() and pipe() libc paths.
    - fix: sys_fstat: validate with is_user_range_accessible(buf_ptr,16) (or write via copy_to_user_bytes of a [u32;4]) before any store. sys_pipe2: use copy_to_user_bytes for the [read_fd,write_fd] pair.
- **[HIGH/lxe/effort:medium]** WXE NT/CRT services bypass the capability system entirely
    - evidence: mod.rs:706-708 routes WindowsX86_64 threads to windows::dispatch(regs) and returns BEFORE syscall_capability_allowed is ever consulted (the cap check at mod.rs:170 is only on the native dispatch_inner path; the fast-path at mod.rs:160-167 also skips it). Inside windows/mod.rs, nt_create_file/nt_open_file (mod.rs:628-673) → open_wxe_file_handle → crate::fs::vfs::open directly; wxe_create_file (mod.rs:550) likewise; nt_allocate_virtual_memory (mod.rs:420) → sys_mmap_u64 directly. None check CAP_FILESYSTEM/CAP_MEMORY. The Linux path (linux/mod.rs:317 dispatch) is identical — no capability gating in its giant match either.
    - impact: A WXE/LXE process can open/write/create files and map memory regardless of the capabilities its parent granted at SYS_WXE_SPAWN/SYS_LXE_SPAWN time. The capability model (CLAUDE.md App Capabilities) is silently void for the entire foreign-ABI surface.
    - fix: Either (a) enforce capabilities at the foreign-ABI boundary: map NT/Linux services to the equivalent native cap and call syscall_capability_allowed with the mapped requirement before performing the action, or (b) explicitly document that WXE/LXE processes inherit a fixed cap set and run the underlying native handlers (sys_write/sys_open) which themselves enforce caps — but currently they call vfs::open directly, bypassing even that.
- **[HIGH/performance/effort:small]** current_thread_abi() takes the global SCHEDULER spinlock on every single syscall (mislabeled lock-free)
    - evidence: mod.rs:699-709 comments it is read 'once (lock-free per-CPU read)' as 'the hottest branch in the syscall path', but thread_config.rs:89-98 current_thread_abi() does `let guard = SCHEDULER.lock();`. Every syscall on every CPU now acquires the one global scheduler spinlock before dispatch. On SMP this serializes all syscalls against each other and against the scheduler tick. By contrast set_thread_linux_rootfs (thread_config.rs:117) maintains a real lock-free per-CPU cache, showing the intended pattern exists but is not used for abi.
    - impact: Syscall throughput collapses under SMP contention (problem #9 perf): read/write/open all stall on the global scheduler lock; a scheduler holding the lock blocks every CPU's syscall entry. Also a latent deadlock risk if any code path holding SCHEDULER tries to read abi.
    - fix: Cache the ABI personality in a per-CPU array updated on context switch (next to the linux_rootfs cache and the windows_gs_base wrmsr at scheduler/mod.rs:2651) and read it without locking in syscall_dispatch_64.
- **[HIGH/stability/effort:small]** sys_screen_size, sys_capture_screen, sys_grant_framebuffer write info structs through raw pointers with no validation
    - evidence: display.rs:24-29 sys_screen_size writes `*(buf_ptr as *mut u32); *buf.add(1)` after only `if buf_ptr == 0`. display.rs:1010-1017 sys_capture_screen writes width/height/pitch via `*(info_ptr as *mut u32)` with only `if info_ptr != 0` (no range, no mapping). display.rs:1041-1049 then does an unvalidated row-by-row copy into `buf_ptr as *mut u8` (the buf_size check is value-only; buf_ptr is never validated against user range/mapping). display.rs:1342-1349 sys_grant_framebuffer writes out_info via `*(out_info_ptr as *mut u32)` with only `if out_info_ptr != 0`. Note these are compositor-gated (is_compositor) so the attacker must be the compositor, lowering severity vs. net/time but still a kernel-write primitive if the compositor is compromised or buggy.
    - impact: Compositor process can cause kernel memory corruption / #PF by passing a bad info pointer; given the compositor handles untrusted window content this is a meaningful escalation surface.
    - fix: Validate every out_info/buf pointer with is_user_range_accessible (or write via copy_to_user_bytes). sys_capture_screen must validate buf_ptr against buf_size and mapping before the memcpy loop.
- **[MEDIUM/stability/effort:small]** sys_audio_write builds an unvalidated user slice
    - evidence: display.rs:259-264 sys_audio_write: after `if buf_ptr == 0 || buf_len == 0` it does `core::slice::from_raw_parts(buf_ptr as *const u8, buf_len)` with NO is_valid_user_ptr and NO length cap, then passes it to the audio driver. buf_len is a full u32 (up to 4 GiB).
    - impact: Kernel reads an arbitrary, attacker-sized region (info leak into audio device / DMA) or #PF; any process with CAP that reaches audio can trigger it.
    - fix: Add is_user_range_accessible(buf_ptr, buf_len) and cap buf_len (e.g. 1 MiB) before constructing the slice; ideally copy_user_bytes into a bounded kernel buffer.
- **[MEDIUM/architecture/effort:large]** Three fully duplicated giant dispatch matches (native/linux/windows) with no shared structure
    - evidence: Native: mod.rs dispatch_inner ~lines 174-650 (one match arm per ~180 syscalls). Linux: linux/mod.rs:341+ a parallel giant match. Windows: windows/mod.rs:211-282 two matches. The native match also re-lists SYS_WRITE/SYS_READ etc both in the fast path (mod.rs:160-167) and again in the main match (mod.rs:177-178) — dead arms. mmap/munmap/sbrk are handled in BOTH syscall_dispatch_64 (u64 path, mod.rs:747-787) and dispatch_inner (u32 legacy arms, mod.rs:189-190), with comments admitting the duplication. The VT-x syscalls are listed twice (dispatch_inner cfg arms AND the u64 pre-dispatch block mod.rs:791-899).
    - impact: High maintenance cost and bug surface (e.g. an arg that should be u64 truncated in one path but not the other); the dead/duplicate arms are confusing and the truncation discipline is easy to get wrong (the file's own header warns about it).
    - fix: Introduce a table-driven dispatch (array indexed by syscall number → fn pointer + arg-width descriptor + required cap) shared by all three ABIs, or at least factor the u64-pointer syscalls into one list consumed by both paths. Remove the dead SYS_WRITE/SYS_READ/etc arms from dispatch_inner now that the fast path handles them.
- **[MEDIUM/lxe/effort:medium]** WXE map_fd_handle treats any handle <= u32::MAX as a raw fd index — Windows HANDLEs are forgeable into kernel fds
    - evidence: windows/mod.rs:1190-1198 map_fd_handle: besides the three std handles, `h if h <= u32::MAX as u64 => Some(h as u32)` — i.e. ANY 0..=0xFFFFFFFF value is accepted as a file-descriptor index and passed to sys_read/sys_write/sys_close/sys_lseek (nt_read_file/nt_write_file/nt_close/wxe_set_file_pointer_ex). open_wxe_file_handle returns the raw native fd as the HANDLE (mod.rs:753 `Some(fd as u64)`). There is no table mapping opaque HANDLEs to fds, so a WXE program can call NtReadFile/NtWriteFile on arbitrary fd numbers it never opened.
    - impact: A WXE process can read/write/close any FD in its own per-process fd table by guessing indices (e.g. fds opened by the loader or inherited), and NtClose on fd 0/1/2 is silently swallowed. The underlying native fd handlers do bound-check the per-process table so it cannot reach other processes, limiting this to intra-process fd confusion, but it breaks the HANDLE abstraction and can corrupt the program's own state.
    - fix: Maintain a per-WXE-process HANDLE→fd table (opaque, non-sequential handle values) instead of returning the raw fd as the HANDLE and accepting any integer as a handle.
- **[MEDIUM/lxe/effort:small]** WXE stack_arg reads stack args from user RSP without validating each slot is mapped before use in privileged ops
    - evidence: windows/mod.rs:1215-1221 stack_arg reads `read_user_u64(regs.rsp + 8 + 32 + (n-5)*8)` — this DOES go through copy_user_bytes (mapping-validated), which is good. But nt_write_file/nt_read_file (mod.rs:319-377) take `buffer = stack_arg(regs,6)` and `length = stack_arg(regs,7)` then pass buffer straight to sys_write/sys_read which only do is_valid_user_ptr (range) — so the data buffer itself is range-checked but not mapping-checked, inheriting the is_valid_user_ptr weakness above. Length is correctly bounded by MAX_NT_IO_COPY.
    - impact: NtReadFile/NtWriteFile with a valid-range but unmapped buffer faults in the kernel (DoS) — bounded to WXE processes.
    - fix: Once sys_read/sys_write are upgraded to mapping-validated transfers (copy paths already use copy_user_bytes in io.rs for the file branch; the issue is the initial is_valid_user_ptr gate at io.rs:27/154), this is covered. Verify the io.rs read/write chunk paths reject unmapped pages mid-transfer (they do via copy_user_bytes returning None).
- **[MEDIUM/file-length/effort:large]** display.rs is 2156 lines and loader/windows.rs 1485 — exceed maintainable size with arch-duplicated bodies
    - evidence: wc -l: display.rs=2156, process.rs=1681, windows/mod.rs=1277, loader/windows.rs=1485, system.rs=1114, net.rs=1110. display.rs duplicates almost every handler as separate #[cfg(target_arch="x86_64")] / #[cfg(target_arch="aarch64")] functions (e.g. sys_screen_size x2, sys_map_framebuffer x2, sys_gpu_command x2, sys_input_poll x2 — the input_poll pair alone is ~220 lines duplicated).

- **[LOW/architecture/effort:small]** sys_set_dll_u32 / fast-path syscalls skip the capability check
    - evidence: mod.rs:160-167 the fast path returns sys_write/sys_read/sys_uptime/yield/sleep BEFORE syscall_capability_allowed (mod.rs:170). For write/read this is arguably fine (they enforce via fd table), but it means the cap gate is structurally easy to bypass by adding a fast-path arm. Combined with the foreign-ABI bypass, the capability model is enforced inconsistently.

### Refactor opportunities
- Centralize ALL user-memory access behind copy_user_bytes/copy_to_user_bytes (mapping-validated) and forbid raw `as *mut`/`from_raw_parts` in handlers via a clippy lint or CI grep; this single change closes the sys_time/net_config/fstat/audio class of bugs.
- Add a copy-fault exception table (like Linux's __ex_table) so a user access that faults returns -EFAULT instead of panicking the kernel — eliminates the entire TOCTOU/unmapped-page panic class even on SMP munmap races.
- Make current_thread_abi() a lock-free per-CPU read (update it on context switch alongside windows_gs_base/linux_fs_base) — removes a global spinlock from every syscall.
- Convert the three giant ABI matches into one table-driven dispatch (num → {fn, arg-width, required_cap}) so truncation rules, capability enforcement, and the u64-pointer list are defined once and shared by native/linux/windows.
- Enforce capabilities at the WXE/LXE boundary (map NT/Linux service → native cap, or route through native handlers that already enforce caps) so foreign-ABI processes can't silently exceed their granted capability set.
- Introduce an opaque per-process HANDLE table for WXE instead of returning raw fds as Windows HANDLEs.
- Split display.rs and loader/windows.rs per the suggested module boundaries and de-duplicate the x86_64/aarch64 handler bodies behind a small arch trait.
- Remove dead duplicate match arms in dispatch_inner (SYS_WRITE/SYS_READ already in fast path; mmap/munmap/sbrk duplicated between dispatch_inner and syscall_dispatch_64).

### Test gaps
There appear to be no kunit-style tests for the syscall validation layer (no test module in handlers/helpers.rs and no harness referenced). The highest-value, lowest-effort coverage: (1) Unit-test is_valid_user_ptr / is_user_range_accessible / copy_user_bytes against boundary cases (ptr=0, ptr+len overflow at 2^48, kernel-half ptr, page-boundary spanning, unmapped page) — these are pure logic and can run under kunit. (2) A headless serial-driven negative-test program that fires each syscall that takes a pointer with (a) NULL, (b) a kernel-half address, (c) an in-range unmapped address, and asserts the kernel returns an error rather than panicking — this would immediately surface sys_time/sys_set_time/sys_net_config/sys_fstat/sys_audio_write. (3) A WXE conformance test that confirms NtCreateFile honors (or documents bypassing) CAP_FILESYSTEM, and that NtReadFile rejects un-opened HANDLEs. (4) A SMP stress test measuring syscall throughput to expose the SCHEDULER.lock() in current_thread_abi(). None of these exist today; the closest is the manual surf-host/QEMU workflow which does not exercise malformed syscall pointers.

### Open questions
1) Is the WXE/LXE capability bypass intentional (foreign processes get a fixed cap set) or an oversight? It needs an explicit decision because NT/Linux services currently call vfs::open and sys_mmap_u64 directly, bypassing even the native handlers' own cap checks. 2) On SMP, is the user address space pinned for the duration of a syscall? If not, even is_user_range_accessible is racy against a concurrent munmap from another thread of the same process — confirming this determines whether a copy-fault handler is mandatory. 3) Several handlers (display.rs framebuffer mapping) call map_page under the user CR3 during a syscall; the code comments note the first-64-MiB identity-map limitation — worth confirming there is no remaining path that allocates phys pages under user CR3 (sys_set_resolution already switches to kernel CR3, but sys_map_framebuffer/sys_capture_screen call map_page directly). 4) The CLAUDE.md DS/ES section references kernel/asm/x86/syscall_entry.asm which does not exist — confirm the doc should be updated to syscall_fast.asm so future contributors don't look for a phantom file.

## LXE-KERNEL — LXE (Linux execution environment) — kernel-side Linux x86_64 syscall translation layer

**Architecture:** LXE is a "Tier-0" Linux x86_64 syscall bridge living in `kernel/src/syscall/linux/`. `dispatch()` in mod.rs (kernel/src/syscall/linux/mod.rs:317) is a giant `match nr { ... }` over ~190 Linux syscall numbers; unknown numbers fall through to `linux_unsupported_syscall` → `-ENOSYS`. Each subsystem lives in its own file: fs.rs (path/stat/open/dirents/xattr), io.rs (read/write/pread/pwrite/ioctl/poll/select/fcntl/sendfile), process.rs (clone/fork/vfork/wait4/signals/futex/ids/sched/clocks), memory.rs (brk/mmap/mremap/mprotect/arch_prctl/swap), socket.rs, procfs.rs (a synthetic /proc backed by enum file-IDs in FdKind::LinuxProc), path.rs (rootfs chroot translation + a global resolve cache), abi.rs (struct writers), fb.rs (/dev/fb0), trace.rs, ipc.rs (all SysV IPC stubbed). Errno mapping is the Linux negative-errno convention via `linux_err()`.

Linux processes run under a chroot-style rootfs at `/System/var/lxe/rootfs`; every guest path is normalized, prefixed with the rootfs, and symlink-resolved inside the rootfs (path.rs `linux_resolve_translated_path` + a 256-entry positive cache and 512-entry negative cache). FS calls ultimately go through anyOS VFS (`crate::fs::vfs`), so LXE inherits the VFS/block-cache layer including the known apt/exFAT large-block read-after-write coherence problem.

The ELF loader is `kernel/src/task/loader/linux.rs`: it parses ELF64, maps the main image (DYN at fixed bias 0x5555_0000_0000, interpreter at 0x7000_0000_0000), maps an 8 MiB ASLR stack, builds the System V initial stack (argv/envp/16 auxv entries incl. AT_RANDOM), installs a sigreturn trampoline, and either spawns a new thread or replaces the current image (execve). Per-thread Linux state (fs_base, clear_child_tid, real/eff/saved uid/gid, rootfs, brk) lives in the scheduler Thread struct. Futexes use a fixed global 64-slot × 8-waiter table (process.rs) — there is no per-process namespacing and no condition recheck under a lock around the actual block.

Global state of note: LXE_RESOLVE_CACHE / LXE_NEGATIVE_PATH_CACHE (Spinlock<Vec>, path.rs), LINUX_FUTEX_WAITERS (Spinlock<[slot;64]>, process.rs), WAIT4_DEBUG_SEQ, and several AtomicU8 console-state globals in io.rs. Signal actions / blocked mask / fs_base / ids are per-thread in the scheduler.

### Problems
- **[CRITICAL/lxe/effort:medium]** wait4 never reports WIFSIGNALED — signal-killed children look like normal exits, breaks shells/build tools
    - evidence: process.rs:679 unconditionally encodes every result as a normal exit: `let status_value = (code & 0xff) << 8;` (i.e. WIFEXITED, WEXITSTATUS=code). But the scheduler stores signal deaths AS the exit_code: lifecycle.rs:212/339 set `exit_code = Some(9)` for SIGKILL, mod.rs:2273/2523 + lifecycle.rs:794 set `Some(139)` for SIGSEGV, accessors.rs:162 `Some(139)`, lifecycle.rs:896 `Some(signal)`. So a child killed by SIGSEGV is returned to the guest as status 0x8B00 → WIFEXITED true, WEXITSTATUS=139, WIFSIGNALED false. A child killed by SIGKILL becomes 'exited 9'. There is no WIFSIGNALED path (low 7 bits = signal) and no WCOREDUMP bit. wait4 also never sets the 0x7f 'stopped' encoding except the special sentinel u32::MAX-2 which just returns 0.
    - impact: bash/make/apt/dpkg use WIFSIGNALED/WTERMSIG to detect crashed children and abort/cleanup. They will instead treat a segfaulted helper as a clean exit with a weird status, mis-sequence multi-stage pipelines, and skip error handling — a primary reason 'LXE is not stable'.
    - fix: Propagate the death kind from the scheduler: store a discriminator (exited vs signalled) alongside exit_code, or reserve a high bit. In linux_wait4 encode `WIFSIGNALED` as `signal & 0x7f` (optionally |0x80 for core), and reserve `<<8` only for true exits. Map anyOS 128+sig convention back to a signal number for the signalled case.
- **[CRITICAL/lxe/effort:large]** futex FUTEX_WAIT has a lost-wakeup race: value re-check and block are not atomic with respect to FUTEX_WAKE
    - evidence: process.rs:1672-1706. linux_futex_wait takes LINUX_FUTEX_WAITERS.lock(), adds the waiter, re-reads the value, calls prepare_to_block_current()/prepare_to_block_until() while holding the futex lock, then DROPS the lock (end of block at :1694) and only afterwards calls scheduler::schedule() (:1696). prepare_to_block_current (wait.rs:461) takes a *separate* SCHEDULER.lock() and only sets state=Blocked; it does not deschedule. Between releasing LINUX_FUTEX_WAITERS and calling schedule(), a FUTEX_WAKE on another CPU can run futex_wake_addr (process.rs:1600) → remove the tid and call wake_thread(tid) (priority.rs:31) which flips the thread back to Ready *before it ever blocked*. Then this thread calls schedule() and blocks forever with no waiter entry remaining. There is no seqlock/wait-queue token bridging the unlock→schedule gap.
    - impact: glibc/pthread mutexes, condition variables and the apt/dpkg lock fallbacks deadlock intermittently under SMP or preemption. This matches the reported LXE freezes. Also the 64×8=512 global waiter cap silently returns ENOMEM (:1675) when exceeded, and is shared across ALL Linux processes with no PID namespacing, so private-futex addresses from different processes that happen to collide will cross-wake.
    - fix: Block atomically: extend the scheduler with a 'prepare_to_block while holding token X, then atomically commit the block in schedule()' primitive, or keep the futex slot lock held until the thread is marked Blocked inside SCHEDULER and have wake_thread be a no-op until save_complete. Recheck the futex word after marking Blocked but before releasing the run queue. Namespace futexes by page-directory (private futex) so addresses can't collide across processes; key the slot on (pd, uaddr).
- **[HIGH/lxe/effort:medium]** mprotect is a complete no-op — W^X / PROT_NONE guard semantics silently ignored
    - evidence: memory.rs:431-437 linux_mprotect ignores addr and prot entirely, returns 0 for any non-zero len. It never changes page table permissions. Combined with linux_mmap which maps anonymous regions as RW (linux_map_fixed at memory.rs:580 maps 0x02|0x04 = writable+user, no NX control) and large/no-access anon via sys_mmap_reserve. JIT engines (the guest's own libjs-equivalent, Python, Java, BoringSSL with hwcap) that mmap RW then mprotect RX will execute pages that are still writable, or expect PROT_NONE guard pages (e.g. between thread stacks, glibc's thread guard) that are in fact accessible.
    - impact: PROT_NONE guard pages don't fault → stack overflows in guest threads silently corrupt adjacent memory instead of crashing cleanly. mprotect(...,PROT_READ) on relro/GOT doesn't take effect → no protection and, worse, code relying on the EFAULT-on-write behavior won't get it. This is both a stability and a correctness hole.
    - fix: Implement real mprotect by walking the page tables for [addr,addr+len) and updating present/writable/NX bits per PROT flags (PROT_NONE → not-present or reserved, no PROT_WRITE → clear writable, no PROT_EXEC → set NX), with TLB shootdown. Validate the range is mapped and return ENOMEM for holes. Make mmap honor prot for the initial mapping too.
- **[HIGH/lxe/effort:xl]** MAP_SHARED file mmap and writable shared mmap rejected; file mmap is a one-shot copy with no writeback
    - evidence: memory.rs:71-82 rejects any MAP_SHARED with PROT_WRITE as ENOSYS, and memory.rs:157-183 implements file-backed MAP_PRIVATE by eagerly copying file bytes into freshly allocated anonymous pages (linux_fill_mapping_from_fd). There is no page-cache sharing, no copy-on-write, no msync writeback (linux_msync memory.rs:439 is a no-op that only validates the range). mremap of a file mapping just memcpys anonymous pages.
    - impact: Shared writable mmap (used by databases, dpkg's mmap of status, SQLite default VFS, /dev/shm, many runtimes) returns ENOSYS and aborts the program. Private file mmap that the guest later writes-back via msync(MS_SYNC) silently loses data. Large binaries mmap'd by ld.so consume full anonymous RAM per mapping instead of sharing the page cache. The eager copy also re-reads the file through the same VFS path implicated in the exFAT corruption bug.
    - fix: Add a page-cache-backed file mapping with demand paging and a dirty-page writeback on msync/munmap for MAP_SHARED. At minimum implement MAP_SHARED read-only and MAP_SHARED writable for regular files with writeback, and CoW for MAP_PRIVATE so writes don't need the eager full-file copy.
- **[HIGH/swap/effort:large]** LXE pread/mmap-fill read path is the exact surface of the apt/exFAT large-block read-after-write corruption
    - evidence: memory.rs:625-688 linux_read_fd_at + linux_read_global_chunk_at: pread64 (io.rs:338) and file mmap fill (memory.rs:169) call vfs::read_at (vfs/mod.rs:4192). read_at flushes writer append buffers via sync_open_exfat_path then does a detached read. fs.rs / io.rs read() path goes through sys_read → vfs::read. The two paths have different flush/coherence behavior. The comment at memory.rs:667-671 explicitly documents a previously-fixed 'zero hole' bug where a short chunk from read_at at a FAT-run boundary was treated as EOF and corrupted ar member headers — i.e. LXE pread is precisely where the documented apt/exFAT data-corruption bug bites. The 64 KiB chunking (FILE_MAP_COPY_CHUNK) interacts with the block cache's per-sector keying noted in CLAUDE.md/memory.
    - impact: apt/dpkg extract .deb (ar/tar) members via pread/mmap right after the download writer committed them; stale or zero-filled cache pages produce silent archive corruption. Matches the stored memory note that this is a large-block read-after-write cache bug rather than a syscall bug — but LXE's split read vs read_at code paths make it easy for one path to miss the flush.
    - fix: Unify LXE's positional reads onto a single coherent VFS primitive that always flushes all writers for the path AND reads through the block cache with correct large-block (multi-sector) invalidation. Add a kunit/vfsstress regression that writes a multi-MiB file via fd A then prereads it via fd B at non-sector-aligned offsets and byte-compares. Fix the underlying block-cache large-block read-after-write coherence (the root cause) rather than patching each LXE caller.
- **[HIGH/lxe/effort:xl]** clone CLONE_VM thread shares page directory but the futex/TLS/clear_tid model is incomplete; vfork is a full fork
    - evidence: process.rs:365-370 linux_vfork just calls linux_fork — vfork's contract (parent suspended until child execs/exits, shared address space) is violated; the comment admits it. linux_clone (process.rs:147-153) requires CLONE_THREAD with CLONE_VM|CLONE_SIGHAND but create_linux_clone_thread (spawn.rs:212) clones fd_table and signals by value (spawn.rs:289-290 `.clone()`), so CLONE_FILES/CLONE_SIGHAND threads do NOT actually share the fd table or signal handlers — a write to one thread's fd table is invisible to siblings, violating POSIX thread semantics. clone also ignores CLONE_VFORK and any unknown flag in the non-thread path beyond child_stack!=0 → ENOSYS.
    - impact: vfork-based shell spawn (dash/busybox) corrupts because parent isn't suspended; pthreads that dup/close fds or install signal handlers expected to be process-wide get per-thread copies → file descriptors leak/desync and signal delivery is wrong. This is a structural reason multithreaded Linux binaries are unstable under LXE.
    - fix: Make CLONE_FILES/CLONE_SIGHAND share the underlying fd table / sighand via reference-counted shared structures rather than cloning. Implement vfork properly (suspend parent until child execve/exit, or at least mark the shared mapping). Reject thread creation that requests sharing semantics LXE can't honor with EINVAL rather than silently diverging.
- **[HIGH/lxe/effort:xl]** epoll / eventfd / signalfd / timerfd / inotify / poll-blocking are missing or busy-poll; modern event loops break or burn CPU
    - evidence: mod.rs dispatch has no epoll_create/epoll_ctl/epoll_wait (213-233), eventfd2 (290), signalfd4 (289), timerfd_* (283-286), inotify (253-254), ppoll, io_uring, memfd_create, pidfd_* — all fall to linux_unsupported_syscall → ENOSYS. poll/select/pselect6 (io.rs:667/717/862) are implemented as busy spin loops: `loop { net::poll(); ready=...; net::wait_for_poll_progress() }` with no real blocking on fd readiness. There is no readiness wait queue; a poll with a long/infinite timeout spins.
    - impact: Any program built on libevent/glibc's epoll-based event loop (systemd tools, modern apt's http method uses poll heavily, Python asyncio, Node) gets ENOSYS and aborts. Programs that fall back to poll/select still run but pin a CPU at 100% because the wait is a busy loop, which both wastes power and starves other threads — a 'freeze/perf' symptom.
    - fix: Add eventfd and a minimal epoll backed by the same fd readiness primitives poll uses; convert poll/select/epoll_wait to block on a readiness wait queue (sleep until net poll progress or a timer tick, woken by I/O completion) instead of spinning. signalfd/timerfd can be layered on the existing signal/timer infrastructure.
- **[HIGH/stability/effort:medium]** Struct layout writers use raw unaligned pointer stores with no per-write bounds check; 32/64-bit and field-offset bugs are unchecked
    - evidence: abi.rs:128-142 write_u32/u16/u64 do `*((base+offset) as *mut T) = value` with no alignment or mapping check — they rely on a single up-front is_user_range_accessible(stat_ptr,144) in callers (fs.rs:41). But write_linux_stat writes through offset 104 (abi.rs:44, ctime nsec area) for a struct only validated to 144 bytes — the real glibc struct stat is 144 bytes so it's borderline; statx validates 256 and writes to 140 (abi.rs:110) which is fine. More dangerous: getdents (fs.rs:1551-1564) computes reclen = align_up(18+name+2,8) then writes d_type at base+reclen-1 and pads with `reclen - 20 - name.len()` (fs.rs:1562) which UNDERFLOWS to a huge usize when reclen==19+name (write_bytes of ~2^64) — and the getdents64 dirent struct uses 19-byte header but old getdents uses a different layout; both hand-roll offsets. linux_clock_gettime/gettimeofday write timespec assuming 64-bit time_t only. There is no 32-bit-compat struct support at all (uname/stat/timespec are all 64-bit-only) yet the loader explicitly rejects ELF32 (loader/linux.rs:471) so that's consistent — but glibc x32 / seccomp-restricted structs are not.
    - impact: A directory entry whose name length makes reclen exactly 19+name triggers `write_bytes(ptr, 0, reclen-20-name)` with a near-2^64 count → kernel memory corruption / panic from a getdents on attacker-or-app-controlled filenames. The hand-rolled offsets are fragile and any future struct change silently writes wrong fields with no compile-time layout guarantee.
    - fix: Replace hand-rolled offset writes with #[repr(C)] structs and a single checked copy_to_user_bytes of the whole struct. Fix the getdents padding underflow (compute padding as reclen - (header+name+1) with saturating_sub and an assert). Add explicit reclen<=remaining checks.
- **[MEDIUM/stability/effort:medium]** linux_read/linux_write do not validate buf_ptr range before the FdKind dispatch; rely on weaker is_valid_user_ptr in sys_read
    - evidence: io.rs:202-230 linux_read: for File fds it calls handlers::sys_read which validates only via is_valid_user_ptr (helpers.rs:53 — checks ptr!=0 and end<=2^47 but NOT that pages are mapped) then copy_to_user_bytes per chunk (which does validate). But the LinuxProc/socket/framebuffer branches (io.rs:210-222) pass buf_ptr straight to sub-handlers; linux_copy_proc_content (procfs.rs:123) only checks buf_ptr==0 then relies on copy_to_user_bytes — OK — but socket_read/linux_fb_read must each independently validate. The pattern is inconsistent: some paths validate the full range up front, some only at copy time, some (poll fds_ptr, getdents) validate up front. read_user_str_safe (helpers.rs:154) walks up to 4096 bytes re-checking page mapping per boundary which is correct but the whole-range readv path (io.rs:628) reads iov base/len from user memory then re-enters linux_read per iov — a TOCTOU where user could unmap between iov read and use (mitigated only because copy_to_user_bytes re-checks).
    - impact: Mostly mitigated by per-chunk copy validation, but the inconsistency makes it easy to introduce a direct unchecked deref (as abi.rs already does) in a new branch, and is_valid_user_ptr alone (no mapping check) is insufficient if any path dereferences without going through copy_*_bytes. Hard to audit.
    - fix: Establish one rule: every syscall validates its full user buffer with is_user_range_accessible up front, and only the bulk copy helpers touch user memory. Add a debug assertion or wrapper so raw `*ptr` stores in abi.rs are impossible. Audit socket_read/linux_fb_* for full-range validation.
- **[MEDIUM/lxe/effort:small]** getrandom is a non-cryptographic xorshift seeded from tick/tid; AT_RANDOM likewise weak
    - evidence: process.rs:941-958 linux_getrandom seeds an xorshift64 with `timer_ticks ^ (tid<<32) ^ const` and returns at most 256 bytes regardless of requested len (silently truncates: `let len = len.min(256)`), ignores the GRND_RANDOM/GRND_NONBLOCK flags arg entirely (it isn't even a parameter — dispatch passes only buf,len at mod.rs:543). loader/linux.rs:359-366 builds AT_RANDOM the same weak way. No EFAULT range check on the full buffer (only buf_ptr==0).
    - impact: Stack canaries (AT_RANDOM), ASLR seeds, and any guest crypto/TLS seeding via getrandom are predictable across boots/ticks → security weakness, and getrandom returning fewer bytes than requested without error violates the ABI (glibc loops expecting full fill could spin or use uninitialized bytes). Missing buffer range check can write up to 256 bytes past a short valid mapping.
    - fix: Back getrandom with the kernel CSPRNG/entropy source, return the full requested length (looping), honor GRND_* flags, and validate the entire output buffer with is_user_range_accessible. Use the same source for AT_RANDOM.
- **[MEDIUM/lxe/effort:large]** SysV IPC (shm/sem/msg) and many process syscalls fully stubbed; setpgid/getpgrp/setsid are fictional
    - evidence: ipc.rs: all shmget/shmat/shmctl/semget/semop/semctl/msgget/msgsnd/msgrcv/msgctl return ENOSYS/EINVAL (ipc.rs:3-51). process.rs:733-765: setpgid does nothing but validate, getpgid/getpgrp returns the tid as the pgid, setsid returns tid, getsid returns the pgid — there is no real process-group/session model. sched_setaffinity (process.rs:834) validates then ignores. capset (process.rs:1458) is root-gated no-op. prlimit (process.rs:1503) returns hardcoded fake limits (RLIMIT_NOFILE=64 always).
    - impact: Job control (shell pipelines, terminal signal delivery to a process group, daemons calling setsid) behaves incorrectly; SysV IPC users (PostgreSQL, some installers) fail. RLIMIT_NOFILE=64 fixed limit will break programs that try to raise it. Mostly 'feature gaps' but they manifest as confusing partial breakage rather than clean ENOSYS.
    - fix: Implement a minimal pgid/sid model in the scheduler (store pgid/sid per thread-group; setpgid/setsid mutate it; kill(-pgid) iterates). Implement SysV shm at least on top of the existing anon shared memory. Return real RLIMIT_NOFILE from the fd table size. Where unimplementable, prefer the errno a real Linux returns over a silent fake success.
- **[MEDIUM/stability/effort:large]** execve replaces the image with interrupts disabled and a manual CR3/MSR dance; cross-CPU page-table UAF risk and no robust-list/clear_tid handling
    - evidence: loader/linux.rs:764-867 exec_current_linux_process: after building the new pd it does `cli; mov cr3, kernel_cr3; wrmsr FS_BASE,0` (822-839), conditionally destroys the old pd only if terminate_exec_siblings says it's safe (800/841), then `mov cr3, new_cr3; jump_to_user_mode`. The comment at 845 admits old pd is retained to avoid 'cross-CPU page-table UAF' — i.e. the safe-destroy condition is a heuristic, leaking the old address space when other CPUs might reference it. set_robust_list is accepted as a no-op (mod.rs:531) so robust futexes are never cleaned up on thread death (only clear_child_tid is, handlers/process.rs:27-32).
    - impact: execve leaks page directories under SMP contention (memory growth over many exec cycles — apt runs hundreds of execs). Robust-list futexes held by a crashing thread are never released → other threads block forever (another freeze vector). The hand-rolled cli/cr3 sequence is fragile and arch-specific in a file that also has aarch64 branches.
    - fix: Reference-count address spaces so the old pd is freed exactly when its last CPU reference drops, removing the leak. Implement robust-list walking on thread exit to wake/clear owned futexes. Extract the cr3/fs-base transition into the HAL so the loader isn't doing inline asm per arch.
- **[MEDIUM/performance/effort:medium]** Path resolve cache is unbounded-scan O(n) Vec with FIFO eviction and is not invalidated on all mutating paths
    - evidence: path.rs:163-208 linux_resolve_cache_get/put iterate a Vec linearly (up to 256 entries) on every path syscall under a global Spinlock; eviction is remove(0) (O(n) shift). The negative cache is 512 entries, same pattern. Invalidation (linux_resolve_cache_invalidate_path, path.rs:133) is only called from open(create)/rename/mkdir/unlink/symlink/link inside LXE — but a file created via the *native* anyOS path, or via a writeback that changes a symlink target out from under LXE, is not invalidated, so the negative cache can pin a 'not found' for a path that later exists.
    - impact: Every fs syscall pays a linear cache scan under a global lock — contention and latency for the fd-heavy apt/dpkg workloads. Stale negative-cache entries cause spurious ENOENT after a concurrent create from outside LXE; stale positive entries return a path whose symlink was retargeted. Correctness + perf.
    - fix: Replace the Vec caches with a hashmap keyed by (rootfs,path,flags) with LRU eviction, and hook cache invalidation into the VFS layer (invalidate on any namespace mutation regardless of caller) rather than only LXE-internal mutators.
- **[LOW/lxe/effort:medium]** sched_yield always full-reschedules; nanosleep/clock_nanosleep ignore remaining-time and EINTR; rt_sigsuspend/pause are fake
    - evidence: process.rs:786-792 sched_yield calls scheduler::schedule() (correct intent). But process.rs:1204 linux_sleep_timespec ignores rem_ptr entirely (_rem_ptr) so an interrupted sleep can't report remaining time, and it never returns EINTR — a signal during sleep is lost from the guest's perspective. linux_rt_sigsuspend (process.rs:767) just returns EINTR without ever atomically installing the temp mask and waiting. linux_pause (mod.rs:379) returns EINTR immediately without ever blocking. alarm (mod.rs:381) returns 0 and does nothing.
    - impact: Programs relying on sigsuspend/pause to wait for a signal will spin (immediate EINTR loop) burning CPU; alarm()-based timeouts never fire; nanosleep can't be correctly resumed after a signal. Lower severity because few build-tools depend on these, but contributes to CPU-burn 'freezes'.
    - fix: Implement pause/sigsuspend as a real block on the signal wait queue returning EINTR only when a signal is actually delivered; fill rem_ptr on interrupted nanosleep; implement alarm via a per-thread timer that raises SIGALRM.
- **[LOW/lxe/effort:small]** linux_set_tid_address / clear_child_tid does not wake on thread exit via the robust path, and clone parent_settid write is unchecked-after-validate
    - evidence: process.rs:226-229 and 280-283 write the child tid to parent_tidptr via write_u32 after validating with is_user_range_accessible at 160-165/242-244, but the validation and the write are separated by create_linux_clone_thread / sys_fork which can schedule and the user page could be unmapped in between (TOCTOU on the parent_tidptr store — a direct kernel write to a now-unmapped user page → #PF in kernel). clear_child_tid wake exists (handlers/process.rs:32 calls futex_wake_addr) but only on clean exit; combined with the futex race above, the wake can be lost.
    - impact: Rare kernel fault if the parent unmaps the tid page during clone; pthread_join relying on the clear_child_tid futex wake can hang if the wake races (see futex finding). Low frequency.
    - fix: Use copy_to_user_bytes for the parent_tidptr store (which re-validates atomically) instead of raw write_u32 after an earlier validate. Ensure the exit-time clear_child_tid wake goes through the fixed atomic futex primitive.
- **[MEDIUM/file-length/effort:medium]** Five LXE files exceed ~1000–1800 lines, violating problem #1 (far-too-long files) and making the ABI hard to audit
    - evidence: wc -l: fs.rs 1788, process.rs 1736, socket.rs 1702, io.rs 1421, procfs.rs 1071. Each mixes many unrelated syscall families (e.g. process.rs holds clone, wait, signals, futex, credentials, scheduling, clocks, getrandom, uname). The dispatch match in mod.rs is also a 200-line flat table that is easy to mis-wire (e.g. CHOWN and LCHOWN both routed to linux_chown at mod.rs:436 so lchown follows symlinks — a subtle ABI bug hidden by file length).
    - impact: High cognitive load, merge conflicts, and exactly the kind of subtle routing bug (lchown==chown) that long flat files hide. Slows every future LXE fix.
    - fix: Split per the per-file suggestions in key_files. Additionally, drive dispatch from a table of (nr, name, handler) tuples so name and handler can't drift, and so lchown vs chown is explicit.
- **[LOW/lxe/effort:medium]** lchown incorrectly follows symlinks; rename does not handle RENAME_NOREPLACE/EXCHANGE; many *at flags ignored
    - evidence: mod.rs:436 `LINUX_SYS_CHOWN | LINUX_SYS_LCHOWN => linux_chown(...)` — both follow the symlink (linux_chown_translated has no nofollow). renameat2 (mod.rs:536) only accepts flags==0, returns EINVAL otherwise (so RENAME_NOREPLACE used by safe-write patterns fails). utime/utimensat (fs.rs:1204/1249) validate then just stat the file — they NEVER actually set the timestamps (return 0 as success). chmod/chown/utimensat are effectively partial no-ops for metadata.
    - impact: Tools that chown a symlink expecting lchown semantics modify the target; atomic rename-with-RENAME_NOREPLACE (used by dpkg/coreutils mv) fails; build systems and tar/cpio that set mtimes find them silently ignored → incremental builds and 'make' timestamp logic misbehave. Low individually but collectively erode trust.
    - fix: Route LCHOWN through a nofollow variant; support RENAME_NOREPLACE (stat target, EEXIST) in renameat2; make utimensat actually persist mtime/atime via a vfs set_times API (add one if missing) instead of returning fake success.

### Refactor opportunities
- Drive dispatch() from a static table of (number, name, handler-fn) so syscall_name() can't drift from the routing and mis-routes like lchown==chown become visible; this also shrinks mod.rs.
- Replace all hand-rolled offset writers in abi.rs with #[repr(C)] structs + a single checked copy_to_user_bytes, eliminating the getdents underflow class of bug and the fragile fixed-offset arithmetic.
- Introduce one mandatory user-access discipline: syscalls validate the full buffer with is_user_range_accessible up front, and only copy_user_bytes/copy_to_user_bytes touch user memory — forbid raw *ptr stores outside those helpers.
- Extract the futex implementation into its own module with a proper per-page-directory wait-queue keyed on (pd,uaddr) and an atomic block-under-token primitive in the scheduler, reused by poll/select/epoll/sigsuspend/pause to convert busy-spins into real blocking.
- Reference-count address spaces (page directories) so execve and exit free them deterministically, removing the 'retain old pd to avoid cross-CPU UAF' leak in loader/linux.rs.
- Unify LXE positional reads (pread, mmap-fill, sendfile, copy_file_range) onto one coherent VFS primitive that always flushes writers and reads through a correctly-invalidated block cache, then add the regression test.
- Split the five oversized files along syscall-family lines (see key_files split_suggestions).

### Test gaps
There are no automated tests for the LXE ABI; correctness is validated only by booting real Linux binaries (apt/dpkg/bash) under QEMU per the memory note. Concretely untested and testable: (1) wait4 status encoding — a kunit/headless test could fork a child, kill it with each signal, and assert the returned status decodes to WIFSIGNALED/WTERMSIG correctly (this would have caught the critical wait4 bug). (2) Futex wait/wake under contention — a stress test spawning N clone-threads doing FUTEX_WAIT/FUTEX_WAKE ping-pong on shared words, asserting no lost wakeups, runnable headless over serial. (3) pread/mmap read-after-write coherence — extend vfsstress (already used per memory note) to write a multi-MiB file on fd A and pread it at non-sector-aligned offsets on fd B, byte-comparing, to lock down the exFAT/block-cache corruption regression. (4) getdents reclen/padding — a unit test feeding directory names of lengths that hit reclen==19+name to prove no usize underflow in the pad write_bytes. (5) Struct-layout golden tests — compare write_linux_stat/statx output bytes against captured real-Linux struct dumps. (6) mprotect — map RW, mprotect to PROT_NONE, assert a subsequent access faults (would catch the no-op mprotect). (7) Path resolve cache invalidation — create a path natively (outside LXE), assert LXE no longer returns cached ENOENT. Most of these can run as kunit-style kernel tests driven over the headless serial console without GUI, since LXE is pure kernel logic plus VFS.

### Open questions
1) Does the scheduler currently store any discriminator distinguishing 'exited(code)' from 'killed(signal)'? I found only a single u32 exit_code field with signals stored AS the code (lifecycle.rs Some(9)/Some(139)/Some(signal)); confirming there is no separate flag would make the wait4 fix require a scheduler struct change. 2) Is the apt/exFAT corruption fully a block-cache layer bug (per memory note) or does LXE's split read vs read_at flush logic also contribute on the write side? The write path (io.rs linux_write → sys_write → vfs::write with exFAT append buffer) was not deeply audited here. 3) Whether any guest currently exercises MAP_SHARED writable (would immediately ENOSYS) — prioritization of the mmap rework depends on which binaries the user targets (apt/dpkg vs full glibc test suite). 4) The aarch64 branches in loader/linux.rs (exec image replacement) appear partially wired but LXE is x86_64-only per load_and_run_with_args_stdio guard — is ARM64 LXE in scope at all, or dead code to remove?

## LXE-USER — LXE userspace tooling (liblxecore, lxed daemon, lxe/lxediag CLIs, lxemanager/lxeshell apps, host tests)

**Architecture:** LXE ("Linux Experience Extension") is anyOS's in-process Linux ELF64 personality (not a VM). The userspace side splits into: (1) `liblxecore` — the shared core library that creates/repairs the Debian rootfs, downloads/parses the apt Packages index, resolves dependency closures, downloads .deb archives, extracts data.tar.{gz,xz}, writes dpkg status/marker DBs, and spawns Linux processes via `process::lxe_spawn`; (2) `lxed` — a singleton daemon that serializes rootfs access via a text line-protocol over a named pipe (`BEGIN_RUN/END_RUN`, `BEGIN_WRITE/END_WRITE`, `TRACK_PROCESS`, `STATUS`, `SYNC`) and `fs::sync()`s the rootfs when idle; (3) thin clients: `bin/lxe` (CLI), `bin/lxediag` (standalone HTTP byte-path diagnostic that re-implements its own HTTP client), `apps/lxemanager` (GUI installer driving `manager.rs` from a worker thread via static atomics + static-mut text buffers), `apps/lxeshell` (GUI terminal that pipes to `lxe shell --pty-bridge`). Config lives in confd (`services/lxe` manifest) with built-in defaults in `config.rs`.

The dominant architectural problem is `package.rs` at 2834 lines: it is a god-file that mixes at least eight distinct concerns — apt index download/decompress/validate, Packages-paragraph parsing, dependency resolution (two near-identical recursive resolvers), parallel wget prefetch job scheduling, libhttp/wget download with retry/fallback, .deb (ar) + tar extraction with symlink/hardlink materialization, dpkg status.db + info/*.list + installed-marker generation, and package-specific runtime validation. There is no layering between "pure parsing" (testable) and "side-effecting fs/network" code, so the host test harness (`hosttest.rs`) does not test the production code at all — it re-implements `find_package_in_bytes`, `package_info_from_para`, `parse_depends`, `field_value`, `ar_entry`, and verification independently, so the real install/extraction/dpkg-write paths have zero automated coverage.

Global mutable state lives in three places: `package.rs` uses `static mut APT_INDEX_READY` and `static mut DOWNLOAD_LAST_PRINT` (unsynchronized process-global flags); `lxed/state.rs` holds the authoritative lease state (`active_runs`, `active_processes`, `writer_tid`) keyed by raw TIDs; and the GUI apps use `static mut APP` singletons plus `apps/lxemanager/src/state.rs` static-mut byte buffers (`PROGRESS_PHASE_BUF`, etc.) shared between the worker thread and the UI timer thread, with only the *lengths* (not the buffer bytes) guarded by atomics. The rootfs is plain anyOS filesystem content under `/System/var/lxe/rootfs`; there is no real "mount" — lifecycle is create-via-`ensure_rootfs_layout`, repair-via-`repair_rootfs_runtime`, teardown-via-`delete_recursive`. Atomicity of the rootfs as a whole depends entirely on the lxed write-lease being honored, which is cooperative and TID-based.

### Problems
- **[HIGH/file-length/effort:large]** package.rs is a 2834-line god-file mixing 8 unrelated concerns with no layering
    - evidence: libs/liblxecore/src/package.rs spans index download (ensure_apt_index L1099-1237), Packages parsing (package_info_from_para L1394, field_value L1453, parse_depends L1497), TWO near-duplicate recursive resolvers (install_package_inner L425-517 and resolve_package_plan_inner L625-718), parallel wget scheduling (prefetch_packages_with_wget L827-941), download+retry+fallback (download_url* L2497-2639), ar/tar extraction (install_deb L1528-1664, materialize_hardlink* L1716-1784), dpkg DB writing (mark_installed L2042, update_dpkg_status_from_marker L2068, replace_lxe_dpkg_status_record L2173), and per-package runtime validation (validate_*_runtime L1807-1885). Pure parsing is interleaved with fs/network side effects in the same file, preventing isolation.
    - impact: Hard to reason about, test, or modify safely; a change to dependency resolution risks breaking extraction. This is the single biggest contributor to LXE instability being hard to diagnose.
    - fix: Split as described in key_files (index/parse/resolve/download/deb/dpkg/validate submodules). Critically, isolate pure functions (parse/resolve) from I/O so they can be unit-tested in the host harness.
- **[HIGH/lxe/effort:large]** Two divergent dependency-resolution code paths can install different sets
    - evidence: There are two independent recursive resolvers: install_package_inner (package.rs L425-517, used by the serial fallback path in cli.rs bootstrap_rootfs L435 and install_package) and resolve_package_plan_inner (L625-718, used by resolve_install_plan for the plan path). They duplicate the same logic (pre_depends then depends, alternatives via groups, pending stack, depth>32) but differ subtly: the plan resolver pops `pending` BEFORE pushing to plan (L712-715) while the inner installer keeps the package on `pending` across the actual install (L478, popped at L515-516). cli.rs falls back from one to the other (L435 `if !plan_installed`), and manager.rs has its OWN third fallback loop (manager.rs L114-127). hosttest.rs has a FOURTH resolver (resolve_package L88).
    - impact: The set of packages installed by `lxe init` vs the fallback vs the GUI manager can differ, producing inconsistent/partial rootfs states that are exactly the 'container in a bad state' failure mode. Bugs fixed in one resolver are not fixed in the others.
    - fix: Collapse to a single pure `resolve_plan(packages) -> Result<Vec<PackageInfo>, Error>` that all callers (CLI init, apt, manager, hosttest) use. Remove install_package_inner's embedded resolution; let install consume a pre-resolved plan only.
- **[HIGH/lxe/effort:medium]** lxed leases are keyed by raw TIDs that can be reused after exit → false BUSY or premature unlock
    - evidence: lxed/state.rs tracks writer_tid:u32 and Vec<u32> active_runs keyed by caller TID (begin_run L58, begin_write L75). Liveness is checked via threads.rs is_thread_alive which scans sysinfo for a matching entry_tid and returns true if state<=2 (threads.rs L19-22). The kernel recycles TIDs; if a writer crashes and its TID is reused by an unrelated process, cleanup_dead_leases (state.rs L49) will see the TID 'alive' and keep the write lease held, or conversely a new caller with the same TID could be granted a lease it doesn't own. There is no generation/nonce/cookie per lease.
    - impact: Stuck write lease → every later `lxe init/apt/repair` returns BUSY until the 120s LEASE_TIMEOUT (daemon.rs L10) elapses, or a lease is silently stolen, corrupting concurrent rootfs writes. Directly matches the 'no stable LXE' and 'freezes' reports.
    - fix: Issue an opaque lease token (monotonic u64 cookie) on BEGIN_*; require it on END_*/TRACK. Verify (tid,cookie) pair against a /proc-style start-time so a reused TID is distinguishable. Add an explicit lease TTL the daemon reclaims regardless of liveness heuristics.
- **[HIGH/lxe/effort:medium]** Reply-pipe name collides across nested lxed requests from the same PID, racing on responses
    - evidence: daemon.rs request() derives the reply pipe name solely from process::getpid(): `let reply_name = format!("lxed-{}", tid)` (L115). lxed sends the response to `lxed-<tid>` (protocol.rs send_reply L99). During `lxe init`, the same process holds a write lease and then issues further requests (track_process/untrack_process for each spawned Linux process — cli.rs L630/L639) all reusing the SAME pid-derived reply pipe. request() even closes a pre-existing pipe of that name before recreating it (daemon.rs L116-120), so an in-flight reply for a prior command can be dropped or read by the wrong call.
    - impact: Lost/mismatched daemon replies cause spurious timeouts (8s REQUEST_TIMEOUT each, daemon.rs L9) and 'lxed returned malformed status', stalling init/apt. Concurrent lxe invocations from forked children sharing a pid namespace amplify this.
    - fix: Make reply-pipe names unique per request (pid + monotonic counter or a UUID-ish nonce). Do not unconditionally close/recreate a same-named pipe. Consider a request-id echoed in the response so the client can match reply to request.
- **[MEDIUM/lxe/effort:medium]** lxed reads requests into a fixed 1024-byte buffer with no cross-read line reassembly
    - evidence: main.rs reads into `let mut buf = [0u8; 1024]` (L56) and handle_requests (protocol.rs L23-47) splits the single read on '\n', dispatching any trailing partial fragment after the last newline immediately (L42-45 `if line_start < data.len()`). There is no buffering of an incomplete final line until the next read. If a client write is split across two pipe reads (or two clients interleave writes into the shared `lxed` pipe), a command line is fragmented and handle_single_request silently drops it (no '\t' → return at protocol.rs L53).
    - impact: Under load or with concurrent clients, valid commands are silently dropped, causing client-side 8s timeouts and apparent daemon hangs. The shared single request pipe has no framing/locking between writers.
    - fix: Maintain a persistent partial-line buffer in RuntimeState across reads; only dispatch complete '\n'-terminated lines, retaining the remainder. Better: frame requests length-prefixed, or give each client its own request channel.
- **[HIGH/lxe/effort:medium]** dpkg status writes are non-atomic and O(n^2), risking a corrupt status DB on interruption
    - evidence: update_dpkg_status_from_marker (package.rs L2068-2094) reads the whole /var/lib/dpkg/status, rebuilds it paragraph-by-paragraph, and write_bytes_atomic's the result — for EVERY package installed (called from mark_installed L2064). For N bootstrap packages this re-reads+rewrites the growing status file N times (O(n^2) I/O). sync_dpkg_status (L261-308) does the same scan-and-rewrite again. replace_lxe_dpkg_status_record (L2173) re-parses by splitting on "\n\n", which is fragile if any field value contains a blank-line-like sequence. While write_bytes_atomic itself is atomic, the broader 'install a package' operation (extract files + write marker + rewrite status + write .list) is NOT a transaction.
    - impact: A crash/power loss between extracting payload and rewriting status leaves files on disk but no status entry (or vice-versa) — exactly the 'rootfs in a bad state' problem. The O(n^2) rewrite also slows bootstrap (perf #9).
    - fix: Accumulate all status records in memory during a bootstrap/apt run and write the status DB once at the end under the write lease. Make 'mark installed' a single atomic step ordering: write payload+fsync → write marker → (batch) status. Avoid "\n\n" splitting; parse paragraphs by leading-column field detection.
- **[HIGH/stability/effort:small]** manager::delete_rootfs recursion has no depth limit and follows directory entries without symlink guard
    - evidence: manager.rs delete_recursive (L420-449) recurses on entry_type==FS_TYPE_DIRECTORY using fs::readdir, with NO depth guard (contrast scan_tree L384 which caps depth at 24, and rootfs.rs remove_tree L236 which caps at 32 and uses lstat to avoid following symlinks). delete_recursive uses readdir (follows symlinks for stat in many VFS impls) and never lstat-checks, so a symlink-to-directory inside the rootfs (LXE installs many) could be descended into and its TARGET unlinked. A symlink loop or a deep tree could overflow the kernel stack.
    - impact: Deleting the LXE rootfs from the GUI can delete files outside the rootfs (if a package symlink points outside, e.g. /lib64/ld... aliases) or stack-overflow on pathological trees. Data loss / crash.
    - fix: Reuse rootfs::remove_tree (lstat-based, depth-capped, symlink-safe) for deletion instead of a second ad-hoc walker. Add the same `path_under_rootfs` guard that mark_installed/materialize use before any unlink.
- **[MEDIUM/stability/effort:medium]** lxemanager worker thread and UI thread share static-mut text buffers without memory synchronization on the bytes
    - evidence: apps/lxemanager/src/state.rs declares `pub static mut PROGRESS_PHASE_BUF/DETAIL_BUF/ERROR_BUF`. The worker thread writes the bytes in write_progress_text (L112-121) then stores only the LENGTH atomically (PROGRESS_PHASE_LEN). The UI timer thread reads the bytes in read_static_text (ui.rs L454-476) guarded only by the atomic length load. There is no Acquire/Release fence ordering the buffer-byte writes relative to the length store across threads, and the reader can observe a new length over stale/torn bytes. worker.rs also `core::mem::forget`s the thread handle (L11), so a still-running worker outlives a closed window.
    - impact: Torn/garbled progress and error strings, and from_utf8 mid-codepoint splits (handled by unwrap_or("")) hide real errors. The forgotten thread can keep writing to freed static buffers after the UI thread/process tears down.
    - fix: Use a single seqlock pattern (write seq odd→bytes→len→seq even) or guard the whole buffer+len behind a spinlock/Mutex. Join or signal-stop the worker on window close instead of mem::forget; gate worker writes on a still-active flag.
- **[MEDIUM/lxe/effort:small]** Process-global `static mut APT_INDEX_READY` causes stale-cache decisions and is unsound across threads
    - evidence: package.rs L23 `static mut APT_INDEX_READY: bool`, set/cleared via unsafe in apt_index_ready/set/clear (L1083-1097). It is a per-process flag, but the actual index lives on disk in the shared rootfs cache managed by lxed across multiple lxe processes. One process setting READY does not reflect another process clearing/refreshing the on-disk index; and ensure_apt_index trusts the flag first (L1100) then re-validates on disk (good), but the GUI manager worker thread and any future multi-threaded use share the same non-atomic static.
    - impact: Cross-process index staleness can cause a package lookup to use a flag that says 'ready' while another lxe run replaced the index; and the unsynchronized static is technically UB under threads.
    - fix: Drop the in-memory flag and rely on the cheap on-disk validation (looks_like_plain_packages_index + required-entry check), or move 'index ready' state into lxed (single owner of the shared cache). At minimum use AtomicBool.
- **[HIGH/testing/effort:large]** Host test harness does not exercise any production install/extract/dpkg code
    - evidence: tools/lxe-hosttests/src/main.rs calls liblxecore::hosttest::run_full_download_test, and hosttest.rs (L146-354) re-implements find_package_in_bytes, package_info_from_para, field_value, parse_depends, provides_package_bytes, preferred_package, ar_entry, verify_deb, verify_deb_payload as private copies. The production equivalents in package.rs (cfg-gated out under `host`, see lib.rs L19-24 `#[cfg(not(feature="host"))] mod package`) are never compiled or called in tests. The only real production code shared is config.rs/model.rs.
    - impact: The most failure-prone code (extraction, symlink/hardlink materialization, dpkg status/marker generation, runtime validation, lease protocol) has zero automated coverage. Regressions in the real install path ship undetected — a primary cause of 'no stable LXE'.
    - fix: After extracting pure modules (parse/resolve/deb-ar/dpkg-record) so they don't depend on anyos_std fs syscalls, compile them under the `host` feature and have hosttest assert the REAL parser/resolver/ar-extractor against the live index. Add a kunit/serial smoke test that runs `lxe init` headless and asserts bootstrap-state == complete.
- **[MEDIUM/stability/effort:medium]** Daemon STOP and any panic in lxed silently drops all in-flight leases with no client recovery
    - evidence: protocol.rs dispatch handles "STOP" => process::exit(0) (L91-93). RuntimeState lives only in lxed's heap; on exit/crash all lease bookkeeping is lost. main.rs has no panic catch and the main loop (L57-62) calls handle_requests then sleeps 25ms — a panic in any handler (e.g. an alloc failure inside RuntimeState::reload→LxeConfig::load→confd) takes down the daemon. Clients (daemon.rs ensure_daemon L162) will try to restart via `svc start lxed`, but any holder of a RuntimeLease still believes it holds a lease (RAII Drop sends END_* to a fresh daemon that never granted it).
    - impact: A daemon restart mid-operation leaves the rootfs un-synced (END_WRITE→sync never reaches the new daemon) and lease accounting permanently wrong until all clients exit. Partial writes are not flushed → corruption risk.
    - fix: Persist minimal lease/sync intent to disk (or have lxed fsync on every END regardless of accounting). On client side, detect daemon-restart (pipe id change / sequence reset) and fail the operation loudly rather than assuming the lease survived. Wrap the daemon main loop so a handler panic is logged and the daemon re-publishes 'failed' health instead of dying.
- **[MEDIUM/lxe/effort:medium]** Incomplete .deb extraction leaves partial payload before failing; no rollback of already-written files
    - evidence: install_deb (package.rs L1528-1663) extracts each file atomically (write_bytes_atomic) but on the first failed entry sets complete=false and CONTINUES the loop (L1607-1611), then after the loop returns false (L1640-1644) WITHOUT removing the files it already wrote. mark_installed is correctly skipped on failure, and is_installed later re-validates the marker, but the orphaned payload files remain. validate_installed_package only checks a hardcoded subset of packages (coreutils/libc6/libpam0g/keyring, L1797-1805); all other packages are accepted if at least one file extracted.
    - impact: A failed package install pollutes the rootfs with partial files that the next `lxe apt install` won't clean (only the marker is missing). Over repeated failed attempts the rootfs accumulates inconsistent state — the 'bad state' the daemon is supposed to prevent.
    - fix: Track written paths and unlink them on extraction failure (or extract into a staging dir and rename-into-place only on full success). Generalize validation beyond the hardcoded package list, or drop the special-casing in favor of manifest-existence checks already in installed_manifest_valid.
- **[LOW/architecture/effort:medium]** lxediag re-implements an entire HTTP/1.0 client instead of reusing libhttp_client
    - evidence: bin/lxediag/src/main.rs (506 lines) hand-rolls DNS+TCP, request building, header parsing, content-length handling, tail-retry, and FNV hashing (download L202-293, parse_status L450, parse_content_length L457). package.rs already standardizes on libhttp_client (download_url_with_libhttp L2514). The diagnostic's HTTP path therefore does NOT exercise the same code that real apt downloads use, so it cannot reproduce libhttp-specific download bugs.
    - impact: Diagnostic divergence: lxediag may report 'native net/disk path stable' while the real libhttp path that apt uses is the one failing. Maintenance burden of a second HTTP client.
    - fix: Have lxediag drive the same libhttp_client download path (or a thin wrapper) so the diagnostic and production share code. Keep the write/fsync/readback verification, which is the genuinely useful part.
- **[LOW/stability/effort:medium]** is_thread_alive caps at 256 threads and hardcodes an 80-byte sysinfo ABI
    - evidence: threads.rs L3-4 `THREAD_ENTRY_SIZE=80`, `MAX_THREADS=256`; the buffer is `[0u8; 80*256]` on the stack (20KB) and only the first 256 threads are scanned (L13 loop bound by count but buffer is fixed). The state byte at offset 5 (L21) and 'alive if <=2' are magic numbers tied to a kernel struct with no shared definition. If the system exceeds 256 threads, a tracked process beyond index 256 is reported dead → its lease is reclaimed while it is still writing.
    - impact: On a busy system, lxed can free a write lease out from under a live Linux process, allowing a concurrent writer in and corrupting the rootfs. Also a silent correctness cliff.
    - fix: Query the actual thread count first and size the buffer dynamically (or page through), share the thread-entry layout via a constant in anyos_std, and add an explicit kernel 'is_tid_alive(tid)' syscall instead of scanning the whole table per lease check (also a perf win — this runs on every cleanup_dead_leases).
- **[LOW/lxe/effort:small]** manager scan/delete use the legacy 64-byte readdir that truncates names >55 bytes
    - evidence: manager.rs scan_tree (L388 `[0u8; 64*96]`, name_len min 56 at L400) and delete_recursive (L421) use fs::readdir with 64-byte entries / 56-byte names, while rootfs.rs deliberately switched to fs::readdir_long (264-byte entries, 256-byte names) for clear_apt_list_files (L96) and remove_tree (L246). Debian packages contain paths/filenames longer than 55 bytes (e.g. /usr/lib/x86_64-linux-gnu/... and long doc filenames).
    - impact: scan_tree under-counts/skips long-named files (cosmetic miscount in the GUI), but delete_recursive will FAIL to unlink long-named files, leaving residue after 'Delete Rootfs' — and then ensure_dir_recursive recreates a non-empty rootfs. Inconsistent teardown.
    - fix: Switch both to readdir_long (already used elsewhere) or, for delete, reuse rootfs::remove_tree which already does this correctly.
- **[LOW/architecture/effort:small]** config.rs migration table is a 50-line copy-paste wall re-asserting the same two keys at every version
    - evidence: config.rs LXE_MIGRATIONS (L45-96) repeats `migration_string(N, "apt/index_required_packages_csv", ...)` and `migration_string(N, "bootstrap/packages_csv", ...)` for N=2..11 — eleven near-identical pairs forcing the default CSVs on every bump. This pattern means any future package-set change requires hand-adding another version row, and the intent ('always reset these to current defaults') is obscured by repetition.
    - impact: Maintenance hazard and the source of the schema version churn (manifest version 11). Easy to forget a row and silently keep a stale package set on upgrade.
    - fix: Replace with a single 'reset-to-default on any version change' migration policy for the volatile CSV keys, or a helper that expands the list. Bump the manifest version only when the set actually changes.

### Refactor opportunities
- Unify the four dependency resolvers (install_package_inner, resolve_package_plan_inner, manager fallback loop, hosttest resolve_package) into one pure resolve_plan() used by all callers.
- Extract pure, I/O-free modules from package.rs (parse, resolve, ar/tar, dpkg-record) so the host test harness can drop its ~250 lines of duplicated parsing and test production code directly.
- Move 'apt index ready' and 'rootfs needs sync' state out of process-global static mut and into lxed (the single owner of the shared cache), eliminating cross-process staleness and the unsynchronized statics.
- Replace lxed's TID-keyed leases with opaque lease tokens (cookie + TTL) and add a kernel is_tid_alive syscall to replace the per-check 256-thread sysinfo scan in threads.rs.
- Make package install transactional: stage payload, write marker, batch the dpkg status rewrite once per run (fixes O(n^2) status rewrites and partial-state corruption).
- Have manager delete/scan reuse rootfs::remove_tree (depth-capped, lstat-based, readdir_long) instead of ad-hoc walkers, removing duplication and the symlink-follow data-loss bug.
- Split rootfs.rs (927 lines) into layout/path/fsutil/repair; the hardcoded /etc default-file content is ~400 lines and belongs in a data module.
- Make lxediag drive libhttp_client so the diagnostic exercises the same download path apt uses.
- Replace config.rs's repeated migration rows with a single reset-on-change policy for the volatile CSV keys.
- Factor lxeshell's VT/escape/SGR/screen logic (1034 lines) into modules and ideally share the terminal-emulation core with the existing Terminal app rather than maintaining a second VT implementation.

### Test gaps
There is essentially no test coverage of the real LXE install pipeline. The only automated test (tools/lxe-hosttests via scripts/test-lxe-host.sh → scripts/test-anyrc-host.sh) downloads the live Debian index over real TCP and resolves the bootstrap closure, but it does so with PRIVATE re-implementations in hosttest.rs (find_package_in_bytes, package_info_from_para, parse_depends, field_value, ar_entry, verify_deb_payload, resolve_package) — the production functions in package.rs are cfg-gated out under the `host` feature (lib.rs L19-24) and never compiled or exercised. So: the dependency resolver actually used at runtime, install_deb extraction, symlink/hardlink materialization, dpkg status/marker/.list generation, marker re-validation (is_installed), runtime validation, the lxed lease protocol, the daemon line-protocol framing, and partial-state recovery are ALL untested. The host test also depends on network availability and a magic-number assertion (index.len() < 20_000_000, hosttest.rs L46) that will silently break when Debian's index grows.

Concrete ways to close the gaps: (1) Extract the pure parse/resolve/ar-tar/dpkg-record logic into submodules with NO anyos_std fs/syscall dependencies, compile them under `host`, and replace hosttest's duplicates with calls to the real code (kills the duplication AND tests production). (2) Add table-driven unit tests for: Packages-paragraph parsing (multi-line continuation fields, Provides), parse_depends alternatives/version-constraint stripping, ar_entry odd-size padding, dpkg status record replace/dedup (replace_lxe_dpkg_status_record), and path translation/normalization (normalize_abs_path, path_under_rootfs, resolve_rootfs_symlink_path with loops). (3) Add a headless QEMU serial smoke test that runs `lxe init` non-interactively and asserts <db>/bootstrap-state Status: complete, then `lxe run /bin/true` returns 0 — this is the only way to cover the lease protocol, extraction, and the loader handoff end-to-end. (4) Add a lxed concurrency test: spawn two writers and assert exactly one wins / the loser gets BUSY then succeeds after release, plus a 'kill the writer mid-lease' test to verify the daemon reclaims the lease (currently TID-based and likely flaky). (5) Fuzz/property-test install_deb against synthetic .deb archives with crafted symlink loops, paths escaping rootfs, long names, and a deliberately-failing entry to assert no partial-payload residue and no out-of-rootfs writes.

### Open questions
Does the kernel recycle TIDs quickly enough that the lxed lease TID-reuse race is observed in practice, or is the TID space large enough that it is only theoretical? (Needs a kernel TID-allocation review — out of scope of this audit.) Are named pipes in this kernel single-writer or multi-writer, and do concurrent writers to the shared `lxed` pipe interleave at byte or message granularity? That determines whether the request-framing bug (protocol.rs) is latent or active. Is write_bytes_atomic's rename truly atomic on the underlying exFAT/CoreFS rootfs, or does the known large-block read-after-write cache bug (noted in user memory: lxe-storage-corruption-investigation) undermine the atomicity LXE relies on for dpkg status/marker writes? If the FS cache bug is real, much of the 'rootfs in bad state' instability may originate below liblxecore, not in it.

## DRIVERS-HAL — DRIVERS + HAL (kernel/src/drivers/* and kernel/src/arch/{x86,arm64}/* HAL boundary)

**Architecture:** There are actually TWO disjoint "driver models" in the tree, neither of which is consistently enforced.

(1) The nominal HAL. `kernel/src/drivers/hal.rs` defines a single generic `Driver` trait (name/driver_type/init/read(offset,buf)/write/ioctl) plus a `HalRegistry` keyed by `/dev/...` path string, and `probe_and_bind_all()` walks `crate::drivers::pci::devices()` against a static `PCI_DRIVER_TABLE` (kernel/src/drivers/pci_drivers.rs) of `{PciMatch, factory: fn(&PciDevice)->Option<Box<dyn Driver>>}` entries. This is a clean, table-driven PCI probe/attach mechanism on x86 — the one genuinely good piece of architecture here. BUT the `Driver` trait is a byte-stream abstraction (read/write at a usize offset) that does not fit block, network, GPU, or input semantics, so almost every real driver registers a thin "HalDriver" shim that does nothing (e.g. `StorageHalDriver`, `NetworkHalDriver`) and exposes its real functionality through a SECOND, type-specific global singleton.

(2) The real device models are per-class globals. Storage: free functions `storage::read_sectors/write_sectors` dispatching on a `static mut BACKEND: StorageBackend` enum (mod.rs:74), with each backend (ahci/nvme/lsi/ata) keeping its own `static mut AHCI`/`static mut CTRL` controller. There is no `BlockDevice` trait object — `blockdev.rs` `BlockDevice` is a plain struct that calls back into the free functions. GPU: a real `GpuDriver` trait behind `static GPU: Mutex<Option<Box<dyn GpuDriver>>>` (gpu/mod.rs:604) with a `with_gpu()` accessor that defensively validates the trait-object vtable pointer on every call and supports a "poisoned" state. Network: a real `NetworkDriver` trait behind `static NET: Spinlock<Option<Box<dyn NetworkDriver>>>` (network/mod.rs:52) but RX is explicitly NOT routed through the trait — drivers poll/IRQ on their own `static *_STATE` singleton. So there are three different lifecycle/ownership conventions (free-fn+enum, Box<dyn> behind Mutex, Box<dyn> + side singleton) for three device classes.

The x86/aarch64 HAL boundary (arch/hal.rs) is clean for CPU/timer/IRQ-controller/page-table/FPU primitives — these are well-abstracted free functions with cfg-gated bodies. But the DRIVER layer does not use it: the entire aarch64 device stack is a parallel universe (`drivers/arm/*`, `storage_arm64.rs`, `network_arm64.rs`, `boot/arm64/mod.rs`) that re-implements the VirtIO transport, virtqueue, GPU, block, and input drivers from scratch with hand-written dispatch (`match dev.device_id() { 2=>blk, 16=>gpu, 18=>input }` in boot/arm64/mod.rs:69) and does NOT touch hal.rs `Driver`, the PCI table, or the x86 `drivers/virtio` code. The arm/ module comment literally says "zero interaction with the x86-specific drivers". Per-driver MMIO is hardcoded to fixed kernel-higher-half VAs (AHCI 0xFFFF_FFFF_D006_0000, E1000/SVGA each their own) with manual `virtual_mem::map_page`, and IRQ unmasking is copy-pasted (`if apic::is_initialized(){ioapic::unmask_irq}else{pic::unmask}`) into 12 driver files, reaching directly into `arch::x86::{apic,ioapic,pic}` with no HAL `irq_unmask()`.

Global mutable state is pervasive: 29 `static mut` in drivers/. The storage controllers (`static mut AHCI`, `static mut CTRL`, `static mut SECONDARY_AHCI`) are accessed as `&mut` from worker threads while also read from IRQ handlers, relying entirely on the external `IO_LOCK` in storage/mod.rs for soundness — there is no lock inside the driver itself.

### Key files
- `kernel/src/drivers/hal.rs` (526 lines) — The HAL: generic Driver trait + path-keyed registry + x86 PCI probe_and_bind_all(). Driver trait is byte-stream shaped, doesn't fit block/net/gpu/input.
- `kernel/src/drivers/pci_drivers.rs` (604 lines) — Static PCI_DRIVER_TABLE wiring vendor/device + class matches to per-driver probe() factories. The cleanest abstraction in the subsystem.
- `kernel/src/arch/hal.rs` (765 lines) — x86/arm64 CPU/timer/IRQ-ctrl/page-table/FPU primitives, cfg-gated. Clean except it stops at the device layer and contains an in-tree RBP-corruption diagnostic panic in set_kernel_stack_for_cpu (lines 251-307).
- `kernel/src/drivers/storage/mod.rs` (1165 lines) — Block storage dispatch: static mut BACKEND enum, IO_LOCK serialization, adaptive readahead, readahead buffer pool. No BlockDevice trait.  **[SPLIT]** Split into backend_dispatch.rs (read/write_sectors_raw + BACKEND), io_lock.rs (IO_LOCK + diagnostics), readahead.rs (pool + adaptive logic), cache_glue.rs (blockcache overlay/populate).
- `kernel/src/drivers/storage/ahci.rs` (2648 lines) — AHCI driver: static mut AHCI controller, multi-slot command engine, IRQ/MSI completion, port recovery, bounce buffers, ATAPI, secondary controllers. NCQ disabled.  **[SPLIT]** Split into ahci/regs.rs (register/struct defs), ahci/port.rs (start/stop/recover), ahci/command.rs (issue/wait/slot mgmt), ahci/irq.rs (handler+hotplug), ahci/atapi.rs, ahci/init.rs (probe/identify/secondary).
- `kernel/src/drivers/storage/nvme.rs` (1148 lines) — NVMe driver: static mut CTRL accessed as &mut without internal lock; fully polled completion (io_wait_completion spins 10M iters); IO queue depth only 8; single I/O queue.  **[SPLIT]** Split into nvme/queues.rs, nvme/admin.rs, nvme/io.rs, nvme/init.rs; and replace polled completion with IRQ-driven completion.
- `kernel/src/drivers/storage/async_io.rs` (526 lines) — Async block I/O scheduler: 2 worker threads, priority queue, prefetch merging. Decent design but executes via the same synchronous backend + IO_LOCK underneath.
- `kernel/src/drivers/gpu/mod.rs` (944 lines) — GpuDriver trait + Mutex<Box<dyn>> singleton with vtable-corruption validation and 'poisoned' recovery state — strong evidence of recurring heap corruption of the driver box.  **[SPLIT]** Move splash-cursor IRQ logic and output/rotation helpers into submodules; keep the trait + registry in mod.rs.
- `kernel/src/drivers/gpu/virtio_gpu.rs` (3191 lines) — VirtIO GPU 2D+3D(virgl) driver, single struct VirtioGpu with ~80 fields and all command builders inline.  **[SPLIT]** Split into virtio_gpu/cmds.rs (repr(C) command structs), virtio_gpu/cursor.rs, virtio_gpu/scanout.rs, virtio_gpu/virgl3d.rs, virtio_gpu/transport.rs.
- `kernel/src/drivers/usb/xhci.rs` (1359 lines) — xHCI controller, fully POLLED (CMD_INTE kept clear, comment line 91), single command/event ring. No IRQ-driven transfer completion.  **[SPLIT]** Split into xhci/ring.rs, xhci/control.rs (control transfers), xhci/event.rs, xhci/init.rs; add interrupter-driven event handling.
- `kernel/src/drivers/arm/mod.rs` (346 lines) — ARM64 VirtIO MMIO transport — full reimplementation of init_device/setup_queue/notify/ack, duplicating drivers/virtio/mod.rs.
- `kernel/src/drivers/network/e1000.rs` (817 lines) — E1000 NIC; e1000_irq_handler (line 740) calls process_rx_ring which does Vec::with_capacity heap alloc in IRQ context despite a comment claiming it avoids that.  **[SPLIT]** Acceptable length; main issue is correctness not size.
- `kernel/src/arch/x86/irq.rs` (105 lines) — Dynamic IRQ handler table; only 2 handlers per line (primary + chained) — insufficient for >2 devices sharing a legacy PCI IRQ.
- `kernel/src/arch/x86/idt.rs` (2356 lines) — IRQ/exception dispatch. Timer ISR runs per-tick TSS.RSP0 / PERCPU.kernel_rsp / stack-canary corruption checks (lines 2181-2273) — diagnostic scaffolding indicating chronic memory corruption.  **[SPLIT]** Split fault-diagnostics (dump/repair) into idt/diagnostics.rs, keep dispatch + frame defs in idt.rs.

### Problems
- **[HIGH/hal-driver/effort:large]** No unified block-device trait; storage is dispatched through a global `static mut BACKEND` enum
    - evidence: kernel/src/drivers/storage/mod.rs:67-74 defines `enum StorageBackend{Ata,Ahci,Nvme,LsiScsi}` and `static mut BACKEND`. read_sectors_raw_for_disk (mod.rs:928-948) and write_sectors_raw_for_disk (mod.rs:1034-1053) `match unsafe{BACKEND}` to call free functions in each backend module. There is no `trait BlockDevice{read_sectors;write_sectors;flush;capacity}` — `blockdev.rs:19` BlockDevice is a partition descriptor struct that calls back into the free functions. The HAL `Driver` shim `StorageHalDriver` (mod.rs:1120-1155) is a no-op that re-derives lba=offset/512 and ignores disk_id entirely.
    - impact: Adding a storage backend means editing a closed enum and four match arms in mod.rs; per-disk routing is bolted on via `disk_id!=0` special-cases and a separate IO_OVERRIDES vector (mod.rs:35). Multiple controllers of the same type can't coexist cleanly (secondary AHCI is a separate `static mut SECONDARY_AHCI` array). The HAL registry can't actually be used to do block I/O.
    - fix: Introduce `trait BlockDevice: Send { fn read(&self, lba:u64, buf:&mut[u8])->Result<(),IoError>; fn write(&self, lba:u64, buf:&[u8])->Result<(),IoError>; fn flush(&self)->Result<(),IoError>; fn capacity_sectors(&self)->u64; fn block_size(&self)->u32; fn supports_parallel(&self)->bool; }`. Each controller registers `Arc<dyn BlockDevice>` instances per physical disk in a registry keyed by disk_id. mod.rs cache/readahead/IO_LOCK becomes a generic wrapper over `Arc<dyn BlockDevice>` instead of a backend enum. This removes the static mut BACKEND, the disk_id special cases, and the IO_OVERRIDES side-channel.
- **[CRITICAL/stability/effort:medium]** NVMe controller is `static mut CTRL` taken as `&mut` with no internal lock — aliasing UB under concurrent I/O
    - evidence: kernel/src/drivers/storage/nvme.rs:145 `static mut CTRL: Option<NvmeController>`; read_sectors (nvme.rs:624) and write_sectors both do `let ctrl = match unsafe{CTRL.as_mut(){..}}` and then mutate queue tails, phase bits, next_cmd_id, and the shared bounce buffer. The two async_io worker threads (async_io.rs:16 WORKER_COUNT=2) both call into this via read_sectors_raw_chunked. Soundness depends entirely on the EXTERNAL `IO_LOCK` in storage/mod.rs being held — but nothing in nvme.rs enforces it, and `flush`/diagnostic paths or any future direct caller would create two live `&mut NvmeController` aliases = undefined behaviour.
    - impact: Latent memory-unsafety: two `&mut` to the same controller (different CPUs) is instant UB in Rust, can corrupt queue head/tail/phase tracking and the doorbell sequence, producing the kind of silent data corruption noted in the LXE/exFAT memory note. AHCI has the same shape (`static mut AHCI`) but at least takes `&` and uses internal atomics for slot tracking.
    - fix: Wrap the controller in `Spinlock<NvmeController>` (or Mutex for the I/O queue) and acquire it inside nvme.rs, not via an unrelated module-level lock. At minimum make the public functions take a guard. Long-term, fold into the proposed `BlockDevice` trait whose impl owns its own lock so correctness is local to the driver.
- **[HIGH/performance/effort:large]** NVMe is fully polled with a 10-million-iteration busy spin and IO queue depth 8
    - evidence: kernel/src/drivers/storage/nvme.rs:297-310 io_wait_completion spins `for spin in 0..10_000_000`, only yielding every 256 iterations, and on exhaustion logs 'I/O command timeout'. Completion is via phase-bit polling (io_poll_completion nvme.rs:280) — there is no MSI/IRQ completion handler registered for NVMe at all. IO queue is a single SQ/CQ pair with `NVME_IO_QUEUE_DEPTH=8` (nvme.rs:157) and `IO_QUEUE_SIZE` admin-sized small.
    - impact: NVMe — the fastest storage HW — runs slower and burns more CPU than AHCI here: a single device with no interrupt completion, depth 8, and a busy-poll that pegs a core. On real NVMe SSDs this caps throughput far below the device and starves other threads (problem #9 IO perf). The 10M spin can also wedge a worker for a long time on a slow/failed command before the timeout.
    - fix: Register an MSI-X completion handler (NVMe always supports MSI-X) that flips a per-command completion and wakes the waiter, mirroring the AHCI interrupt-driven path (ahci.rs:907 wait_for_interrupt_completion). Increase IO_QUEUE_DEPTH (≥64), and use one I/O queue per CPU with per-CPU doorbells to remove cross-CPU serialization. Replace the bounded spin with a sleep-on-completion that has a tick-based timeout like AHCI.
- **[MEDIUM/performance/effort:medium]** xHCI is fully polled — no interrupt-driven transfer completion
    - evidence: kernel/src/drivers/usb/xhci.rs:91 `const CMD_INTE: u32 = 1<<2; // Interrupter enable (we keep this clear — polled)`. The event ring is drained by polling (xhci.rs event-ring helpers), and there is a single command ring + single event ring (header comment lines 39-46).
    - impact: USB HID (keyboard/mouse) and USB mass storage latency/throughput depend on a polling cadence; under load this adds input lag and slow USB disk I/O, and consumes CPU polling the event ring. Combined with EHCI/UHCI also present, the USB stack has three large polled drivers (xhci 1359, ehci 1041, uhci 1053).
    - fix: Enable the xHCI primary interrupter (set IMAN.IE + CMD_INTE, register an MSI handler) and signal transfer completions from the event-ring handler to wake the submitting thread. Keep a polled fallback only when MSI is unavailable.
- **[HIGH/stability/effort:medium]** E1000 IRQ handler allocates heap memory in interrupt context
    - evidence: kernel/src/drivers/network/e1000.rs:740 e1000_irq_handler -> process_rx_ring (e1000.rs:687) which does `let mut packet = Vec::with_capacity(length)` (e1000.rs:703) for each received frame, inside the IRQ handler under `E1000_STATE.try_lock()`. A comment at e1000.rs:769-771 claims the handler avoids Vec allocation in IRQ context, but process_rx_ring (invoked at e1000.rs:762) does exactly that.
    - impact: If the interrupted thread happened to hold the global heap allocator lock, the IRQ handler's Vec allocation deadlocks the CPU. This is a classic IRQ-context allocator deadlock and a plausible source of the freezes in problem #3. The try_lock on E1000_STATE avoids the device-lock deadlock but not the allocator-lock one.
    - fix: In IRQ context only set a 'RX pending' flag / advance the ring tail with NO allocation, and do the Vec copy + ethernet::handle_frame in a bottom-half (the existing poll_rx_into path or a softirq worker thread). Pre-allocate a fixed pool of RX buffers at init and hand out indices from the IRQ. This matches the pattern the comment claims to follow.
- **[MEDIUM/hal-driver/effort:small]** Legacy shared PCI IRQ supports only 2 handlers per line
    - evidence: kernel/src/arch/x86/irq.rs:14-23 has exactly one IRQ_HANDLERS slot and one IRQ_CHAIN slot per line; register_irq (irq.rs:31) claims primary then chain then logs 'cannot register more' (irq.rs:59) and returns false. AHCI/E1000/audio/etc. each fall back to legacy IRQ via register_irq_chain when MSI is unavailable.
    - impact: On real hardware where INTx# pins are routed so 3+ devices share one legacy IRQ (common before MSI), the third device's interrupts are silently dropped — its driver then relies on its polling fallback or hangs waiting for a completion that never wakes it. Contributes to flaky bring-up on physical machines.
    - fix: Replace the fixed primary+chain pair with a small `Vec`/array list of handlers per IRQ line (lock-free append at init time), and call every registered handler in dispatch_irq. Or require MSI/MSI-X for all DMA-capable devices and treat legacy INTx as a fallback that genuinely chains N handlers.
- **[HIGH/hal-driver/effort:large]** The HAL `Driver` trait is a byte-stream that doesn't model any real device class
    - evidence: kernel/src/drivers/hal.rs:104-117 trait Driver has read(offset:usize,buf)/write(offset,buf)/ioctl(cmd:u32,arg:u32). Storage shoehorns lba=offset/512 (mod.rs:1135) and ignores disk_id; NetworkHalDriver read returns NotSupported and write transmits raw bytes (network/mod.rs:174-184); GPU does not register through Driver at all (uses GpuDriver). Real per-class behaviour lives in GpuDriver (gpu/mod.rs:106), NetworkDriver (network/mod.rs:24), and storage free functions.
    - impact: The 'unified driver model' is unified in name only: it can list devices and route ioctls by type, but cannot perform class-appropriate operations, so every subsystem invents its own registry. Three ownership conventions (free-fn+enum, Box<dyn> in Mutex, Box<dyn>+side singleton) make lifecycle, hot-unplug, and crash recovery inconsistent across classes.
    - fix: Make `Driver` an enum-of-traits or have the registry store a `DeviceClass` enum wrapping `Arc<dyn BlockDevice>` / `Arc<dyn NetDevice>` / `Box<dyn GpuDriver>` / `Box<dyn InputDevice>` / `Box<dyn CharDevice>`. The PCI probe table already returns these per-class objects; the registry should keep them typed instead of flattening to the byte-stream Driver. ioctl/read/write at the syscall layer then dispatch to the class.
- **[HIGH/hal-driver/effort:xl]** aarch64 device stack is a full parallel reimplementation, not the HAL/PCI model
    - evidence: kernel/src/drivers/arm/mod.rs:1-19 declares a self-contained VirtIO MMIO transport + virtqueue duplicating drivers/virtio/* (arm/virtqueue.rs 334 lines vs virtio/virtqueue.rs 540; arm/gpu.rs 968 vs gpu/virtio_gpu.rs 3191). boot/arm64/mod.rs:69-74 hand-dispatches `match dev.device_id(){2=>blk::init,16=>gpu::init,18=>input::init}`. storage_arm64.rs and network_arm64.rs are separate front-ends; fs/* calls `drivers::arm::storage::read_sectors` directly (fs/exfat.rs:29, fs/fat/mod.rs:219). None of this goes through hal.rs Driver, pci_drivers.rs, the block cache/async_io, or the storage IO_LOCK.
    - impact: Two divergent driver worlds doubles maintenance, and the ARM path misses everything the x86 path gained (block cache, async I/O, readahead, retry, bounds checks). Bug fixes (e.g. the large-block read-after-write cache corruption in the memory note) only land on one arch. The 'HAL' does not actually abstract drivers across arch.
    - fix: Factor the VirtIO core (device handshake, virtqueue, descriptor mgmt) into an arch-neutral crate parameterized over a transport trait (`VirtioTransport` with read_reg/write_reg/notify/ack + DMA alloc), with PCI and MMIO transports as the two impls. ARM block I/O should register a `BlockDevice` so it inherits the cache/async/readahead path. Route MMIO discovery through a DTB-driven equivalent of probe_and_bind_all that produces the same per-class objects.
- **[MEDIUM/hal-driver/effort:small]** Drivers reach directly into arch-specific interrupt-controller code; IRQ-unmask logic copy-pasted across 12 files
    - evidence: grep shows 12 driver files call `crate::arch::x86::apic::is_initialized()` + `ioapic::unmask_irq()`/`pic::unmask()` directly (ahci.rs:1911-1915, e1000.rs:425-429, igc.rs:287, rtl8125.rs:250, rtl8168.rs:294, iwl_wifi.rs:217, audio/hda.rs:680, audio/ac97.rs:271, gpu/vmware_svga.rs:1455, virtio/input.rs:909, virtio_net.rs:488, serial.rs:386). The arch HAL (arch/hal.rs) exposes irq_eoi/send_ipi but has NO irq_unmask/register_irq, so drivers bypass it. ARM drivers similarly call arch::arm64::{gic,exceptions} directly (arm/input.rs:244, network_arm64.rs:362).
    - impact: Every new NIC/audio/storage driver duplicates the same 5-line apic-vs-pic block; a fix (e.g. to handle a third interrupt controller, or MSI-only platforms) must be applied 12+ times. Drivers are not arch-portable because they hardcode x86 interrupt-controller calls.
    - fix: Add `arch::hal::irq_register(irq:u8, handler)`, `arch::hal::irq_unmask(irq:u8)`, `arch::hal::irq_mask(irq:u8)` with x86 (apic/ioapic/pic) and arm64 (gic) bodies. Replace all 12 inline blocks with `hal::irq_unmask(irq)`. This is the single highest-leverage HAL cleanup.
- **[HIGH/stability/effort:large]** GPU driver box requires per-call vtable validation and a 'poisoned' recovery state — symptom of chronic heap corruption
    - evidence: kernel/src/drivers/gpu/mod.rs:35-68 validate_gpu_vtable transmutes the &dyn GpuDriver fat pointer and checks both data and vtable pointers are in higher-half, dumping over raw serial and SKIPPING the call if not. with_gpu (mod.rs:698-718) runs this check on EVERY GPU call and stores LAST_GPU_DRIVER_* for crash diagnostics; force_unlock_gpu (mod.rs:754) + GPU_POISONED disable the GPU after a crash. idt.rs:1013 calls force_unlock_gpu from the fault handler. The timer ISR also runs per-tick TSS.RSP0/PERCPU.kernel_rsp/stack-canary checks (idt.rs:2181-2273) and arch/hal.rs:251-307 has an RBP-corruption panic guard.
    - impact: This much defensive scaffolding means the team is repeatedly hit by corruption of the Box<dyn GpuDriver> heap allocation and kernel stacks (problems #3 fragile compositor and #7). The validation hides the symptom (skips the call, blanks the screen) rather than fixing the cause; it also adds a transmute + branch to every GPU op on the compositor hot path.
    - fix: Root-cause the corruption rather than guard it: (a) move the GPU driver state out of a heap Box into a statically-allocated arena or a pinned allocation that can't be freed/reused, (b) audit the IRQ-context allocations (see E1000 finding) and the kernel stack overflow guard hits, (c) once stable, demote validate_gpu_vtable to a debug_assert. Keep poisoning only as a last-resort fault path.
- **[MEDIUM/file-length/effort:large]** AHCI/storage giant files concentrate unrelated concerns; storage NCQ permanently disabled
    - evidence: ahci.rs is 2648 lines mixing register defs, slot allocator, command issue, two completion paths, port recovery, ATAPI, hot-plug, and secondary-controller init. virtio_gpu.rs 3191 lines is one struct VirtioGpu with ~80 fields and all command builders inline. storage/mod.rs 1165 lines mixes backend dispatch, IO_LOCK + diagnostics, readahead pool, and cache glue. AHCI_ENABLE_NCQ=false (ahci.rs:72) and supports_parallel_io() (ahci.rs:2482) gate the whole multi-slot path off, so all AHCI I/O serializes through IO_LOCK despite the elaborate slot machinery.
    - impact: These are the largest, hardest-to-review files in the kernel; the AHCI command/recovery interplay (AHCI_RECOVERY flag + slot mask + IRQ-fired bits) is subtle and untested, and because NCQ is disabled the multi-slot code paths are effectively dead weight that still has to be reasoned about. Serialized AHCI is a real IO-throughput ceiling (problem #9).
    - fix: Split per the file table (ahci/{regs,port,command,irq,atapi,init}.rs, virtio_gpu/{cmds,cursor,scanout,virgl3d}.rs, storage/{backend,io_lock,readahead,cache_glue}.rs). Separately, write a vfsstress/kunit-style AHCI NCQ stress test (the CLAUDE note says NCQ is off until 'an explicit stress test' exists) so the multi-slot path can be enabled and AHCI stops serializing.
- **[LOW/hal-driver/effort:medium]** Secondary AHCI controllers register the primary-only MSI handler; their completions can't wake waiters
    - evidence: ahci.rs:2200-2203 a secondary controller calls `register_msi_handler(vec, ahci_msi_handler)`, but ahci_msi_handler (ahci.rs:653) -> ahci_irq_handler (ahci.rs:558-564) only does `unsafe{AHCI.as_ref()}` (the PRIMARY controller) and ignores SECONDARY_AHCI entirely. Secondary I/O therefore relies on polled completion via issue_command_on_port.
    - impact: Low impact today because secondary disks use the polled path, but the MSI is registered for nothing and a future move of secondary disks to interrupt completion would silently never wake. It also means a secondary controller's error/hot-plug interrupts are acked against the wrong base or not at all.
    - fix: Give the IRQ/MSI handler access to a list of controllers (primary + secondaries) and dispatch by matching the MMIO base / interrupt status, or register a distinct handler per controller carrying its index. Tie this into the BlockDevice refactor so each controller is a first-class object with its own completion routing.
- **[MEDIUM/hal-driver/effort:medium]** Per-driver hardcoded MMIO virtual addresses with manual page mapping
    - evidence: ahci.rs:14 AHCI_MMIO_VIRT=0xFFFF_FFFF_D006_0000, ahci.rs:231 AHCI_SECONDARY_MMIO_VIRT=0xFFFF_FFFF_D006_8000, with manual virtual_mem::map_page loops (ahci.rs:1501-1505, 2090-2094). Comments in the file note the address is chosen 'after E1000 (0xD000_0000) and VMware SVGA FIFO (0xD002_0000)' — i.e. a hand-partitioned MMIO VA space shared by convention across unrelated driver files.
    - impact: MMIO VA assignments are a manual global registry encoded as comments; adding a driver or a second instance of an existing one risks silent VA overlap and is fragile on systems with more BARs than the hardcoded windows anticipate. No bounds checking that a BAR fits the reserved window.
    - fix: Provide a HAL MMIO mapper `hal::map_mmio(phys, len) -> VirtAddr` that allocates from a managed MMIO VA arena and returns the mapping, replacing every per-driver fixed constant. This also lets multiple instances of a controller coexist.

### Refactor opportunities
- Introduce arch::hal::irq_register/irq_unmask/irq_mask and delete the 12 copy-pasted apic-vs-pic blocks across drivers — smallest change, biggest portability win.
- Define trait BlockDevice and register Arc<dyn BlockDevice> per disk; make storage/mod.rs cache+readahead+IO_LOCK a generic wrapper instead of a static-mut backend enum; this also kills IO_OVERRIDES and the disk_id!=0 special-casing.
- Define trait CharDevice and InputDevice so serial, PS/2, virtio-input, USB-HID register through the registry like NetworkDriver/GpuDriver, giving one consistent device model across all 5 classes.
- Extract a transport-agnostic VirtIO core (handshake + virtqueue + DMA) parameterized over a VirtioTransport trait, with PCI and MMIO impls, eliminating the drivers/arm vs drivers/virtio duplication (~880 lines of duplicated virtqueue alone).
- Make NVMe interrupt-driven (MSI-X), multi-queue (per-CPU), and depth>=64; wrap NvmeController in its own lock to remove the static-mut &mut aliasing UB.
- Enable xHCI interrupter and signal transfer completions to waiters instead of polling.
- Split the 4 oversized driver files (ahci 2648, virtio_gpu 3191, storage/mod 1165, nvme 1148, xhci 1359) along the suggested submodule boundaries.
- Add a HAL MMIO VA allocator (hal::map_mmio) to replace hardcoded per-driver MMIO virtual base constants and allow multiple controller instances.
- Once corruption is root-caused, demote the GPU vtable-validation and per-tick TSS/canary checks to debug builds so they stop costing hot-path cycles.

### Test gaps
There is essentially no automated test coverage of the driver/HAL layer. The CLAUDE notes explicitly say AHCI NCQ stays disabled 'until that path has an explicit stress test' (ahci.rs:69-72) — that test does not exist, so the multi-slot/NCQ path is unverified dead code. Concrete, achievable test hooks: (1) A headless-serial / kunit-style storage stress harness that issues randomized overlapping read/write/flush against a RAM-backed BlockDevice impl and a virtio-blk disk under QEMU, asserting read-after-write coherency — this would directly catch the large-block cache corruption already noted in memory and let NCQ be enabled. (2) An async_io scheduler unit test (it is mostly pure logic: pop_best priority ordering, make_room_for prefetch eviction, try_merge_prefetch contiguity) that can run host-side with a mock backend — async_io.rs has no test despite being safety-critical for I/O ordering. (3) A loopback/virtio-net frame round-trip test over QEMU to exercise the e1000/virtio_net RX path off the IRQ (and prove the bottom-half refactor removes IRQ-context allocation). ## VFS-IO — Filesystem / VFS / Block IO (kernel/src/fs/* + kernel/src/drivers/storage/mod.rs block-cache integration)

**Architecture:** The FS subsystem layers three independent caches over a backend-agnostic sector device. (1) A global write-back **block cache** (kernel/src/fs/blockcache.rs, 16384 fixed 512-byte slots = 8 MiB, hash-accelerated LRU, per-disk dirty estimate + write-range guard). (2) Per-driver in-RAM caches: exFAT keeps a 128-slot **cluster cache** (exfat.rs ClusterCache via UnsafeCell), a **directory-lookup cache** (DirLookupCache), and the full **FAT table + allocation bitmap** in RAM with per-sector dirty bitmaps flushed lazily by flush_metadata(). (3) A per-open-file **append buffer** in the VFS layer that coalesces sequential appends. The storage layer (drivers/storage/mod.rs) decides write-back vs direct-to-disk on a single threshold WRITE_BACK_MAX_SECTORS=8: writes <=8 sectors become dirty cache entries; larger writes go direct to disk and then invalidate the cache range. Reads consult the cache (lookup_range, which STOPS at the first miss), fetch misses from disk, then call overlay_cached to re-stamp any dirty write-back sectors back onto the just-read buffer — this overlay-after-read is the linchpin that preserves read-after-write coherence for the dirty write-back cache.

The VFS itself (vfs/mod.rs, 6952 lines) is the single worst file in the tree. A clean `Filesystem` trait exists in vfs/types.rs (read/write/lookup/readdir/create/delete + defaulted metadata/symlink/sync methods, type-erased via as_any), but it is barely used. Instead VFS dispatch is a giant per-syscall if-else chain keyed on magic `file.fs_id` integers (1=DevFs, 2=ISO9660, 3/6=exFAT, 4=NTFS, 7=Overlay, 8=CoreFS, 9=FUSE) — 36 such branch sites. VfsState (vfs/mod.rs:569) holds one *typed* field per filesystem (iso9660_fs, devfs, smbfs, mounted_exfat, overlay_fs, corefs_driver, mounted_corefs, exfat_fs, fat_fs, ntfs_fs, root_other) rather than a uniform mount table of `Box<dyn Filesystem>`; the comment at :589 admits this is to preserve field-level borrow splitting that the legacy dispatch relies on. Each driver also re-implements read/write twice: once for the locked path and once as a lock-free "detached plan" (prepare/execute/finish, ~30 Detached* types/functions) that drops the heavyweight VFS mutex during disk I/O. Global state lives in a single `Mutex<Option<VfsState>>` (VFS, :467) plus the block cache's own Spinlock and per-disk atomics in storage/mod.rs.

The read-after-write corruption bug from the memory note (apt/exFAT, block=262144) was the dropped-dirty-on-eviction case: it is fixed in the current tree — insert_with_dirty now returns evicted-but-unflushed dirty sectors that write_back() writes through to disk after releasing the lock (blockcache.rs:432-465, 884-905), and writeback_flush snapshots dirty data under the lock and verifies slot identity with a key_check seal before clearing the dirty bit (blockcache.rs:963-1104). The coherence path is now structurally sound, but several latent hazards, a kernel panic on corrupt on-disk data, and notable performance cliffs remain.

### Problems
- **[HIGH/file-length/effort:xl]** vfs/mod.rs is 6952 lines with 7+ distinct responsibilities and 36 fs_id dispatch branches
    - evidence: kernel/src/fs/vfs/mod.rs is the largest file in the codebase (6952 lines, 138 functions, 54 pub fns). read() (:3976) and write() (:4221) are each ~250-line if-else ladders on the magic integer `file.fs_id` (1/2/3/4/6/7/8/9). `grep 'fs_id =='` finds 36 branch sites. The same logic is duplicated three ways per FS: locked read/write, plus a full parallel set of lock-free Detached* plans (prepare_detached_read/write/open/delete/read_dir/rename/mkdir/stat/attrs/readlink/symlink + execute_/finish_/rollback_ — ~30 functions, lines 985-3947).
    - impact: Unmaintainable: adding a filesystem requires touching dozens of branch sites; every change risks a missed branch (e.g. a new FS that forgets the append-buffer flush in read()). High cognitive load directly feeds problems #2 and #3.
    - fix: Drive all I/O through the existing `Filesystem` trait (vfs/types.rs) so read()/write() become a single mount-lookup + trait call. Replace the typed VfsState fields with a `Vec<Mount{ path:String, fs:Box<dyn Filesystem> }>`. Then physically split per the key_files split_suggestion (mount.rs/open.rs/io.rs/detached.rs/exfat_glue.rs/meta.rs/sync.rs).
- **[HIGH/architecture/effort:xl]** Filesystem trait exists but is bypassed; VFS dispatches on magic fs_id integers + typed per-FS state fields
    - evidence: vfs/types.rs:69 defines a complete `Filesystem` trait (read/write/lookup/readdir/create/delete/stat/statfs/rename/truncate/set_mode/symlink/sync + as_any). But only CoreFS goes through it end-to-end (vfs/mod.rs:4096 `Filesystem::read(driver,...)`, :4340 write). exFAT/NTFS/ISO/Overlay/SMB are dispatched by hand-written fs_id branches. VfsState (:569-615) has 11 typed fields (exfat_fs, fat_fs, ntfs_fs, iso9660_fs, devfs, smbfs, overlay_fs, corefs_driver, mounted_corefs, mounted_exfat, root_other) and the comment at :589-599 explicitly says they exist 'to preserve Rust's field-level borrow splitting that the legacy dispatch code relies on.' There is no uniform mount table — find_submount + per-FS Vec scans are reimplemented everywhere.
    - impact: The intended HAL-style abstraction (#2) is not enforced: drivers cannot be added without editing the VFS core, the trait's default methods (symlink/stat/truncate) are dead for the typed FSes, and borrow-splitting hacks block refactoring. This is the root cause of the file-length and stability problems.
    - fix: Make every driver a `Box<dyn Filesystem>` stored in a single mount table keyed by canonical path; resolve mount → (&dyn Filesystem, relative_path) once per syscall and call the trait. Keep exFAT's cluster/append optimizations behind trait methods (e.g. an optional `as_exfat()` downcast via as_any, which already exists) instead of fs_id branches. This collapses the 36 branch sites to ~1.
- **[HIGH/stability/effort:medium]** cluster_to_lba panics the whole kernel on an out-of-range cluster (corrupt FAT chain → kernel panic)
    - evidence: kernel/src/fs/exfat.rs:916-931 `fn cluster_to_lba(&self, cluster)` does `panic!("exfat::cluster_to_lba: bogus cluster ...")` if cluster <2 or >= cluster_count+2. It is called all over the read/write/plan paths (read_cluster:1052, write_cluster:1099, read_file:2534, get_file_read_plan:2670/2685, load_bitmap:1298, execute paths). next_cluster() can return a corrupted value from a damaged on-disk FAT, and inodes encode cluster numbers (decode_inode) that can be stale across rename/truncate.
    - impact: A single bad cluster number (on-disk corruption, a stale fd after rename/free, or a logic bug in FAT-chain walking) takes down the entire kernel rather than failing the one syscall with EIO. Directly contradicts the stability goal (#3); especially dangerous because exFAT is the root filesystem.
    - fix: Convert cluster_to_lba to `Result<u32, FsError>` returning FsError::IoError (validate_cluster already does exactly this non-panicking check at :897). Propagate the error through read_cluster/write_cluster/plan builders. Never panic on data-derived values.
- **[HIGH/stability/effort:medium]** Read-after-write coherence depends entirely on overlay_cached being called after EVERY backend read; lookup_range stop-at-first-miss makes this fragile
    - evidence: blockcache.rs:282 lookup_range STOPS at the first cache miss (correct for the fast path), so the read fast-path at storage/mod.rs:706-713 only short-circuits when ALL sectors hit. For partial/total misses, the disk read returns STALE bytes for any dirty write-back sector lying past the first miss; coherence is restored ONLY by the subsequent overlay_cached_responsive() calls (storage/mod.rs:792, 820, 844, 868). Every one of the 4 read arms must call overlay; the no-readahead arm gates overlay on `cache_active` and on buffer-length checks (:865-874). If any future code path issues a backend read without the matching overlay (e.g. a new FS calling read_sectors_raw_for_disk, or a refactor that moves the overlay), dirty data is silently shadowed by stale disk data — exactly the apt corruption signature.
    - impact: The fix for the historical 262144-block corruption is correct but structurally brittle: coherence is an emergent property of 'always overlay after read' rather than an invariant of the cache API. One missed overlay reintroduces silent data corruption.
    - fix: Fold the overlay INTO the cache read API: make a single `cache_read_or_fill(disk,lba,count,buf, backend_read_fn)` that (a) reads the whole range from disk into buf, (b) overlays all dirty cached sectors, (c) populates clean ones — so callers physically cannot read the backend without the overlay. Alternatively make write-back write-through for any range that overlaps an in-flight read. Add a kunit test (see test_gaps) asserting: write_back(lba,N) then a full-miss read(lba,N) returns the written bytes.
- **[MEDIUM/performance/effort:medium]** Bulk-write cache invalidation does a full 16384-slot linear scan under the spinlock on every large write
    - evidence: Every direct/bulk write (>WRITE_BACK_MAX_SECTORS=8 sectors) ends with `blockcache::invalidate(disk_id, lba, count)` (storage/mod.rs:1009). invalidate_range (blockcache.rs:587-610) takes the count>MAX_PROBES(32) branch for any write >32 sectors and then scans ALL 16384 cache slots (`for i in 0..self.slots.len()`) while holding the BLOCK_CACHE spinlock, also calling quarantine_slot per slot. A 256 KiB write (512 sectors) thus triggers a 16K-slot scan; a streaming copy does it per chunk. overlay_range_by_slot_scan (:312) and should_flush_before_write_back (:922) and dirty_count (:1121) have the same O(slots)-under-lock pattern.
    - impact: Streaming large writes (file copies, apt unpack, image writes) pay a full-cache linear scan + lock hold per chunk, serializing all other disk I/O behind the spinlock and capping throughput — a concrete #9 IO/perf problem.
    - fix: Maintain a per-disk index of occupied LBA ranges, or hash-probe the exact `count` keys instead of scanning all slots when count is bounded. At minimum, since bulk writes go direct-to-disk and were never write-back-cached, skip the range scan entirely when there are zero dirty sectors for that disk (track a per-disk dirty count, which DIRTY_ESTIMATE already approximates) and only invalidate via hash lookups for the specific LBAs.
- **[MEDIUM/swap/effort:large]** WRITE_BACK_MAX_SECTORS=8 means writes split across a write-back/direct boundary by exFAT's per-cluster loop create mixed-residency ranges
    - evidence: storage/mod.rs:960 WRITE_BACK_MAX_SECTORS=8. exFAT write_file_with_hint writes fragmented files cluster-by-cluster via write_cluster (exfat.rs:3007/3015) → write_sectors(lba, spc). With a 4 KiB cluster (spc=8) each write is exactly 8 sectors → write-back (dirty cache). The multi-cluster fast path (exfat.rs:2989) does one write_sectors(run_clusters*spc) which for >1 cluster is >8 sectors → direct+invalidate. So a single logical file write produces some sectors in the dirty write-back cache and some written direct to disk, depending purely on on-disk fragmentation. Coherence holds today (overlay covers the dirty ones), but the residency of a given sector is non-deterministic and the two paths have different durability semantics (write-back is volatile until writeback_flush; direct is on the drive).
    - impact: Mixed durability within one file write complicates crash consistency and makes the cache behavior hard to reason about / test. Fragmentation-dependent code paths are a classic source of heisenbugs (matches the 'finicky, intermittent' character of the original corruption).
    - fix: Make the write-back vs direct decision based on the *logical* operation, not the post-fragmentation sector count: route all file *data* writes direct-to-disk (with hash-targeted invalidate) and reserve write-back exclusively for small *metadata* (FAT/bitmap/dirent) sectors, or unify on write-through with an explicit ordered flush. Document the durability contract per path.
- **[MEDIUM/stability/effort:large]** flush_metadata writes FAT+bitmap with no ordering barrier and no hardware flush; crash between metadata and data loses consistency
    - evidence: exfat.rs:940-1022 flush_metadata writes dirty FAT runs then dirty bitmap runs via write_sectors, then the comment at :1017-1019 explicitly says it does NOT call storage::flush() (AHCI FLUSH CACHE EXT is 'extremely expensive') and relies on 'the drive's own write cache' for ordering. There is no write barrier between data clusters, FAT chain updates, and the directory entry size update (write() sets file.entry_dirty and defers the dirent commit; commit_open_exfat_entry runs later). maybe_flush_exfat_metadata_periodic (vfs:3949) flushes only every FLUSH_INTERVAL writes.
    - impact: On power loss / crash / QEMU kill, the FAT can reference clusters whose data was never flushed, or a dirent can claim a size/first-cluster not yet backed by a flushed FAT entry → cross-linked or truncated files. This is durability corruption distinct from the (fixed) RAM cache bug and is a real-world risk during apt operations that abort.
    - fix: Establish an ordering discipline: flush data clusters, then FAT, then bitmap, then dirent, with a hardware barrier (or at least cache-flush) at the FAT→dirent boundary on fsync/close. Make fsync actually durable (it currently routes through flush_hardware_for_disks only on sync_write — verify the close path does too). At minimum document that exFAT offers no crash consistency without fsync.
- **[MEDIUM/stability/effort:small]** execute_write_range ignores base_offset (hardcodes run_file_start=0) — latent wrong-sector write if a ranged overwrite plan is ever used
    - evidence: exfat.rs:708 `let mut run_file_start = 0u64;` in execute_write_range, whereas the read twin execute_range:586 correctly uses `self.base_offset`. Today the only caller (vfs prepare_detached_write:3597) builds the overwrite plan via get_file_read_plan which always sets base_offset=0 (exfat.rs:2659/2674/2705), so it works. But get_file_read_plan_range (:2740/2749/2819) builds plans with non-zero base_offset; if anyone wires a ranged overwrite plan into execute_write_range, every sector would be written to (offset - base_offset) — silent on-disk corruption of unrelated file regions.
    - impact: A latent landmine: a plausible future optimization (ranged overwrite to match ranged reads) silently corrupts data. Asymmetry between the read and write plan executors is itself a bug smell.
    - fix: Use `self.base_offset` in execute_write_range exactly like execute_range, or assert base_offset==0 at entry. Add a unit test that builds a base_offset!=0 plan and verifies execute_write_range targets the correct absolute LBAs (or rejects it).
- **[LOW/stability/effort:small]** Stale/incorrect safety comment on exFAT cluster cache UnsafeCell aliasing invariant
    - evidence: exfat.rs:1046-1047 read_cluster: 'SAFETY: ExFatFs is always accessed while the VFS Mutex is held, guaranteeing single-threaded access to the cache.' This is false: the detached read/write paths (vfs/mod.rs:3440 execute_detached_read, :3621 execute_detached_write, :3807 execute_exfat_append_flush) explicitly DROP the VFS mutex and instead take ExFatFsDriver::inner Mutex (exfat.rs:3786, :3801 lock_inner). The invariant that actually upholds the &mut *cluster_cache.get() aliasing safety is the inner driver Mutex, not the VFS Mutex.
    - impact: The documented safety reasoning is wrong. A maintainer trusting the comment could add a code path that touches ExFatFs without the inner lock (thinking the VFS lock suffices) and create a real data race on the UnsafeCell cluster cache. Low severity only because the actual invariant currently holds.
    - fix: Correct the SAFETY comment on read_cluster/write_cluster/dir_cache_* to state the real invariant: 'ExFatFs is only ever accessed through ExFatFsDriver::inner Mutex; lock_inner() serializes all access.' Consider replacing the UnsafeCell caches with the lock-guaranteed &mut already available, or RefCell in debug builds to catch violations.
- **[LOW/performance/effort:small]** exFAT cluster-cache hash_insert overwrites a live mapping on probe overflow, degrading lookups to O(128) linear scan
    - evidence: exfat.rs:133-144 hash_insert probes only 4 slots and on overflow does `self.hash_table[h] = slot_idx` — overwriting whatever valid mapping was at the home bucket, orphaning that cluster's hash entry. lookup (:101) breaks out of the hash probe on the first EMPTY and only then falls back to a full linear scan over all 128 slots (:119). hash_remove (:147) also only probes 4 and can leave stale hash entries. With 128 slots and FNV-style hashing, collisions force frequent linear scans.
    - impact: Cluster-cache lookups silently degrade to O(slots) under collision pressure (directory scans, large file walks). Correctness is preserved by the linear fallback, so this is purely a perf/quality issue, but it makes the cache's claimed O(1) untrue and adds latency to the hot read path.
    - fix: Either probe the full table on insert (it's only ~ a few hundred entries) and never overwrite a live mapping, or replace the bespoke open-addressing with the same proven scheme used by blockcache.rs (tombstones + key_check). Given only 128 slots, a small sorted/array structure may be simpler and faster.
- **[MEDIUM/performance/effort:medium]** Per-FS copy overhead and double caching: every cluster passes through both the block cache (512B slots) and the exFAT cluster cache (full-cluster Vec), plus per-cluster Vec allocations on the RMW path
    - evidence: read_cluster (exfat.rs:1044) caches each cluster in the exFAT ClusterCache (data: Vec<u8>, heap-allocated per slot, exfat.rs:175 .to_vec()), while the underlying sectors are ALSO cached in the global block cache (storage/mod.rs populate). Partial-cluster writes do read-modify-write with a fresh `vec![0u8; cs]` per call (exfat.rs:3018, write_cluster:1106). read_file's batched runs allocate `vec![0u8; run_bytes]` for any unaligned read (exfat.rs:2559). The block cache itself copies 512 bytes per sector on every hit (blockcache.rs:245 copy_from_slice) and on overlay.
    - impact: Each logical 4 KiB read can incur: 1 disk DMA + 8 block-cache inserts (512B copies) + 1 cluster-cache Vec alloc+copy + caller copy = ~3x memory traffic and per-op heap churn. On the write path the global block cache holds the dirty data AND the cluster cache holds a duplicate clean/updated copy. This is a measurable #9 throughput/alloc-pressure problem on FS-heavy workloads.
    - fix: Pick one cache layer for exFAT data: since the block cache already provides write-back coherence, the cluster cache is largely redundant for data (it is most valuable for directory clusters). Restrict ClusterCache to directory/metadata clusters, or drop it and rely on the block cache with a slab/arena for the RMW scratch buffer to kill per-call Vec allocations. Reuse a per-driver scratch buffer for read-modify-write and unaligned-run reads.
- **[LOW/hal-driver/effort:large]** 512-byte sector size is hardcoded throughout; no 4Kn/large-sector support and exFAT rejects bytes_per_sector_shift != 9
    - evidence: blockcache.rs:14 'CACHE_SECTORS: 16384 x 512 = 8 MiB' with `data: [u8; 512]` fixed slot size (:108) and `* 512` arithmetic throughout (lookup_range:275, overlay:330, write_back:889, writeback_flush:1066). storage/mod.rs uses `* 512` pervasively. exfat.rs:800 explicitly rejects volumes with bytes_per_sector_shift != 9 (i.e. only 512-byte sectors). NVMe/AHCI 4Kn devices are not representable.
    - impact: The block layer cannot serve 4K-native disks or optical 2048-byte sectors through the unified cache; the cache and exFAT silently assume 512. Limits the HAL/driver story (#5) and future hardware.
    - fix: Parameterize sector size in the device abstraction and either make the block cache slot size configurable per disk or normalize to a logical block size. At minimum, document the 512-only assumption as an explicit constraint in vfs/types.rs and reject non-512 devices with a clear error rather than scattered `* 512`.

### Refactor opportunities
- Collapse read()/write()/readdir()/stat()/delete()/rename()/mkdir() fs_id ladders into one mount-lookup + Filesystem trait call; this alone removes ~36 branch sites and likely ~1500 lines from vfs/mod.rs.
- Replace the 11 typed VfsState fields with a single mount table Vec<Mount{path, Box<dyn Filesystem>}> + a small typed-downcast escape hatch via the existing as_any(); eliminates the borrow-splitting rationale documented at vfs/mod.rs:589.
- Unify the locked and lock-free (Detached*) I/O into one path: have the trait methods themselves drop the VFS lock and take the driver's inner lock, removing the ~30 parallel prepare/execute/finish/rollback functions.
- Fold overlay_cached into the cache-read API (cache_read_or_fill) so coherence is an API invariant, not a caller convention (fixes the fragility in problem #4).
- Restrict the exFAT ClusterCache to directory/metadata clusters (or remove it) since the block cache already provides data coherence — removes a whole redundant caching layer and its per-cluster Vec allocations.
- Introduce a per-driver scratch arena for read-modify-write and unaligned-run buffers to eliminate per-call vec![0u8; cluster_size] allocations on the hot path.
- Make cluster_to_lba and all data-derived index conversions return Result instead of panicking; centralize cluster validation.
- Extract the storage readahead engine (3 near-identical fetch arms in read_sectors_on_disk:780-855) into one helper to remove triplicated code.
- Parameterize sector size to enable 4Kn/2048-byte media instead of the pervasive hardcoded 512.

### Test gaps
There is NO host-runnable or kunit test for blockcache.rs or exfat.rs — the two files where the corruption bug lived. The only FS tests are corefs/mod.rs, corefs/block_device.rs (in-memory SectorIo mock under #[cfg(test)]/feature=\"kunit\"), corefs/integration_*.rs, and fuse/inode_map.rs. corefs/integration_tests.rs itself documents (its header) that anyOS has no in-kernel harness wired up and kunit is feature-gated but unused.

Concrete high-value tests to add:
1) blockcache coherence unit test (host-portable if the few crate:: deps — task::scheduler, drivers::storage::write_sectors_direct_on_disk, memory::virt_to_phys — are abstracted behind a trait or #[cfg(test)] stub). Assert the exact regression: init(); write_back(disk,lba,N) for N spanning past a forced cache miss; then a FULL-MISS read of [lba..lba+N] must return the written bytes (this pins down the lookup_range-stop-at-miss + overlay invariant). Also: fill the cache with dirty sectors to force dirty eviction, assert insert_with_dirty returns the evicted (disk,lba,data) and that writeback never silently drops a dirty slot (the original bug). 3) exFAT plan symmetry test: build get_file_read_plan_range with base_offset!=0 and assert execute_write_range targets the same absolute LBAs as execute_range reads (would catch the :708 base_offset=0 bug).
4) cluster_to_lba: feed an out-of-range cluster and assert it returns Err (after converting from panic), not abort.

In-guest (vfsstress) coverage already exists for the headline cases (the block= write/readback loop incl. block=262144, 'deb install pattern', long-name large io, no-fsync readback) per bin/vfsstress/src/main.rs and the memory note (seed 2703025645 green). ## NET — NETWORK stack (kernel/src/net/* + kernel/src/drivers/network/* + kernel/src/syscall/linux/socket.rs)

**Architecture:** The stack is a classic layered TCP/IP: NIC driver (e1000/virtio_net/rtl81xx) → ethernet.rs → ipv4/ipv6.rs → tcp/udp/icmp/arp. There is NO interrupt/softirq-driven RX delivery to a worker thread; instead the whole stack is *polled synchronously on the calling thread*. Every blocking call (tcp::recv, tcp::send, connect, accept, arp::resolve, udp::recv_timeout, dns) runs a loop of `net::poll()` (kernel/src/net/mod.rs:139) which drains the NIC RX queue (`poll_rx_into`), runs `ethernet::handle_frame` for each packet, and periodically calls `tcp::check_retransmissions()`. A single background thread (`deferred_reaper_thread`, kernel/src/task/scheduler/mod.rs:2062) also calls `check_retransmissions()` at ~100 Hz. The E1000 IRQ handler additionally runs the full `handle_frame`→TCP state machine→ACK-send pipeline directly in IRQ context (e1000.rs:740-777).

All TCP state lives in ONE global structure: `TCP_CONNECTIONS: Spinlock<Option<Vec<Option<Tcb>>>>` of 256 fixed slots (tcp/mod.rs:39, tcb.rs:19), plus an `unsafe static mut CONN_HASH` 256-entry direct-mapped index (tcp/mod.rs:44). Because `Spinlock::lock()` disables interrupts for the entire hold (sync/spinlock.rs:151-156), the *entire* TCP input state machine, OOO reassembly, send batching and timer scan run with IF=0 and serialize all connections through one lock. Sockets are mapped to slot indices via a separate `LINUX_SOCKETS: Spinlock<[LinuxSocketEntry;256]>` (socket.rs:112). Routing is not a table — ipv4::send_ipv4 just picks `dst` if local else `gateway` (ipv4.rs:151). Interfaces are parsed from /System/etc/network/interfaces into an in-memory Vec (interfaces.rs).

The TCP implementation has window scaling, delayed ACKs, OOO reassembly, fast retransmit and TIME_WAIT, but NO congestion control (no cwnd/ssthresh — grep found none), NO RTT estimation (fixed 3 s RTO with exponential backoff, tcb.rs:34), and the send window is driven purely by the peer's advertised window. Packet buffers are heap `Vec<u8>` allocated and copied at every layer: DMA→`Vec` in the driver, driver queue→`Vec<Vec<u8>>` in poll, then a third `Vec` for the TCP payload in parse_tcp.

### Problems
- **[HIGH/performance/effort:large]** No congestion control (no cwnd / slow-start / ssthresh) — sender bursts up to the full peer window
    - evidence: tcp/send.rs:415-416 computes the send window as `(tcb.snd_wnd as usize).max(MSS).min(MAX_IN_FLIGHT)` — purely the peer's *advertised* receive window (up to 2 MiB, tcb.rs:42). No congestion window exists: grep for cwnd/ssthresh/slow_start/congestion in kernel/src/net returns nothing. tcp/send.rs:422-464 batches up to 64 MSS segments (SEND_BATCH_SIZE, tcb.rs:49) back-to-back as soon as the peer window allows.
    - impact: On any real lossy/bandwidth-limited path the stack overshoots the bottleneck, causes bursty loss, and (with slow single-segment retransmit) collapses to very low goodput; also an RFC 5681 violation. Loopback/QEMU masks this.
    - fix: Add per-TCB cwnd and ssthresh. Init cwnd ~10*MSS (RFC 6928), slow-start until ssthresh then congestion avoidance, halve cwnd on loss. In send.rs use effective_window = min(snd_wnd, cwnd). Reduce cwnd on fast-retransmit (input.rs:512) and RTO (timer.rs:197).
- **[HIGH/performance/effort:large]** Fixed 3-second RTO with no RTT estimation (no SRTT/RTTVAR, no Karn's algorithm)
    - evidence: RETRANSMIT_TICKS = 300 (3 s at 100 Hz) base RTO (tcb.rs:34); timer.rs:120 uses `rto = RETRANSMIT_TICKS << retransmit_count.min(5)`. No per-segment send timestamp and no SRTT/RTTVAR (grep srtt/rtt in net returns only ICMP ping). TCB has only last_send_tick (tcb.rs:177).
    - impact: A single lost segment on a 1 ms-RTT LAN stalls the connection for a full 3 seconds before retransmit, 6/12/24 s on backoff. Dominant cause of 'network slow/freezes' on real links (#9, #3). RFC 6298 mandates RTT-based RTO with a 1 s minimum, not a fixed 3 s.
    - fix: Implement RFC 6298: time the first un-retransmitted segment per window (Karn: skip retransmitted samples), maintain SRTT/RTTVAR, RTO = SRTT + 4*RTTVAR clamped to [200ms, 60s]. Store a (seq, send_tick) for the timed segment in the TCB.
- **[HIGH/performance/effort:medium]** Retransmission timer processes at most ONE connection (and one segment) per call
    - evidence: tcp/timer.rs: each retransmit branch ends with `return;` (lines 194, 257, 312) not `continue`, so one check_retransmissions() can retransmit for only one TCB. Invoked at most every 2 ticks from net::poll (mod.rs:146-149) and ~100 Hz from deferred_reaper_thread (scheduler/mod.rs:2068).
    - impact: With N connections needing retransmit it takes N ticks to service them, multiplying recovery latency. Combined with 3 s RTO this is catastrophic for multi-connection workloads (e.g. Surf's 6 parallel fetch lanes).
    - fix: Replace the `return;` statements with a deferred-send collection (like the delayed-ACK pass timer.rs:21-86): collect all retransmit jobs under the lock, drop the lock once, send them all. Never early-return from the scan loop.
- **[HIGH/performance/effort:xl]** Single global interrupts-off spinlock serializes the entire TCP stack
    - evidence: All TCP state is behind TCP_CONNECTIONS: Spinlock<Option<Vec<Option<Tcb>>>> (tcp/mod.rs:39). Spinlock::lock() does cli() for the whole hold (sync/spinlock.rs:155-156). handle_tcp holds it across the full state machine incl. OOO reassembly (input.rs:28-341); the timer scan iterates all 256 slots under it (timer.rs:36-75, 95-259); recv/send take it every poll iteration (recv.rs:257, send.rs:375).
    - impact: Interrupts disabled while iterating 256 slots and doing memcpy-heavy reassembly raises IRQ latency for ALL devices and serializes every socket through one lock — no per-connection parallelism, hurting throughput and whole-system responsiveness (#3, #9).
    - fix: Move heavyweight work (OOO merge recv.rs:130-190, send-buffer drains) out from under the global lock, or shard the table into per-bucket locks keyed by the 4-tuple hash. Do not hold an IF-off spinlock during O(n) table scans (listener-pending count input.rs:91-128, v6 linear lookup).
- **[HIGH/performance/effort:large]** Per-packet heap allocation and triple-copy on the RX path (no buffer pooling)
    - evidence: E1000 process_rx_ring copies each DMA buffer into a fresh Vec (e1000.rs:703-707) pushed into rx_queue: VecDeque<Vec<u8>> (e1000.rs:142). poll_rx allocates a new Vec<Vec<u8>> per poll and drains into it (net/mod.rs:157-163, e1000.rs:584-597). parse_tcp allocates a THIRD Vec for the payload (tcb.rs:354). virtio_net is identical (virtio_net.rs:184) and transmit does an extra data.to_vec() (virtio_net.rs:242).
    - impact: At line rate every packet hits the global heap allocator 2-3 times under an interrupts-off lock — the #1 memory-alloc/IO hot spot (#9). The TCP payload copy in parse is avoidable; the state machine only needs a borrowed slice.
    - fix: Use a fixed-size frame buffer pool (recycle DMA-sized buffers). Make TcpSegment.payload a borrowed &[u8] into the IP packet (it outlives parse within handle_frame); only OOO buffering clones. Wire up the already-written, zero-call-site transmit_batch (e1000.rs:500) to send.rs batching.
- **[CRITICAL/stability/effort:large]** arp::resolve() recursively re-enters net::poll() and the full RX/TCP path; reachable from IRQ context
    - evidence: arp::resolve (arp.rs:101-115) loops calling super::poll() → poll_rx → handle_frame → handle_tcp. ipv4::send_ipv4 calls arp::resolve(next_hop, 200) (ipv4.rs:162) for every non-cached dest. send_ipv4 is reached from the E1000 IRQ handler: e1000_irq_handler (e1000.rs:740) → handle_frame → handle_tcp → deferred ACK send_segment → send_ipv4 → arp::resolve → poll() inside the IRQ.
    - impact: Re-entrant network processing from inside an IRQ; arp::resolve can block-spin up to 2 s in an interrupt handler. Deadlock/stack-overflow/latency hazard and a plausible source of the reported freezes (#3). A TCP ACK send for connection A can drive RX processing of connection B mid-flight.
    - fix: Never resolve ARP synchronously on TX. Keep a pending-ARP queue: on cache miss send the request, queue the outgoing frame, flush it on reply. The IRQ handler must only enqueue RX frames and wake a worker thread — never run handle_frame (and thus TX/ARP) in IRQ context.
- **[HIGH/hal-driver/effort:large]** E1000 IRQ handler runs the full protocol stack (and can TX) in interrupt context
    - evidence: e1000_irq_handler (e1000.rs:740-777): on ICR_RXT0 it calls process_rx_ring then drains recv_packet() and runs net::ethernet::handle_frame per frame (e1000.rs:772-775). handle_frame → handle_tcp generates ACKs via send_segment → send_ipv4 → transmit, and can call arp::resolve→poll(). The comment at e1000.rs:770 acknowledges allocator-lock deadlock risk yet still runs the whole stack.
    - impact: TCP state machine, the global TCP_CONNECTIONS spinlock, the heap allocator (parse_tcp Vec) and potentially-blocking ARP all run inside the NIC IRQ. If the interrupted thread held TCP_CONNECTIONS or the heap lock, this deadlocks; otherwise unbounded IRQ runtime. Strong freeze candidate (#3).
    - fix: IRQ handler should ack the device, copy frames into the RX queue, and wake a dedicated net-softirq thread; all protocol processing runs in that thread with interrupts enabled. Also fixes re-entrancy and ARP-in-IRQ.
- **[MEDIUM/performance/effort:medium]** IPv6 TCP input does an O(n) full-table linear scan per packet (no hash index)
    - evidence: handle_tcp_v6 finds the connection via table.iter().position(...) over all 256 slots (input.rs:610-620). The CONN_HASH fast path is IPv4-only (insert_slot_hash/remove_slot_hash skip is_ipv6, util.rs:46,55; input.rs:37-74). Every IPv6 segment is O(n) with interrupts off.
    - impact: IPv6 throughput degrades linearly with connection count; inconsistent with the IPv4 fast path.
    - fix: Extend the hash to cover IPv6 (hash v6 remote addr + ports) or add a secondary BTreeMap keyed by (family, ports, addr).
- **[MEDIUM/stability/effort:large]** No IP fragmentation; hardcoded 1500-byte cap silently fails large datagrams
    - evidence: send_ipv4 returns false if total_len > 1500 (ipv4.rs:110); send_ipv4_raw the same (ipv4.rs:185). No RX reassembly — handle_ipv4 ignores MF flag/fragment offset (ipv4.rs:217-229). UDP send builds one datagram (udp.rs:158) so any UDP payload >1472 bytes silently fails.
    - impact: Large UDP sends and fragmented inbound IPv4 are dropped with no error path beyond a bool. TCP is MSS-safe, but the failure is silent and surprising; real-network fragmented traffic is dropped.
    - fix: Implement IPv4 TX fragmentation (split into MTU fragments with correct offset/MF) and an RX reassembly cache keyed by (src,dst,id,proto) with timeout. At minimum propagate EMSGSIZE instead of a bare false.
- **[MEDIUM/stability/effort:medium]** Ephemeral port allocation never checks for in-use ports (collision -> wrong-connection delivery)
    - evidence: alloc_ephemeral_port (tcp/util.rs:36-41) just increments a global counter with no check that the (port, remote) tuple is free. The Linux socket layer has its own NEXT_EPHEMERAL counter (socket.rs:34) — two independent allocators. conn_hash_insert overwrites any prior slot mapping for a colliding 4-tuple (tcp/mod.rs:65-75) with no collision chain.
    - impact: After wrap, a new connection's hash entry can clobber a live/TIME_WAIT connection to the same peer, misrouting segments to the wrong slot or dropping them — hard-to-reproduce connection mix-up (#3).
    - fix: Make alloc_ephemeral_port scan the table for a free (local_port, remote_ip, remote_port) tuple and retry on collision. Unify the two ephemeral allocators.
- **[MEDIUM/stability/effort:small]** Data races on static mut IP_ID and CONN_HASH (no atomics) on SMP
    - evidence: ipv4.rs:121-125 and 192-196 use `static mut IP_ID/RAW_IP_ID` incremented without synchronization. tcp/mod.rs:44 `pub(crate) static mut CONN_HASH: [u16;256]` is read in input.rs:38 and written in conn_hash_insert/remove (mod.rs:73,85).
    - impact: CONN_HASH is protected only incidentally by TCP_CONNECTIONS being held during access; the IP_ID counter has no protection and can produce duplicate/torn IDs. UB per the Rust memory model. CLAUDE.md documents SMP, so this is a real hazard.
    - fix: Make IP_ID an AtomicU16/U32 with fetch_add(Relaxed). Move CONN_HASH inside the TCP_CONNECTIONS-protected struct (it is logically part of the table), removing the unsafe static mut.
- **[MEDIUM/performance/effort:small]** trace::record_frame takes a global interrupts-off lock on every RX/TX frame even when disabled
    - evidence: ethernet::handle_frame (ethernet.rs:60) and send_frame (ethernet.rs:78) call trace::record_frame on every frame. record_frame acquires TRACE_STATE.lock() (trace.rs:117) and only THEN checks state.enabled (trace.rs:118). The lock disables interrupts.
    - impact: Unnecessary global lock + cli/sti per packet in the hottest path, contended against the dcpdump read_and_clear syscall. Pure overhead in the common tracing-off case.
    - fix: Gate on an AtomicBool TRACE_ENABLED loaded Relaxed before locking; return immediately if disabled. Only lock when actually recording.
- **[MEDIUM/performance/effort:xl]** Pervasive busy-poll model: every blocking net call spins calling net::poll() + 1-tick sleeps
    - evidence: recv (recv.rs:255-379), send (send.rs:372-537), connect (connect.rs:192-233), accept (connect.rs:345-418), arp::resolve (arp.rs:101-115), udp::recv_timeout (udp.rs:227-240), dns (dns.rs:484) all loop poll() -> check -> sleep_until(now+1) -> poll(). No single owner of RX; each waiter drives the NIC and the whole TCP timer machinery.
    - impact: N blocked sockets each wake every tick to re-drive poll() and check_retransmissions(), doing redundant full RX drains and 256-slot timer scans. CPU burned proportional to (#blocked sockets x tick rate); wakeups are 1 ms-coarse. Direct scheduler/network perf concern (#9).
    - fix: One net worker thread owns poll()/RX and TCP timers; blocking syscalls sleep on a per-socket wait queue (the waiting_tid mechanism already exists, input.rs:333-338) and are woken by the worker, not self-poll.
- **[LOW/performance/effort:medium]** OOO reassembly uses O(n) Vec::insert/remove and clones tails on the locked path
    - evidence: insert_ooo (recv.rs:130-190) scans ooo_buf (up to MAX_OOO_SEGMENTS=1024, tcb.rs:59), Vec::insert at a found position (O(n) shift), then a merge pass with Vec::remove and .to_vec() tail clones (recv.rs:181). drain_ooo (recv.rs:193-234) re-scans and re-clones with seg.data[consumed..].to_vec(). All under the global lock with interrupts off.
    - impact: On a lossy high-bandwidth flow with a large reorder window this is O(n^2) with repeated reallocation, executed with interrupts disabled — amplifies the global-lock latency exactly during loss recovery.
    - fix: Use a BTreeMap<seq, Vec<u8>> or a slice ring for OOO storage (O(log n) insert, no shift+clone). Track a consumed offset instead of rebuilding the segment.
- **[LOW/stability/effort:medium]** close() can busy-block up to 5 s; TIME_WAIT slots reclaimed only lazily, exhausting the 256-slot table
    - evidence: close (connect.rs:541-726) polls up to 500 ticks (5 s, line 636) before force-RST. TIME_WAIT cleanup happens only when check_retransmissions scans the slot (timer.rs:101-103,137-141); with 256 slots a burst of short connections can exhaust slots before TIME_WAIT (200 ticks, tcb.rs:38) elapses -> connect/listen return u32::MAX (connect.rs:54).
    - impact: Under high connection churn (web crawling, many short HTTP requests) the 256-slot table + 2 s TIME_WAIT + lazy reclamation causes connect failures and accept stalls; the blocking close() pins the calling thread for seconds on a half-dead peer.
    - fix: Grow MAX_CONNECTIONS or make the table dynamic; reclaim the oldest TIME_WAIT slot when allocating if none free. Make close() non-blocking (finish FIN/ACK in the timer thread).
- **[LOW/stability/effort:small]** ARP cache has no expiry/eviction and grows unbounded
    - evidence: ARP_TABLE is a BTreeMap<u32,(MacAddr,u32)> (arp.rs:15). insert stores a learn-tick (arp.rs:38) but lookup ignores age (arp.rs:28-32); nothing expires entries; no max-size or eviction.
    - impact: Stale MAC entries persist forever (breaks after a peer/gateway MAC change), and the table grows unbounded under ARP scanning/spoofing. Minor on small LANs but a correctness gap.
    - fix: Expire entries older than ~5 min on lookup (re-resolve), cap the table with LRU eviction, refresh the gateway entry before expiry.

### Refactor opportunities

## COMPOSITOR — COMPOSITOR server (system/compositor/compositor/src/) + libcompositor/libcompositor_client protocol

**Architecture:** The compositor is a no_std Rust process (`panic = "abort"`) split into two threads sharing one heap-allocated `Desktop` struct via a single global spinlock. `render.rs` holds the entire shared state: `static mut DESKTOP_PTR: *mut Desktop` plus `static DESKTOP_LOCK: AtomicBool`, accessed through `unsafe fn desktop_ref()`. The management thread (`app/management.rs::management_loop`) handles input polling, IPC command dispatch, process reaping, login/dock lifecycle, display hotplug; the render thread (`render.rs::render_thread_entry`) is event-driven (RENDER_NEEDED flag) and runs `compose_deferred()`, draining GPU commands and frame ACKs under the lock then submitting them outside it. Lock discipline is the central design: both threads take the spinlock for short critical sections, and blocking syscalls (`gpu_command`, `evt_chan_emit_to`, `shm_map`, wallpaper I/O) are deliberately kept outside the lock to avoid the busy-wait spinlock starving the other thread.

The compositor model is layer-based (`compositor/mod.rs`: `Vec<Layer>`, z-order = vector order, `next_layer_id`). Each client window (`desktop/window.rs::WindowInfo`) owns a compositor-side `layer.pixels` back buffer plus a raw `shm_ptr`/`shm_id` mapping of the client's surface. `present_ipc_window()` copies client SHM into the layer's compositor-owned pixel buffer; the compose pass blends only compositor-owned buffers (so compositing itself never dereferences live client SHM — good). There are also VRAM-direct layers (zero-copy via GPU RECT_COPY) and a multi-output path (`Output` entries ≥1 re-composite their full framebuffer each frame). Window state machine: create (`create_ipc_window`/`_fast`/`create_vram_window`) → present → focus/drag/resize/maximize/fullscreen → destroy. Focus is a single `Option<u32>` with modal-chain redirection and implicit mouse-down capture (`mouse_down_capture`). IPC is the anyOS event channel (5×u32 packets); commands 0x1000–0x1FFF, responses 0x2xxx, events 0x3xxx.

The dominant architectural weakness is that the global `unsafe` `Desktop` singleton concentrates ALL state (35+ fields, window list, input state, clipboard, drag, fullscreen, shortcuts, multi-monitor) behind one coarse lock and one giant `Desktop` impl spread across files; combined with `panic = "abort"` and no per-client fault isolation, any unguarded slice/pointer access from a malformed client message can abort the whole desktop session.

### Problems
- **[CRITICAL/compositor/effort:medium]** present_ipc_window reads width×height u32s from a client SHM whose size is never validated → out-of-bounds read aborts the whole compositor
    - evidence: desktop/window.rs:2305-2306 builds `src_slice = from_raw_parts(shm_ptr, (shm_w*shm_h) as usize)` where shm_w/shm_h come from the client-declared content_w/content_h (set in create_ipc_window window.rs:2013-2014, validated only against MAX_WINDOW_DIM=8192 / 16M pixels in desktop/mod.rs:415-450). The compositor maps the SHM with `ipc::shm_map(shm_id)` (desktop/ipc.rs:106) which returns only an address — there is NO syscall to query the region's byte size (confirmed: libs/stdlib/src/ipc.rs:161 `shm_map` returns u32 addr only; no shm_size syscall exists). kernel maps whole pages (shared_memory.rs:182-205). So a client can CREATE_WINDOW declaring 8192×8192 (256 MB) backed by a 1-page SHM, then CMD_PRESENT: the scaled loop (window.rs:2314-2328) or the row-copy (2333-2344) reads far past the mapping → page fault. Because Cargo.toml:16 sets `panic = "abort"` and there is no per-client fault isolation, this kills the entire compositor/desktop session.
    - impact: A single buggy or malicious GUI app crashes the whole desktop (all windows, dock, menubar) by lying about its surface size. Also a non-malicious cause: app frees/reallocates its SHM smaller than declared, then the compositor over-reads.
    - fix: Add a kernel syscall to return a mapped SHM region's byte size (region.physical_frames.len()*FRAME_SIZE) and store it on WindowInfo at map time; in present_ipc_window clamp src_count to shm_byte_size/4 and reject CREATE_WINDOW/RESIZE_SHM if width*height*4 > region size. Until then, at minimum clamp every SHM read (`src_end = (src_off+w).min(src_slice.len())` is already done for the row path at 2337 but the SCALED path at 2322-2323 indexes `src_slice[src_row_off + src_x]` with NO bound check — fix that immediately).
- **[HIGH/compositor/effort:small]** CMD_PRESENT has no owner-TID check — any app can force-present/dirty another app's window
    - evidence: desktop/ipc.rs:167-187 CMD_PRESENT reads `window_id = cmd[1]` and calls `present_ipc_window(window_id, dirty_rect)` with no `owns_window()` guard, unlike CMD_DESTROY_WINDOW (ipc.rs:132), CMD_MOVE_WINDOW (ipc.rs:206), CMD_MINIMIZE (ipc.rs:458) etc. which all call `self.owns_window(owner_tid, window_id)`. CMD_SET_TITLE (ipc.rs:188) and CMD_GET_WINDOW_POS (ipc.rs:754) similarly accept any window_id. The dirty-rect fields cmd[3]/cmd[4] are clamped inside present_ipc_window (window.rs:2267-2280), so this is not itself an OOB, but it lets any app trigger an SHM-read + recomposition of an arbitrary window and read another window's position.
    - impact: Cross-app interference / minor info leak (window positions). Combined with the unvalidated-SHM bug above, a malicious app could also try to drive another window's present path. Breaks the per-window ownership model the rest of the IPC surface enforces.
    - fix: Add `owner_tid` to the CMD_PRESENT / CMD_SET_TITLE / CMD_GET_WINDOW_POS packets (or look up the channel's authenticated TID from the event-channel sender rather than trusting cmd fields) and gate on owns_window(). The event-channel layer should ideally tag every command with the verified sender TID so the compositor never trusts caller-supplied TIDs (it already does the right thing for CMD_DRAG_BEGIN at ipc.rs:502-507).
- **[HIGH/compositor/effort:small]** Crash-reap path (on_process_exit/destroy_window) leaks the compositor's SHM mapping for every closed/crashed window
    - evidence: desktop/window.rs:848-889 `destroy_window()` removes the layer and window but NEVER calls `shm_unmap(shm_id)`. The SHM is only unmapped on the explicit IPC path: desktop/ipc.rs:143-145 CMD_DESTROY_WINDOW unmaps then calls destroy_window. But the crash path — reap_exited_processes (window.rs:920-947) → on_process_exit (window.rs:892-917) → destroy_window — bypasses the unmap entirely. Kernel cleanup_process (shared_memory.rs:362-401) strips the dead client's mapping but the region stays alive because the compositor still holds its mapping (frames freed only when mappings empty AND owner_tid==0). So each crashed/closed-via-reap app permanently leaks one window-sized mapping + keeps its physical frames pinned in the compositor's address space.
    - impact: Long-running sessions with many app crashes/launches steadily leak compositor virtual address space and pin physical frames (a full-screen window is multiple MB). Eventually shm_map fails / OOM. Directly worsens problem #3 (stability) and #9 (memory).
    - fix: Move the shm_unmap (and shm_destroy if compositor-owned) into destroy_window() itself so both the IPC and reap paths free the mapping. Also unmap menu/status-icon/drag-image SHMs there. Add a debug counter of live SHM mappings to MGMT-STATS to catch regressions.
- **[CRITICAL/stability/effort:large]** No per-client fault isolation: any unguarded slice index / pointer deref from client input aborts the entire desktop
    - evidence: Cargo.toml:16 `panic = "abort"`; render.rs:25 single `static mut DESKTOP_PTR` shared by both threads; all client-driven handlers run in-process under the shared lock (app/ipc.rs, desktop/ipc.rs). There is no supervisor/restart of the compositor itself (management.rs restarts login/dock but nothing restarts the compositor). Reachable abort sources include the scaled-present OOB (window.rs:2322), the unvalidated SHM size (problem #1), and any future `[idx]` on attacker-influenced data. A panic while holding DESKTOP_LOCK also means the OTHER thread is left spinning forever on acquire_lock (render.rs:36-41 has no poison/timeout) — but since panic=abort the whole process dies first.
    - impact: The compositor is a single point of failure for the entire GUI; one bad frame from one app = total session loss. This is the structural root of problem #7 (fragile compositor).
    - fix: (a) Wrap the client-command dispatch in defensive validation (never index client-controlled lengths without .min(len)). (b) Consider catching panics is impossible under no_std/abort, so instead make the compositor restartable: have a tiny supervisor (or the kernel) re-exec the compositor and have clients reconnect, OR move the per-window SHM blit into a bounded, panic-free routine. (c) Add a lock acquisition timeout/watchdog so a stuck thread is detectable.
- **[HIGH/compositor/effort:medium]** Events are silently dropped to slow/stuck clients (256-deep per-window queue) and emit_to_target can block the management/render thread on a full client channel
    - evidence: window.rs:1100-1106 push_event drops events when `win.events.len() >= 256` with no notice. drain_ipc_events (desktop/ipc.rs:26-68) and management.rs:512-516 then call emit_to_target → ipc::evt_chan_emit_to (app/ipc.rs:11-13). The render thread comment at render.rs:176-178 explicitly notes evt_chan_emit_to 'may block if an app's event queue is full (slow app)'. While the frame-ACK emit was moved outside the lock, the management thread's per-event emit loop (management.rs:512) is serial: one slow/stuck client that never drains its channel can stall delivery of events to ALL other apps for the duration of each blocked emit.
    - impact: A hung GUI app causes input lag / lost key/mouse events for every other window (focus feels 'lost', clicks dropped) — directly the 'lost focus / dropped key/pointer delivery' fragility in problem #7. Silent 256-cap drops cause apps to miss MOUSE_UP (stuck pressed buttons) or CLOSE events.
    - fix: Use non-blocking emit (try_emit) and drop/coalesce on a per-client basis instead of blocking the shared thread; track a per-client 'unresponsive' flag and stop emitting (and reap) clients whose channel has been full for N ms. For the 256-cap, at least coalesce mouse-move events and never drop MOUSE_UP/WINDOW_CLOSE/FOCUS_LOST (prioritized queue).
- **[MEDIUM/compositor/effort:medium]** Key/pointer events are delivered to windows that may be dead; focus fallback after destroy can hand input to popups/about-to-die windows
    - evidence: handle_scroll (input.rs:1222-1229) and handle_key (input.rs:1727-1729) push to self.focused_window with no check that the owner is alive (reaping is only every 250ms, management.rs:128 REAP_INTERVAL_MS). push_event just no-ops if the window id is gone (window.rs:1101) so it won't crash, but events queue to a window whose owner died until the next reap. destroy_window's focus fallback (window.rs:865-882) does `self.windows.last()` to pick the next focus — `last()` is the top of z-order which may be a borderless always-on-top popup/dropdown or another app's modal, not the user's intended next window, causing focus to jump unexpectedly. inject_key_event (input.rs:1859-1862) likewise targets focused_window unconditionally.
    - impact: Focus stealing / wrong-window focus after a window closes; keystrokes briefly delivered to a dead window between crash and reap. Contributes to 'focus stealing, lost focus' in problem #7.
    - fix: In the focus fallback prefer the most-recently-focused NON-borderless, owner-alive, non-modal window (maintain a small focus history stack) rather than windows.last(). Validate owner liveness (cheap: the window must still exist; for dead-owner detection trigger an immediate targeted reap when delivery to focused window fails repeatedly).
- **[MEDIUM/performance/effort:large]** Multi-monitor secondary outputs re-composite their entire framebuffer (full nearest-neighbor wallpaper rescale) every frame the primary has damage
    - evidence: compositor/mod.rs:666-767 render_secondary_outputs runs whenever `force` is true (called from desktop/mod.rs:1195 with `had_damage` from the PRIMARY). It rescales the wallpaper per-frame with a per-pixel divide loop (mod.rs:748-756 `sx = x*sw/dst_w`), recomputes shadows per-frame (comment mod.rs:682-686 'recompute per frame'), and has no per-output damage tracking — `Output.damage` exists (mod.rs:66) but this path ignores it and redraws the whole output. So any single-pixel change on the primary triggers a full re-blit + rescale of every secondary output.
    - impact: On a 2+ monitor setup, cursor movement or a blinking caret on the primary forces a full-screen recomposite of every other monitor → high CPU and dropped frames. Directly problem #9 (performance) and #7 (multi-monitor fragility).
    - fix: Track per-output damage in virtual coords (intersect global damage rects with each output rect) and only re-blit changed regions; cache the per-output scaled wallpaper (it's static — the comment at mod.rs:733-735 already admits this) and the shadow alpha caches per output. Gate the whole pass on whether damage actually intersects that output's rect, not on primary had_damage.
- **[MEDIUM/compositor/effort:small]** copy_shm_to_pixels reads client SHM outside the lock during CREATE_WINDOW pre-render (TOCTOU / undersized-SHM read)
    - evidence: app/ipc.rs:80-109: after `shm_map(shm_id)` the chrome pre-render calls `copy_shm_to_pixels(&mut pre_pixels, width, title_bar_height(), shm_addr as *const u32, width, height)` (ipc.rs:101-108) BEFORE acquire_lock (the lock is taken at ipc.rs:111). copy_shm_to_pixels (window.rs:3101-3109) does `from_raw_parts(shm_ptr, (shm_w*shm_h) as usize)` — same unvalidated size as problem #1, and here it runs on freshly-mapped memory the client could be racing to shrink. validate_window_surface was checked (ipc.rs:72-78) but only bounds w/h, not the SHM size.
    - impact: Same OOB-read → desktop abort risk as problem #1, on the window-creation path; plus a TOCTOU window where the client controls the SHM between map and read.
    - fix: Same SHM-size validation as problem #1; clamp the source slice length in copy_shm_to_pixels (window.rs:3109) to the known region byte size.
- **[MEDIUM/file-length/effort:large]** God-struct Desktop + 3000-line window.rs / 2200-line input.rs / 1500-line mod.rs concentrate all state and logic; no enforced module boundaries
    - evidence: desktop/window.rs is 3123 lines mixing WindowInfo, hit-testing, chrome rendering, present, fkey shortcut slots, the shortcut overlay (~600 lines of UI), and multi-monitor reflow. desktop/input.rs is 2209 lines. desktop/mod.rs defines a Desktop struct with 35+ pub(crate) fields (mod.rs:134-283) touched by every other module. compositor/mod.rs is 1509 lines. All Desktop methods are `impl Desktop` blocks scattered across window.rs/input.rs/ipc.rs/drag.rs so there is no encapsulation: any file can mutate any field.
    - impact: Problems #1 and #2: hard to reason about invariants (e.g. that shm_ptr matches shm_width*shm_height), hard to test in isolation, easy to introduce the kind of unchecked-index bugs that abort the desktop. High change-risk.
    - fix: Split files as noted in key_files. More importantly, encapsulate the SHM invariant: make shm_ptr/shm_id/shm_width/shm_height private behind a `WindowSurface` type whose only read accessor returns a correctly-bounded slice, so present/hit-test/overlay can never construct an oversized from_raw_parts.
- **[LOW/compositor/effort:medium]** No vsync / per-output FLIP synchronization in the non-double-buffer and secondary-output paths → tearing
    - evidence: flush_cursor_region (gpu.rs:194-209) and flush_region issue GPU_UPDATE immediately for the non-hw_double_buffer path; secondary outputs copy back_buffer straight to fb_ptr (mod.rs:705-766) with a SYS_DISPLAY_FLUSH and no page flip. Only the primary hw_double_buffer path uses GPU_FLIP (compositing.rs:134). Frame pacing is a fixed 16ms sleep (render.rs:208-216) not tied to scanout.
    - impact: Visible tearing on memcpy/GMR-only GPUs and on all secondary monitors; not a crash but a quality/fragility issue under problem #7.
    - fix: Where the GPU supports it, route secondary outputs through a double-buffer + FLIP like the primary; otherwise flush only damaged tiles to minimize the tear window. Tie frame pacing to a vblank/FLIP-complete signal if the kernel GPU layer can provide one.
- **[LOW/performance/effort:small]** emit_to_registered_apps and clipboard re-alloc are O(n) under repeated lock round-trips; broadcast on every window open/close
    - evidence: app/ipc.rs:15-29 emit_to_registered_apps acquires/releases the lock to snapshot subs then emits serially; called for EVT_WINDOW_OPENED/CLOSED on every create/destroy (app/ipc.rs:298-312) and for theme/scale/font changes. CMD_LIST_WINDOW_TIDS (app/ipc.rs:226-263) takes the lock three separate times for one command. Clipboard GET reallocates compositor SHM whenever a larger payload arrives (desktop/ipc.rs:663-694) with no shrink/reuse policy.
    - impact: Minor CPU and lock-contention overhead; lock churn adds latency to input under bursty window churn.
    - fix: Snapshot the needed state in one lock section per command; batch broadcasts. Keep the clipboard SHM at a high-watermark capacity (already partly done) and avoid re-map per request.
- **[LOW/stability/effort:small]** next_window_id / next_layer_id are plain `+= 1` with no wraparound or reuse handling
    - evidence: window.rs:720-721, 1969-1970, 2071-2072, 2127-2128 do `let id = self.next_window_id; self.next_window_id += 1;` and compositor/mod.rs:1051-1052/1088-1089/etc do the same for layer ids. No wraparound check; at u32::MAX this overflows (panic in debug, wrap in release). Window lookup is by linear scan of id, so a wrapped id colliding with a live id would misroute commands.
    - impact: Only reachable after ~4 billion window creations, so practically low — but a very long-lived session with rapid window churn could in principle hit it, and an overflow under debug would abort.
    - fix: Use wrapping_add and skip ids that are still in use, or use a free-list. Low priority but trivial to harden.

### Refactor opportunities
- Encapsulate the window surface: replace the raw shm_ptr/shm_id/shm_width/shm_height quartet on WindowInfo with a WindowSurface type whose only pixel accessor returns a length-correct slice (kills the unbounded from_raw_parts pattern at window.rs:2306, 2322, 3109 in one place).
- Add a kernel SYS_SHM_SIZE syscall and have the compositor validate width*height*4 <= region_size on CREATE_WINDOW/RESIZE_SHM (closes problems #1 and #7).
- Tag every event-channel command with the kernel-verified sender TID so the compositor never trusts caller-supplied owner_tid fields (CMD_PRESENT/SET_TITLE/GET_WINDOW_POS gating, problem #2).
- Move shm_unmap into destroy_window() so crash-reap and IPC-destroy share one cleanup path (problem #3).
- Split desktop/window.rs (3123) and desktop/input.rs (2209) along the lines in key_files; reduce the Desktop god-struct by grouping related fields (clipboard, drag, fullscreen, multimon, shortcuts) into sub-structs.
- Replace per-frame full secondary-output recomposite with per-output damage tracking + cached scaled wallpaper + cached shadow alphas (problem #7).
- Make event emit non-blocking (try_emit) with per-client unresponsive detection so one hung app can't stall global input delivery (problem #5).
- Introduce a lock-acquisition watchdog/timeout to detect a thread stuck under the spinlock instead of silently hanging.
- Make the compositor restartable (supervisor re-exec + client reconnect) so it is no longer an unrecoverable single point of failure given panic=abort (problem #3).

### Test gaps
There are essentially no automated tests for the compositor — it can only be exercised by booting the full GUI in QEMU. The CLAUDE.md AnyStream/offscreen-SHM plan (Phase 1: WindowType::Stream + offscreen framebuffer + anyos_testkit) is the right vehicle for headless compositor tests: it would let a test client LAUNCH a window, drive INPUT_KEY/INPUT_PTR, and read back the offscreen SHM pixels to assert on composited output without a physical display. Concretely missing and testable: (1) malformed-IPC fuzzing — send CREATE_WINDOW/RESIZE_SHM/PRESENT with oversized width/height vs a tiny SHM and assert the compositor rejects them instead of aborting (this is the headline bug, problem #1); (2) crash-isolation test — spawn a client, kill it mid-frame, assert the compositor survives, the window is destroyed, AND the SHM mapping count returns to baseline (catches the leak in problem #3); (3) focus-routing tests — open A, open modal B, click A, assert focus redirects to B; close focused window, assert focus falls back to the right window not a popup (problem #6); (4) event-backpressure test — a client that never drains its channel must not stall event delivery to a second client (problem #5); (5) ownership tests — app1 sends CMD_PRESENT/CMD_MOVE for app2's window_id and is rejected. Many of these can be pure-logic kunit-style unit tests if Desktop is refactored so its methods take an injectable surface/IPC abstraction (currently impossible because of the global `static mut DESKTOP_PTR` and direct `anyos_std::ipc` syscalls — that coupling is itself the main testability blocker). A headless serial-driven smoke test (boot compositor, spawn a known-good app, assert 'first_present' log line appears) is cheap and would catch gross regressions today.

### Open questions
Does the event-channel layer (anyos_std::ipc::evt_chan_*) already expose the authenticated sender TID, or must commands carry owner_tid in their payload? If the former, CMD_PRESENT/SET_TITLE ownership gating is trivial; if the latter, the kernel needs a small change. Also: can the kernel GPU layer signal FLIP-complete/vblank so frame pacing and secondary-output flips can be made tear-free (problem #9 vsync)? And is there an existing SHM-size accessor anywhere (I found none in libs/stdlib/src/ipc.rs or kernel/src/syscall/handlers/ipc.rs) — confirming a new syscall is required for the headline fix.

## LIBANYUI — libanyui (server-side GUI framework, runs in compositor process) + libanyui_client wrapper

**Architecture:** libanyui is an OOP retained-mode widget toolkit compiled as a shared library (.so) loaded by GUI apps via dl_open. All state lives in one process-global `static mut STATE: Option<AnyuiState>` (lib.rs:423), accessed through `state()` which hands out `&'static mut AnyuiState` (lib.rs:425-431). AnyuiState owns every widget in a single flat `Vec<Box<dyn Control>>` (lib.rs:281), plus parallel Vecs of windows/comp_windows and all tracking state (focused/pressed/hovered/popup/drag/modal_stack/timers). Each widget implements the `Control` trait (control.rs:745), embedding a `ControlBase` (id, parent, children: Vec<ControlId>, geometry, dirty flag, 26-slot callback table). Parent/child links are by ControlId, so every tree operation resolves IDs through `find_idx` (control.rs:1047), an O(n) linear scan over the flat Vec.

The event loop (event_loop.rs, 4270 lines) runs a strict phased `run_once()` (event_loop.rs:105): drain marshal queue, fire timers, kinetic scroll, tooltip, drain ALL compositor events into a Vec, dispatch per-window via hit-testing and virtual handlers (collecting deferred callbacks into `pending_cbs`), close windows, then Phase 3 fires all user callbacks "with no borrows held" (event_loop.rs:2643-2646), then layout (3.5), dirty-rect collection (3.7), and double-buffered incremental render to per-window back buffers + SHM with VSync back-pressure (Phase 4). This deferred-callback model is a genuinely good design choice that avoids re-entrant mutation of the controls Vec during dispatch.

Rendering targets a `Surface` (draw.rs:11) — a thin `*mut u32` + dims + clip rect — so render/layout/hit-test are pure functions over the buffer and tree, which makes the engine headlessly testable in principle. Layout is a Windows-Forms-style single-pass dock algorithm (layout.rs:25) plus per-control `layout_children()` overrides for StackPanel/FlowPanel/Toolbar. The compositor is reached not through linking but by casting a fixed virtual address 0x04380000 to an export struct (compositor.rs:7,133).

The client wrapper (libanyui_client) resolves all 241 exports via dl_sym into a `static mut LIB` (anyos_rest.rs:414), wraps them in typed `Control`/`Window` structs, and converts Rust closures into extern "C" thunks via a `static mut HANDLERS: Vec<Box<dyn FnMut>>` registry (events/mod.rs:25-45).

### Key files
- `libs/libanyui/src/lib.rs` (4808 lines) — God-file: global AnyuiState, init/shutdown, 241 #[no_mangle] FFI exports covering window mgmt + every control's API (DataGrid/TextEditor/TreeView/Canvas/TextField), dialogs, callbacks, theme, clipboard, modal stack, tray, menus  **[SPLIT]** Split per-control FFI into per-control ffi modules (ffi/data_grid.rs, ffi/text_editor.rs, ffi/canvas.rs, ffi/treeview.rs, ffi/textfield.rs); move window lifecycle to ffi/window.rs, properties/layout to ffi/props.rs, theme/clipboard/scale to ffi/system.rs, message_box/modal to dialogs.rs. Keep AnyuiState struct + state() in a small core.rs. Target <800 lines/file.
- `libs/libanyui/src/event_loop.rs` (4270 lines) — Single run_once() with ~10 inline phases; per-event dispatch with deeply nested combobox/dropdown/autocomplete/drag special-casing; dirty-rect collection; tree render; scroll-blit damage  **[SPLIT]** Extract: dispatch/mouse.rs, dispatch/keyboard.rs (the inline combobox/dropdown/autocomplete KEY_DOWN handling ~event_loop.rs:1860-2095 should move into those controls as virtual methods), dispatch/drag.rs (already partly factored), render/tree.rs (render_tree, collect_dirty_rects, scroll-blit), focus.rs (cycle_focus, clear_tracking_for). run_once() should orchestrate, not implement.

### Problems
- **[HIGH/libanyui/effort:medium]** Closure registry leaks every registered callback and is re-entrancy-unsafe (UB)
    - evidence: libanyui_client/src/events/mod.rs:25-45. `static mut HANDLERS: Option<Vec<Box<dyn FnMut(u32,u32)>>>`; `register()` does `handlers().push(Box::new(f))` and never removes — every on_click/on_change/per-row/per-rebuild closure is leaked permanently. Worse: `closure_thunk` (line 32) takes `let h = handlers()` (a &'static mut into the Vec) then calls `h[idx](id, event_type)`. If that user closure registers a new callback (extremely common: a click handler that builds new widgets with their own callbacks), the nested `handlers().push()` aliases the same Vec while `h` is a live &mut borrow, and a reallocation invalidates the `h[idx]` reference — mutable aliasing + potential use-after-realloc UB.
    - impact: Continuous memory growth in any app that rebuilds UI or attaches per-item callbacks (file managers, data grids, mail lists). Intermittent crashes/corruption when a callback registers another callback and the Vec reallocs.
    - fix: (1) Index the handler by control-id+event-type so re-registration replaces instead of appending, freeing the old Box. (2) In closure_thunk, copy the raw fn-pointer/Box pointer out before invoking so no &mut borrow of HANDLERS is held during the call; or take the closure out, call it, put it back (or use a slotmap with stable addresses, e.g. Vec<Box<...>> where you clone the raw pointer to the trait object and call through it). (3) Provide an unregister path tied to control removal.
- **[HIGH/libanyui/effort:large]** Nested re-entrant event loop in anyui_message_box aliases the global &mut STATE
    - evidence: lib.rs:3789-3798 — anyui_message_box runs `while !MSGBOX_DISMISSED { event_loop::run_once(); sleep(16); }`. run_once() begins with `let st = crate::state()` which is `&'static mut AnyuiState` (lib.rs:425). If anyui_message_box is called from inside a user callback — which executes during Phase 3 of an OUTER run_once that already holds `let st = state()` — the inner run_once obtains a second `&mut` to the same AnyuiState. Two live `&mut` to the same object is undefined behaviour in Rust and can corrupt state on optimization. The busy `sleep(16)` polling and the `static mut MSGBOX_DISMISSED` (lib.rs:3524) compound the fragility (only one modal at a time; nested modals share the flag).
    - impact: Message boxes shown from button handlers (the normal case) are a latent UB/corruption source; nested message boxes (e.g. confirm inside a save handler) can dismiss the wrong dialog.
    - fix: Make state access go through a re-entrancy guard or RefCell-like single borrow that asserts on nested borrow (at minimum debug_assert to surface the bug). Better: implement message boxes as real non-blocking modal windows (modal_stack already exists at lib.rs:387) with a completion callback, instead of a nested run_once. If a blocking API must remain, have it NOT hold the outer borrow — restructure run_once so STATE is borrowed per-phase, not for the whole function.
- **[HIGH/performance/effort:medium]** O(n) find_idx makes all tree traversal and UI construction O(n²)
    - evidence: control.rs:1047 `find_idx` is `controls.iter().position(|c| c.id()==id)` — linear scan. It is called 127 times across the codebase, recursively inside hit_test (control.rs:1141), hit_test_any (1275), cursor_at_point (1214), abs_position (1291), collect_dirty_rects (event_loop.rs:3898,3964), render_tree (event_loop.rs:4012), layout.rs (8 call sites). Every MOUSE_MOVE event runs hit_test_any + cursor_at_point + abs_position + several find_idx (event_loop.rs:688-790) — i.e. multiple O(n²) tree walks per high-frequency event. Additionally every FFI mutator (anyui_set_text lib.rs:781, set_position:810, set_size:819, set_visible:836, add_child, etc.) does its own `controls.iter().find(|c| c.id()==id)`, so constructing a UI of N controls is O(N²), and anyui_remove (lib.rs:3918) uses `to_remove.contains(...)` inside retain (O(n·m)).
    - impact: Sluggish hover/scroll and slow startup on dense UIs (DataGrid with many cells, anycode, mail lists). The CLAUDE.md performance goal (#9) is undermined inside the toolkit itself.
    - fix: Add an `id -> index` HashMap (or a generational slotmap) to AnyuiState, kept in sync on insert/remove, and have find_idx/FFI lookups use it (O(1)). Since IDs are dense u32 from next_id, even a Vec<Option<usize>> indexed by id works. This alone removes the dominant O(n²) factor everywhere.
- **[MEDIUM/libanyui/effort:medium]** Single-pass dock layout: DOCK_FILL ordering and zero-size docked controls are structural fragilities
    - evidence: layout.rs:25-98. dock_layout iterates children in insertion order, mutating area_left/top/right/bottom as it goes. DockStyle::Fill (line 85) consumes whatever remains AT THAT MOMENT, so a Fill added before Top/Bottom/Left/Right siblings claims the whole area and the later docked controls overlap it — exactly the documented 'DOCK_FILL must be added last' pitfall (CLAUDE.md). Top/Bottom take the child's CURRENT `.h` as authoritative (lines 50,59) and Left/Right take `.w`; a control left at default size (0,0) gets width/height set on the cross axis but stays 0 on the main axis → invisible. This is the 'Toolbar (0,0) invisible' pitfall; Toolbar works around it with a control-level MIN_HEIGHT (toolbar.rs:11,23) but generic Views/status bars do not.
    - impact: Layout depends on child-add order and on apps pre-setting sizes; violating either yields invisible or overlapping controls with no error. Fragile to maintain and a recurring app-developer trap (documented as pitfalls rather than fixed).
    - fix: Make dock layout order-independent: process Fill last regardless of insertion order (partition children by dock style: edges first in declared priority, Fill afterward). Give docked controls a sensible default extent on the docked axis when their size is 0 (e.g. from ControlKind::default_size or a min). Surface a debug warning when a docked control has 0 extent on its main axis.
- **[HIGH/stability/effort:medium]** Control removal does not clear all dangling ControlId references
    - evidence: anyui_remove (lib.rs:3888-3919) and clear_tracking_for (event_loop.rs:3472-3489) only reset focused/pressed/hovered. They do NOT clear: active_tooltip, tooltip_pending_id (lib.rs:321-323), last_click_id (303), drag.source_id/target_id and incoming_drag.target_control, modal_stack entries, or popup.menu_id/owner_* (lib.rs:159-168). Removing a control that owns the open context-menu popup, is the active drag source/target, has a pending tooltip, or was the last click target leaves AnyuiState holding a stale ControlId. Subsequent find_idx returns None (graceful) in some paths, but e.g. an open popup whose menu_id was removed, or a drag whose source vanished, can dispatch against a freed id.
    - impact: Crashes/visual glitches when apps dynamically remove controls (clearing list rows while a context menu/tooltip/drag is active). Hard-to-reproduce because timing-dependent.
    - fix: Centralize teardown in one function that, for each removed id, clears EVERY AnyuiState field that can hold a ControlId (focused, pressed, hovered, active_tooltip, tooltip_pending_id, last_click_id, drag, incoming_drag, popup if menu_id/owner matches, modal_stack). Call it from anyui_remove, anyui_clear_children, and window close. Add a debug assertion in run_once that no tracking field points to a non-existent id.
- **[MEDIUM/stability/effort:small]** Compositor accessed via unchecked fixed-address struct cast (no magic/version validation)
    - evidence: compositor.rs:7 `LIBCOMPOSITOR_BASE: usize = 0x0438_0000`; compositor.rs:133-135 `exports() { unsafe { &*(LIBCOMPOSITOR_BASE as *const LibcompositorExports) } }`. The struct carries magic/version/num_exports fields (lines 12-14) but they are never read. Every compositor call (init, present, poll_event, resize_shm, ...) blindly dereferences function pointers at hardcoded offsets. If libcompositor.dlib is not mapped at that address, is an incompatible version, or its export-table layout drifts from this `#[repr(C)]` mirror, the function pointers are garbage and the first call crashes.
    - impact: Silent, total breakage on any compositor ABI change; no graceful failure or diagnostic. Tight, undocumented coupling that defeats the intended 'goes through libcompositor.dlib' abstraction (lib.rs:10-11).
    - fix: Validate magic + version + num_exports in compositor::init() and fail anyui_init() with a clear log if they mismatch. Better long-term: bind the symbols through dl_sym like libanyui_client does for libanyui, instead of a raw address cast, so the loader resolves offsets.
- **[MEDIUM/libanyui/effort:small]** Marshal queue silently drops UI updates on overflow and runs arbitrary callbacks mid-drain
    - evidence: marshal.rs:106-113 marshal_push does `let _ = (*queue).push(cmd)` — when the 256-entry ring is full (marshal.rs:18,85) the command is discarded with no signal. In drain() (marshal.rs:117), the Dispatch variant invokes `(callback)(userdata)` (line 164) while inside run_once with `st: &mut AnyuiState` borrowed; that callback can call anyui_* FFI which calls state() again → the same nested-&mut aliasing as the message-box issue.
    - impact: Worker threads that burst >256 updates (download progress, log streaming) silently lose UI state with no error. Dispatch callbacks can re-enter state() and corrupt it.
    - fix: Return a bool / set an overflow flag from the marshal API so callers can retry/backpressure, or make the queue grow. For Dispatch, queue the callback into the same pending_cbs mechanism the event loop already fires after releasing the st borrow, rather than invoking it during drain.
- **[LOW/libanyui/effort:small]** Toolbar::set_size override bypasses dirty-rect old-bounds preservation
    - evidence: toolbar.rs:91-96 overrides set_size and directly assigns base.w/base.h + mark_dirty, unlike the trait default set_size (control.rs:963-975) which preserves prev_w/prev_h so collect_dirty_rects (event_loop.rs:3934) can union the vacated area. A toolbar that shrinks via set_size won't repaint the area it vacated.
    - impact: Stale pixels when a toolbar is resized smaller (minor visual artifact).
    - fix: Have the override preserve prev_w/prev_h before mutating (mirror the trait default), or fold the MIN_HEIGHT clamp into the default set_size path so no override is needed.
- **[LOW/libanyui/effort:small]** Documented widget pitfalls are stale relative to current code
    - evidence: CLAUDE.md pitfalls claim 'IconButton text+icon overflow: icon (16px centered) + text below overflows' and 'Toolbar defaults to (0,0) and is invisible'. But icon_button.rs:181-220 lays icon+text out HORIZONTALLY ([pad|icon|gap|text|pad]) with auto-size width (icon_button.rs:49-71), and toolbar.rs:11,23 enforces MIN_HEIGHT=36. The behavior the docs warn about no longer matches the code.
    - impact: App developers follow obsolete workarounds (text-only/icon-only buttons, manual toolbar sizing) and avoid features that actually work, perpetuating the perception that libanyui is finicky.
    - fix: Reconcile docs/anyui-api.md and CLAUDE.md pitfalls with current control behavior; where the framework now handles a case automatically, document that. Where a real constraint remains (DOCK_FILL order), prefer fixing the engine (see dock-layout finding) over documenting the trap.
- **[MEDIUM/architecture/effort:large]** Inline control-specific logic in the event loop instead of virtual methods (architecture leak)
    - evidence: event_loop.rs hardcodes per-control behavior in the generic dispatcher: ScrollView/Expander offsets are special-cased in hit_test/hit_test_any/cursor_at_point/abs_position/collect_dirty_rects (control.rs:1118-1135,1199-1268, event_loop.rs:3950-3961); KEY_DOWN handling for ComboBox/DropDown/AutoCompleteTextField popups is inlined ~event_loop.rs:1860-2095; Shift+wheel horizontal scroll bypasses the trait via a manual ancestor walk + cast_mut (event_loop.rs:2137-2160). The Control trait exists precisely to encapsulate this, but the event loop reaches in with cast_mut and ControlKind matches.
    - impact: Adding a scrollable/popup control requires editing the 4270-line event loop in many places; the abstraction is not cleanly enforced (problem #2). Each special case is a place bugs hide.
    - fix: Add virtual hooks to the Control trait: child_coordinate_offset() (returns scroll/header offset), wants_key(keycode) / handle_key for popup-owning controls, handle_scroll_x(). Move the ComboBox/DropDown/AutoComplete popup key logic into those controls. Then hit_test/render/dispatch call the hook uniformly instead of matching ControlKind.
- **[MEDIUM/testing/effort:medium]** No automated tests for a 34k-line UI toolkit
    - evidence: No #[test], #[cfg(test)], or mod tests anywhere under libs/libanyui or libs/libanyui_client (grep returned nothing). Yet render targets a plain *mut u32 Surface (draw.rs:11-24) and hit_test/layout/dock_layout are pure functions over &[Box<dyn Control>], so they are eminently unit-testable.
    - impact: Layout/hit-test/dirty-rect regressions (the exact 'finicky' class of bugs) ship undetected; every fix risks silent breakage of another control.
    - fix: See test_gaps — add headless unit tests that build a control Vec, run perform_layout/hit_test/render_tree into a Vec<u32> surface, and assert geometry/pixels. This requires no compositor, no kernel, and runs on the host (the surf-host host feature already proves these crates build for std).

### Refactor opportunities
- Add an id->index map (HashMap or dense Vec<Option<usize>>) to AnyuiState and route all find_idx + FFI id lookups through it — removes the dominant O(n²) factor in traversal, construction, and removal.
- Split lib.rs (4808) by moving each control's ~241 FFI exports into per-control ffi/* modules; keep only AnyuiState + state() + init/shutdown in a core file.
- Decompose event_loop.rs (4270) into dispatch/{mouse,keyboard,drag}.rs, render/tree.rs, focus.rs; run_once becomes an orchestrator. Move inlined ComboBox/DropDown/AutoComplete key handling into the controls via new trait hooks.
- Introduce Control trait hooks (child_coordinate_offset, handle_scroll_x, popup key handling) so ScrollView/Expander/popup special-casing leaves the generic hit-test/render/dispatch code.
- Centralize control teardown so removal clears every ControlId-holding field in AnyuiState (focus/press/hover/tooltip/last_click/drag/incoming_drag/popup/modal_stack).
- Replace the leaking, re-entrancy-unsafe HANDLERS Vec with an id+event-keyed registry that supports replace/unregister and copies the call target out before invoking.
- Make message boxes / modals non-blocking (use existing modal_stack + completion callback) to eliminate the nested-run_once &mut STATE aliasing; add a re-entrancy guard on state().
- Validate compositor export magic/version in init(); ideally bind compositor symbols via dl_sym instead of a fixed-address struct cast.
- Split DataGrid (2031), TextEditor (1866), dialogs (1686), and the client anyos_rest.rs (1959) into model/render/input sub-modules.
- Make dock layout order-independent (process Fill last) and give docked controls a sane default extent on the docked axis, so the documented DOCK ordering / toolbar-sizing pitfalls become engine guarantees rather than developer traps.

### Test gaps
There is zero test coverage. The engine is structured to allow cheap headless testing because the core is pure: (1) Layout — construct a Vec<Box<dyn Control>> (a Window with docked children), call layout::perform_layout, and assert each child's resulting x/y/w/h. This would directly regression-guard the DOCK_FILL-ordering and zero-size-docked-control fragilities. (2) Hit-testing — build a tree, call control::hit_test / hit_test_any at known coordinates, assert the returned ControlId (incl. ScrollView offset, Expander collapse, scrollbar/divider zones). (3) Rendering — allocate `Vec<u32>` of width*height, wrap in draw::Surface::new(buf.as_mut_ptr(), w, h), call event_loop::render_tree, and assert pixel values / non-zero regions; also test the dirty-rect collector (collect_dirty_rects) produces the expected union after set_position/set_size. (4) Dispatch ordering — feed synthetic compositor event arrays [u32;5] into a refactored run_once and assert the deferred pending_cbs order (mouse_down→focus→click→double-click). (5) Client closure registry — test that re-registering on the same control replaces (after the fix) and that a callback registering another callback does not corrupt the Vec. The main blocker is the `static mut STATE`/`static mut HANDLERS`/`static mut QUEUE` globals and the fixed-address compositor cast: tests need a way to init STATE without a live compositor. Recommend a `#[cfg(test)]`/`#[cfg(feature="host")]` stub compositor (the host feature already exists for surf-host) and a state-reset helper, then add a `tests/` module gated on host so `cargo +stable test` runs them. Longer term, kunit-style serial-output checks could exercise the full app path in QEMU, but pure-Rust host unit tests cover the finicky layout/hit-test/render core far faster.

### Open questions
How often do real apps register callbacks dynamically (per-list-row, on rebuild)? That determines how acute the HANDLERS leak/UB is in practice. How frequently is anyui_message_box invoked from inside event callbacks vs. top-level — does the nested-run_once aliasing actually manifest, or has it been masked by the borrow being to a singleton that LLVM happens not to miscompile? Is there a real-world UI with >~500 controls where the O(n²) find_idx is measurably the bottleneck (vs. compositor/SHM throughput)? Whether the compositor export struct layout has ever drifted (would reveal whether the missing magic/version check has bitten before). Whether the 'host' feature on these crates is complete enough to host-run layout/hit-test tests without a compositor stub, or if new test scaffolding is needed.

## TEST-INFRA — Test Infrastructure (kunit)

**Architecture:** anyOS has a Linux-KUnit-style in-kernel test framework under kernel/src/kunit/. It is split into two phases that run *inline during normal boot* (no separate test binary, no host cargo test): (1) UNIT tests (kunit/runner.rs:run_unit_tests, 16 suites in UNIT_SUITES) and (2) INTEGRATION tests (kunit/integration/mod.rs:run_all, 3 suites). The framework core is kunit/mod.rs: a TestContext accumulates pass/fail counts via expect_* methods that print "[FAIL]" lines to serial but never panic, so every test runs to completion. TestSuite/TestCase are static slices registered by hand in two runner files.

Triggering is entirely cfg-gated by `feature = "kunit"`. The feature is declared in kernel/Cargo.toml:11 and wired through cmake/KernelBoot.cmake:84-86 (ANYOS_KUNIT=ON appends "kunit" to --features). The boot orchestrator kernel/src/boot/x86/mod.rs:11-27 calls platform::run_unit_tests() after heap init (line 19) and platform::run_integration_tests() after interrupts+scheduler (line 25); both bodies in kernel/src/boot/x86/platform.rs:49-54 and 186-189 are `#[cfg(feature = "kunit")]` no-ops when the feature is off. There is NO kernel-side poweroff/qemu-exit after tests — boot CONTINUES into storage+userspace (mod.rs:26). scripts/test.sh --kunit therefore polls the serial log for both summary lines and then kills QEMU itself.

Crucially, the unit-test path runs against the REAL subsystems (real heap from memory::heap::init, real memory::virtual_mem.rs on x86_64 — the file named virtual_mem_stub.rs is actually the full 765-line ARM64 implementation aliased only under `#[cfg(target_arch = "aarch64")]` at memory/mod.rs:13-18, NOT a test stub). Integration tests run after full hardware init (ACPI/APIC/IOAPIC/PIT/SMP/scheduler) and verify live hardware/scheduler/heap state. So kunit is a full-fat boot of the real kernel with extra self-checks injected at two boot points — not a reduced harness.

Coverage is concentrated on pure data-structures and memory/scheduler invariants. There is NO coverage for swap, LXE/Linux execution, compositor, real filesystem (exFAT/CoreFS) read-after-write cache coherency, or HAL/driver behaviour beyond ACPI presence. There is NO CI configuration anywhere in the repo.

### Problems
- **[HIGH/testing/effort:medium]** kunit build requires the FULL userspace image, not a kernel-only image — slow and fragile for headless self-test
    - evidence: scripts/test.sh:140-148 configures with -DANYOS_KUNIT=ON then runs bare `ninja -C build` (the default 'image ALL' target). cmake/Targets.cmake:418-421 makes `image` depend on `bios-image`, which (Targets.cmake:156) depends on `${DISK_IMAGE}` + `programs`. `programs` (Targets.cmake:4-16) pulls RUST_USER_BINS, SYSTEM_BINS, APP_BINS, DLL_BINS, DRIVER_BINS, CXX_TOOLCHAIN_DEPS (libc64/libcxx via clang). So a one-line kunit assertion change rebuilds compositor, all apps, libc64, libcxx, libunwind, libc++abi before QEMU even starts. The in-kernel tests do not need ANY of that userspace.
    - impact: Directly determines whether Claude/automation can iterate on kernel fixes quickly and headlessly.
    - fix: Add a dedicated cmake target `kunit-kernel` that builds ONLY ${KERNEL_ELF} + a minimal bootable image (stage1/stage2 + kernel, empty/stub sysroot) and have test.sh build that target instead of the default. Since kunit unit tests run at boot before userspace is loaded, the image needs no /Applications or /System/bin to produce both summary lines. This cuts the edit-test loop from minutes (full clang+rust userspace) to seconds (kernel cargo build only).
- **[HIGH/testing/effort:small]** No kernel-side test completion signal (qemu isa-debug-exit) — test.sh relies on timed log-polling + killing QEMU
    - evidence: kernel/src/boot/x86/mod.rs:25-26 runs integration tests then unconditionally proceeds to init_storage_and_userspace — there is no poweroff after tests. test.sh:197-225 compensates by polling the serial file once per second for both 'KUnit unit: (ALL PASS|FAIL)' and 'KUnit integration: (ALL PASS|FAIL)' lines, then `kill $QEMU_PID`. QEMU is launched with -no-reboot -no-shutdown (test.sh:186-187). If the kernel hangs AFTER integration tests but the lines were already printed it's fine; but if a test triggers a hang/panic mid-suite, detection depends entirely on the 120s timeout and a fragile 'KERNEL PANIC' grep (test.sh:216). There is no machine-checkable exit code path from the kernel.
    - impact: Makes headless runs deterministic and CI-ready; removes the 120s worst-case wait and the kill-race.
    - fix: When feature=kunit, after run_integration_tests() print a sentinel line (e.g. 'KUNIT-DONE rc=N') and then write to the QEMU isa-debug-exit port (already referenced for acpi shutdown in arch/x86/acpi_pm.rs) with exit code = (total_fail==0?0:1). Add `-device isa-debug-exit,iobase=0xf4,iosize=0x04` to the QEMU line in test.sh and treat exit status (rc<<1)|1 as the result. This gives a deterministic, fast termination and a real exit code instead of log-scraping + SIGKILL.
- **[HIGH/testing/effort:xl]** Zero coverage for 5 of the 9 stated problem areas: swap, LXE, compositor, real-FS cache coherency, HAL/driver

## ARCH-BUILD — Cross-cutting architecture & build (kernel/src/main.rs, boot/*, module tree, arch/{x86,aarch64} boundary, Cargo.toml, CMakeLists.txt, cmake/*, build.rs)

**Architecture:** anyOS is a ~156,600-line, 345-file Rust `#![no_std]` kernel targeting x86-64 (primary) and aarch64 (in-progress). The crate root (`kernel/src/main.rs`, 41 lines) is intentionally thin and delegates to a clean staged boot module (`boot/mod.rs` -> `boot/{x86,arm64}/mod.rs`). The x86 boot orchestration (`boot/x86/mod.rs`, 27 lines) is exemplary: it calls a linear sequence of named phases (init_cpu -> init_memory -> run_unit_tests -> init_platform -> init_virtualization -> init_early_drivers -> init_scheduler -> enable_interrupts_and_bind -> run_integration_tests -> init_storage_and_userspace) split across focused submodules. This top-of-tree layering is the strongest part of the codebase.

Below that, the de-facto layering is: arch (HAL) <- memory <- sync/ipc <- drivers <- fs/net <- task (scheduler/loader) <- syscall. The intended boundaries exist as artifacts (an `arch::hal` free-function module, a `drivers::hal::Driver` trait, a `fs::vfs::types::Filesystem` trait) but are pervasively bypassed. There are TWO unrelated things both named "HAL": `arch/hal.rs` (CPU/MMU/timer/interrupt abstraction) and `drivers/hal.rs` (a device-registry `Driver` trait). The arch HAL is a wall of paired `#[cfg(target_arch)]` free functions, not a trait — and it is widely circumvented: 420 direct `crate::arch::x86::` references exist outside `arch/` and `boot/`, plus 590 `#[cfg(target_arch)]` attributes scattered through portable modules. So the arch boundary is porous: the scheduler reaches into `arch::x86::power::wrmsr`, the loader into `arch::x86::syscall_msr` and `arch::x86::cpuid`, and most drivers directly use `arch::x86::port`.

Global mutable state is pervasive and lives mostly behind `Spinlock<Option<T>>`/`Mutex<Option<T>>` boot-initialized singletons (46 instances incl. SCHEDULER, VFS, HAL) plus 69 raw `static mut` (per-CPU arrays in the scheduler: SCRATCH_CTX, SCRATCH_FPU, PER_CPU_THREAD_NAME, PER_CPU_LINUX_ROOTFS, TID_INDEX_CACHE). The `Spinlock<Option<T>>` pattern means every access either unwraps (panic-if-pre-init) or silently no-ops, and the scheduler documents an 8-level manual lock hierarchy in a doc-comment rather than enforcing it in types.

The heaviest layering violations: (1) `fs/vfs/mod.rs` is a 6,952-line god-module that, despite the existence of a clean `Filesystem` trait, still carries 528 exFAT-specific and 248 CoreFS-specific references inline — exFAT durability/commit/retarget-after-rename logic lives directly in the VFS layer, and `VfsState` holds both a generic trait-object path (`root_other`) AND explicit per-FS fields (`exfat_fs`, `fat_fs`, `ntfs_fs`, `corefs_driver`, `mounted_exfat`...), with ~18 `match mnt_fs_type` dispatch sites. The trait migration (labeled "Phase 6") was added but the old enum-dispatch was never removed, doubling the surface. (2) `syscall -> task` coupling is 469 references and `drivers -> task` is 44 (AHCI/NVMe call `scheduler::schedule()`, `contention_backoff`, `deferred_wake` directly for blocking I/O). (3) The IRQ-safe spinlock re-enables interrupts mid-acquisition under contention (a KVM-PLE workaround) which violates the interrupt-disable invariant it is built to provide.

Build: CMake+Ninja drives Cargo with `-Zbuild-std=core,alloc` against custom JSON targets (`x86_64-anyos.json`/`aarch64-anyos.json`). NASM assembles x86 boot/ISR/context-switch/syscall stubs to ELF objects passed to Cargo via the `ANYOS_ASM_OBJECTS` env var; clang assembles the aarch64 `.S` stubs. The 32-bit i686 cross-compiler is no longer needed (HAS_CROSS_COMPILER=FALSE; the C userspace was removed, all userspace is 64-bit Rust + libc64/clang). `cmake/UserPrograms.cmake` is 1,541 lines and assembles ~105 CLI bins + 27 apps + libraries; the disk image is built by a C `mkimage` tool. There is NO fast kernel-only test loop: kunit tests (a respectable 16-suite unit + 3-suite integration framework) run IN-KERNEL during boot gated by the `kunit` feature, so even pure-algorithm tests (buddy, heap-stress, net-types) require a full kernel build + QEMU boot to execute.

### Problems
- **[HIGH/architecture/effort:xl]** VFS layer is not a clean dispatch over the Filesystem trait — exFAT/CoreFS internals are baked into vfs/mod.rs
    - evidence: fs/vfs/mod.rs is 6952 lines (largest file in the kernel) and contains 528 exFAT-specific and 248 CoreFS-specific references. Functions like snapshot_open_exfat_commit (mod.rs:99), finish_detached_exfat_commit (:134), sync_open_exfat_path (:306), retarget_open_exfat_paths_after_rename (:357), and types ExFatReadHint (:635), DetachedExFatWriteResult (:805), PendingExFatAppendFlush (:812) put exFAT durability/commit logic inside the VFS. A clean Filesystem trait DOES exist (fs/vfs/types.rs:69) but VfsState (mod.rs:2000) keeps BOTH a generic trait-object path (root_other) AND explicit per-FS fields (exfat_fs, fat_fs, ntfs_fs, corefs_driver, mounted_exfat, mounted_corefs, iso9660_fs, smbfs, overlay_fs). There are ~18 `match mnt_fs_type { FsType::ExFat => ... }` dispatch sites (mod.rs:1005,1225,1321,1531,...,6656).
    - impact: The trait abstraction (advertised as Phase 6) coexists with the old enum-dispatch it was meant to replace, doubling the code surface, making every new FS feature touch the 7000-line god-file, and coupling VFS correctness to exFAT-specific assumptions. This is the #1 file-length AND #2 architecture problem combined.
    - fix: Finish the Filesystem-trait migration: make every mount a Box<dyn Filesystem>; delete the per-FS VfsState fields and the match mnt_fs_type sites; move exFAT commit/sync/retarget logic into fs/exfat behind trait methods (e.g. a fsync()/durability hook). Then split the remaining vfs/mod.rs into mount.rs, open_files.rs, path.rs, detached_io.rs.
- **[HIGH/hal-driver/effort:xl]** Arch HAL is widely bypassed — 420 direct arch::x86 refs and 590 #[cfg(target_arch)] in portable code
    - evidence: arch/mod.rs and arch/hal.rs document 'Platform-agnostic code should use arch::hal::* instead of directly referencing arch::x86::*'. In practice: 420 `crate::arch::x86::` references exist outside arch/ and boot/, and 590 `#[cfg(target_arch)]` attributes are scattered through the tree. Examples of leakage in supposedly-portable code: task/scheduler/mod.rs:2646 calls arch::x86::power::wrmsr directly; task/loader.rs:157 calls arch::x86::cpuid::features(), :690 arch::x86::syscall_msr::ensure_gs_is_kernel_for_ring3. The HAL is also free-functions with paired #[cfg] bodies (arch/hal.rs has 66 cfg attrs), not a trait, so there is no compile-time guarantee both arches implement the same surface.
    - impact: The aarch64 port cannot be kept correct by construction — every portable module that reached into arch::x86 must be hand-patched with a cfg fork. This is exactly problem #5 (no clean HAL & driver architecture) and a primary reason the ARM64 port stays perpetually 'in progress'.
    - fix: Convert arch::hal into a trait (or a set of traits: CpuOps, MmuOps, IrqController, Timer) with one impl per arch selected once at the module root, so missing methods are compile errors. Then sweep the 420 direct arch::x86 references and route them through the HAL; the remaining genuinely-x86-only call sites (e.g. VMX) should live in x86-only modules, not be cfg-forked inside portable files.
- **[HIGH/swap/effort:xl]** SWAP is a non-functional half-implementation: backing-store registry only, zero eviction/reclaim/page-fault integration
    - evidence: memory/swap.rs (290 lines) docstring explicitly states it 'deliberately keeps the policy bits (page reclaim, victim selection, COW integration) out of the first slice'. It exposes swapon_path/swapoff_path/allocate_slot/free_slot/write_page/read_page/stats — but write_page/read_page/allocate_slot are NEVER called from anywhere outside swap.rs (grep for swap_out/swap_in/store_page/evict_page across the whole kernel returns nothing). The only callers are syscall handlers (syscall/handlers/system.rs:609 swapon, syscall/linux/memory.rs:477) and the stats query. There is no page-fault swap-in path and no reclaim/victim selection anywhere in memory/.
    - impact: `swapon` succeeds and reports stats, but pages are never evicted to swap and under memory pressure the system OOMs / kills instead of swapping. This is exactly problem #6 (no clean SWAP implementation) — the feature is plumbing without a policy engine.
    - fix: Implement the reclaim half: a page-reclaim daemon / on-OOM hook that selects victim user pages (LRU/clock via the accessed bit), calls swap::write_page, unmaps and marks the PTE as swapped (encode SwapSlot in the PTE), and a page-fault handler path that recognizes swapped PTEs and calls swap::read_page to fault them back in. Integrate with COW and the VMA registry.
- **[HIGH/stability/effort:large]** IRQ-safe spinlock re-enables interrupts mid-acquisition under contention, violating its own invariant
    - evidence: sync/spinlock.rs:217-225: inside the acquisition loop, after each 128-PAUSE batch, `if was_enabled { sti(); for _ in 0..4 { spin_loop(); } cli(); }`. The doc-comment (lines 205-216) justifies this as a KVM PLE workaround and a single-CPU lock-holder-preemption escape. The lock is sold as 'Disables interrupts before acquiring the lock' (file header), but a waiter actually runs with interrupts ENABLED for windows during contention.
    - impact: A thread spinning to acquire ANY spinlock can be preempted/take an IRQ mid-spin, so 'I hold IRQs off while waiting' is false under load. This papers over the real defect (locks held far too long — the code itself notes the SCHEDULER lock can be held 100-400ms and documents a manual no-alloc-under-lock rule). It is a likely contributor to the intermittent freezes/login failures in problem #3, and the SPIN_TIMEOUT=10M diagnostic (lines 18,182) is a band-aid for the same.
    - fix: Stop re-enabling IRQs mid-spin. Fix the root cause: never hold SCHEDULER (or any leaf lock) across allocation or long work; convert long-held global locks to finer-grained per-CPU/per-object locks; use a blocking/scheduler-aware mutex (sync/mutex.rs exists) for anything that can contend long, reserving spinlocks for truly short critical sections. For KVM PLE specifically, enable paravirt spinlock hints or simply keep critical sections short enough that PLE never triggers.
- **[MEDIUM/stability/effort:medium]** Scheduler/loader use raw `static mut` per-CPU arrays (UB-prone under Rust 2024 static_mut_refs)
    - evidence: 69 `static mut` across the kernel. The hot ones are in task/scheduler/mod.rs: TID_INDEX_CACHE (:139), PER_CPU_THREAD_NAME [[u8;32];MAX_CPUS] (:164), PER_CPU_LINUX_ROOTFS [[u8;512];MAX_CPUS] (:224), SCRATCH_CTX [CpuContext;MAX_CPUS] (:256), SCRATCH_FPU (:302). These are mutated from context-switch/IRQ paths; taking `&mut` to a `static mut` is increasingly UB-flagged and any aliasing here corrupts scheduler state silently.
    - impact: Silent memory corruption risk on SMP (two CPUs touching adjacent array slots, or a reference aliasing an interrupt that also touches it). Contributes to hard-to-reproduce crashes (problem #3). The arch/hal.rs:254 RBP-clobber panic guard is direct evidence the team has already chased exactly this class of mysterious state corruption.
    - fix: Replace `static mut [T; MAX_CPUS]` with per-CPU `[AtomicU64;N]` (for scalars) or `[SpinlockOrUnsafeCellWrapper; MAX_CPUS]` accessed only via a checked per_cpu(cpu) accessor that asserts cpu==current_cpu_id() for the no-lock fast path. Centralize per-CPU storage in one scheduler/percpu.rs module so the unsafe surface is auditable.
- **[MEDIUM/hal-driver/effort:large]** Two separate things both called 'HAL'; the driver Driver-trait is too thin and most real drivers bypass it
    - evidence: arch/hal.rs (CPU/arch HAL) and drivers/hal.rs (device-registry HAL with a `Driver` trait) are unrelated but share the name. The Driver trait (drivers/hal.rs:104) is just name/driver_type/init/read/write/ioctl — too coarse for block/net/gpu semantics, so although 37 types impl it, the real fast paths (AHCI read_sectors, e1000 TX/RX, virtio_gpu commands) are called directly, not through the trait. Worse, register_device itself forks by arch: x86 takes Option<PciDevice> (drivers/hal.rs:147), aarch64 takes Option<u64> (:171), forcing callers to cfg-split. HalDevice.pci is #[cfg(x86_64)] (:126).
    - impact: The 'device registry' is a thin veneer that doesn't actually mediate device I/O, and its arch-forked signature pushes cfg-noise onto every caller. This is the device half of problem #5 — there is no uniform driver model that block/net/input/display all flow through.
    - fix: Rename one of the two HALs (e.g. arch -> `cpu`/`platform`, keep `drivers::hal`). Make the bus-binding info generic (an enum BusAddr { Pci(..), Mmio(u64), Platform } instead of arch-forked Option types) so register_device has one signature. Define category sub-traits (BlockDevice, NetDevice, DisplayDevice) that the VFS/net/compositor dispatch through, so the registry actually owns the I/O path.
- **[MEDIUM/architecture/effort:large]** Heavy upward/sideways coupling: syscall->task (469), drivers->task (44), net->task (30)
    - evidence: Cross-module reference counts: syscall/ -> crate::task:: = 469; drivers/ -> crate::task:: = 44 (drivers/storage/ahci.rs:955 calls scheduler::schedule(), :956 sleep_until, :643 try_wake_thread/deferred_wake; nvme.rs, usb/mod.rs similar); net/ -> crate::task::scheduler = 30. Drivers reaching into the scheduler for blocking I/O means the storage layer knows scheduler internals.
    - impact: Drivers and the scheduler are mutually entangled, so you cannot reason about (or unit-test) a driver without the scheduler, and the scheduler's lock hierarchy leaks into driver code. Makes the 'no cleanly-enforced architecture' problem concrete.
    - fix: Introduce a narrow blocking-I/O primitive (e.g. an IoWaiter/Completion type in sync/) that drivers use to park and get woken, hiding scheduler::schedule()/sleep_until/deferred_wake behind one interface. Drivers should depend on sync/ + a tiny waitqueue, never on task::scheduler directly.
- **[MEDIUM/testing/effort:medium]** No fast kernel-only test loop — all kunit tests require a full kernel build + QEMU boot
    - evidence: kunit/runner.rs runs UNIT_SUITES (16 suites incl. buddy_tests, heap_stress_tests, net_types_tests, vma_tests, crypto_tests — all pure algorithm/data-structure tests with no hardware dependency) in-kernel after memory::heap::init(), gated by the `kunit` cargo feature (KernelBoot.cmake:84). There is no `cargo test`, no host-runnable harness, and no `kunit`/`test-kernel` CMake target (grep found none in cmake/*.cmake or build.sh). The user's own MEMORY.md notes builds/tests are run manually in QEMU.
    - impact: Iterating on allocator/buddy/net-types logic costs a full Cargo build-std + image + QEMU boot cycle, which is why problem #3 (stability) and #9 (perf in alloc) are hard to iterate on. Directly throttles the velocity needed to fix the other 8 problems.
    - fix: Make the no-hardware unit suites compilable as a host `cargo test` (a thin std shim crate that pulls in buddy.rs/heap.rs/net types behind cfg(test)), OR add a `run-kunit` CMake target that builds with --features kunit and boots QEMU headless with a serial-exit assertion, so the inner loop is `ninja run-kunit` and parses PASS/FAIL from serial.
- **[MEDIUM/file-length/effort:large]** Per-function #[cfg(target_arch)] duplication bloats files and risks x86/aarch64 drift
    - evidence: Many large files duplicate every public function for x86 and aarch64 in the same file: syscall/handlers/display.rs has 64 cfg attrs and every sys_* (sys_screen_size :19/:50, sys_set_resolution :76/:121, sys_audio_write :259/:268, sys_map_framebuffer :401/:476, ...) appears twice; task/loader.rs has 52 cfg attrs with install_sigreturn_trampoline (:53/:100), store_pending_fork (:569/:582), jump_to_user_mode (:1613/:1695) all defined twice. Also memory/virtual_mem.rs (x86, 1996 lines) and virtual_mem_stub.rs (aarch64, 765 lines) are two parallel paging implementations kept in sync only by convention, aliased via `pub use virtual_mem_stub as virtual_mem` (memory/mod.rs) — a misleadingly-named full implementation.
    - impact: Inflates the long-file count and guarantees the two arch bodies drift (a fix to the x86 sys_* is easy to forget on the aarch64 twin). Compounds problems #1 and #5.
    - fix: Where the body is identical except for one HAL call, write it once over the HAL and delete the twin. Where genuinely different, move the aarch64 body into an arch-specific submodule (display_arm64.rs) rather than interleaving in the portable file. Rename virtual_mem_stub.rs to arch/arm64/paging.rs and unify x86/arm64 paging behind a Paging trait.
- **[LOW/architecture/effort:medium]** Global init pattern Spinlock<Option<T>>/Mutex<Option<T>> defers init errors to runtime panics/no-ops
    - evidence: 46 instances of `Spinlock<Option<T>>` / `Mutex<Option<T>>` boot-initialized singletons: SCHEDULER (task/scheduler/mod.rs:132), VFS (fs/vfs/mod.rs:467), HAL (drivers/hal.rs:134), etc. Accessors either .expect()/unwrap (vfs/mod.rs:2019 'VFS must be initialized') or silently do nothing if None. No lazy_static/Once/OnceCell is used.
    - impact: Any code path that touches a subsystem before its init() either panics or silently no-ops, with ordering enforced only by the linear boot sequence — a fragile, runtime-only contract.
    - fix: For genuinely-once init, consider a Once-style cell so first-access initializes or a typed 'Uninitialized' guard; at minimum centralize the accessor so the panic message is uniform and the init ordering is asserted. Lower priority than the trait/swap/lock work.
- **[LOW/stability/effort:small]** Debug/diagnostic artifacts left in hot/fault paths
    - evidence: arch/hal.rs:253-307: set_kernel_stack_for_cpu wraps two trivial calls in an RBP-clobber detector that captures RBP before/after each callee and panic!()s on mismatch — a left-in bisection probe for a past corruption bug. idt.rs embeds a full UART printf (uart_putc/puts/dec/hex, lines 34-115) inside the fault module. task/scheduler/debug_trace.rs is 1297 lines of trace scaffolding compiled into the kernel.
    - impact: Adds overhead and noise to the per-context-switch and fault paths, and the RBP guard can itself panic the kernel. Symptomatic of chasing the static-mut/locking corruption without a root-cause fix.
    - fix: Gate all of this behind a debug_trace cargo feature (or remove the RBP guard now that the cause is suspected to be static-mut aliasing). Move idt diagnostics into a shared low-level serial-diag module reused by spinlock.rs (which has its own copy of the same printf helpers).

### Refactor opportunities
- Finish the Filesystem-trait migration and delete the parallel enum-dispatch + per-FS VfsState fields, then split fs/vfs/mod.rs (6952 lines) into mount/open_files/path/detached_io submodules — single biggest architecture+file-length win.
- Convert arch/hal.rs from paired #[cfg] free functions into a trait (CpuOps/MmuOps/IrqController/Timer) with one impl per arch, then sweep the 420 direct arch::x86 references in portable code through it so the aarch64 port is correct-by-construction.
- Implement the swap reclaim/eviction half (victim selection + PTE swap-encoding + page-fault swap-in) so swapon actually relieves memory pressure.
- Introduce a sync-level blocking-I/O primitive (IoWaiter/Completion + waitqueue) so drivers (AHCI/NVMe/USB) stop calling scheduler::schedule()/sleep_until/deferred_wake directly (cuts the drivers->task coupling from 44).
- Rename one of the two 'HAL's, make register_device bus-address-generic instead of arch-forked, and add category sub-traits so devices actually flow through the registry.
- Replace scheduler/loader raw `static mut [T; MAX_CPUS]` per-CPU arrays with atomic or checked per-CPU accessors centralized in scheduler/percpu.rs; remove the arch/hal.rs RBP-clobber panic guard once root-caused.
- Split idt.rs (2356) into descriptors/diag/fault/vsyscall, and share the UART-diag printf between idt.rs and spinlock.rs (currently duplicated).
- De-duplicate per-arch sys_* bodies in display.rs and per-arch fns in loader.rs by writing once over the HAL; move genuinely-different aarch64 bodies into arch submodules and rename virtual_mem_stub.rs.
- Add a fast kernel-only test path (host cargo test for no-hardware suites + a headless run-kunit QEMU target).
- Split cmake/UserPrograms.cmake (1541 lines) into RustUserPrograms/RustApps/CLibs modules.

### Test gaps
The kernel ships a real in-kernel kunit framework (kunit/runner.rs; 16 unit suites + 3 integration suites covering buddy, heap-stress, slab/alloc, vma, physmap, blockcache, sync, net types, crypto, capabilities, syscall-safety, ipc, vfs-readahead). The gap is execution model, not coverage of primitives: ALL of it runs only during a full kernel boot under the `kunit` feature, so there is no `cargo test` and no headless CMake test target — pure-algorithm tests (buddy/heap/net-types/vma) that need zero hardware still cost a build-std + image + QEMU cycle. Concretely untested or untestable in the fast loop: (1) the Filesystem-trait dispatch and exFAT durability/commit logic (no FS-level kunit suite exists — the existing FS coverage is only vfs_readahead); (2) the scheduler's per-CPU static-mut state and work-stealing under SMP (scheduler_tests is integration-only and single-boot); (3) the spinlock's contended mid-spin-IRQ behavior; (4) swap (no test because there is no eviction path to test). Recommended: extract the no-hardware suites into a host-buildable crate behind a std shim for `cargo test` (fast inner loop for allocator/net/buddy), and add a `ninja run-kunit` target that boots QEMU headless with `--features kunit` and exits via an isa-debug-exit / serial PASS-FAIL parse for CI. For SMP/scheduler and FS-durability bugs that only reproduce on real boot, add serial-driven integration assertions (the existing kunit integration phase is the right hook) plus the vfsstress workflow the user already uses.

### Open questions
Proposed target module/layer architecture (strict downward dependency only):
  L0 arch (CpuOps/MmuOps/IrqController/Timer traits, one impl per arch; the ONLY place #[cfg(target_arch)] lives)
  L1 sync + memory (spinlock/mutex/waitqueue; physical/buddy/slab/heap/paging-via-Paging-trait/swap-with-reclaim)
  L2 ipc + bus/driver-model (generic BusAddr, BlockDevice/NetDevice/DisplayDevice/InputDevice sub-traits)
  L3 device drivers (impl the L2 sub-traits; depend on sync waitqueue, NEVER on task::scheduler)
  L4 fs (VFS dispatches ONLY through dyn Filesystem; exFAT/CoreFS/FAT/NTFS each fully own their durability) + net (depends on NetDevice + sync)
  L5 task (scheduler/loader; the ABI personalities anyos/linux/windows are loader+syscall-table plugins)
  L6 syscall (thin: arg marshalling + capability check + dispatch into L0-L5; no business logic)
Enforcement: forbid upward edges via module visibility + a CI grep-gate (no `crate::task::` under drivers/, no `crate::syscall::` under fs/net/drivers, no `crate::arch::x86::` outside arch/).

Open questions for the user: (1) Is the long-term intent to keep three guest ABIs (anyOS/Linux/Windows) as first-class, or is Windows (syscall/windows ~2000 lines + loader/windows.rs 1485) experimental and prunable? (2) Should the exFAT-durability work in VFS migrate into the Filesystem trait as an explicit fsync()/barrier hook, given exFAT has no journaling? (3) Is CoreFS being deprecated as the system FS (CMakeLists forces exfat) — if so, can the CoreFS dispatch be removed from VfsState entirely to shrink vfs/mod.rs? (4) For aarch64, is the goal full parity (then a Paging trait + HAL trait is mandatory) or is x86 the only shipping target for now (then the cfg-fork debt can be deferred)?
